OAuth authorization code + PKCE — a login, then a silent token refresh 55 minutes later

Same solver seam as the login walkthrough and the checkout detour: four lifelines, one activation per row, every message an edge the run token rides. The authorization code never travels straight from the identity provider to the app backend — it bounces through the browser, and PKCE's code_verifier/code_challenge pair is what stops a stolen code from being redeemed by anyone else. Later, the access token quietly expires; the resource API's activation fails outright, and the app backend has to notice that on its own and start a brand-new activation to refresh it — a failed activation cannot hand anything to a successor, so there is no edge from the dead call to the retry.

    What to look for

    • PKCE: the code_verifier never leaves the app backend. Only the code and its challenge cross through the browser, so a stolen authorization code is useless to anyone who doesn't hold the verifier that minted its challenge.
    • Every redirect between the app and the identity provider bounces through the browser — the two never talk to each other directly during login, only during the code exchange and the later token refresh.
    • 55 minutes on, the access token has expired: the resource API's activation fails outright (red) and stops there. A failed activation is terminal for its branch — no finish event, no message out — so the retry can't be an edge from it; it's a fresh activation the app backend starts on its own.
    • The identity provider rotates the refresh token on every use, so the old one is dead the moment the new pair is issued.
