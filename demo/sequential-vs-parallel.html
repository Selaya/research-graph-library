  • Lockstep. Both run.play() calls start on the same beat and both clocks tick in declared minutes, so "the right one finished first" is readable off the two transport bars, not just the captions.
  • The total bar names both totals. The pipeline preset runs with total: "both", so the bar along the bottom of each pane reads sum … · critical …: the left chain has one number (3h 20m — in a straight pipeline the two agree, so the bar stays bare), while the right one sums the same 3h 20m of declared work next to a much shorter critical path. Re-wiring never removes work, only automation does (the right sum drops to 1.8h once the gate lands). The big numbers up top are run.sim().declared — the compiled schedule's wall clock, the same critical path the bar names.
  • The critical path is the point. Beat 2 highlights it: on the left it is all seven steps; on the right it is Build → Rel. notes → Sign-off → Deploy — the two ✋ manual steps dominate, and adding more parallel branches would not shave a minute off it.
  • Condense the bottleneck. Beat 3 merges Rel. notes + Sign-off into one ⚡ automated gate with g.condense(); the chip odometers 1h 40m → 6m with a delta badge, the graph gets one rank shorter, and the replay lands the right-hand run at 1h 05m.
  • Honest clocks. Both runs compile with hopMs: 0 and a linear dwell, so every millisecond on the timeline is declared step time and nothing else. Pacing is a separate dial — a bare playbackSpeed / speed(f) multiplies playback only, so the headline never moves when you change speed.
