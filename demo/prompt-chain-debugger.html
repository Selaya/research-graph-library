Prompt chain debugger — live mode, replaying one LLM request

A single customer turn walks through a six-step LLM chain: classify intent fans out to retrieve docs (one embedding query spawning four chunk reads) and load user profile, both AND-join into compose answer, then safety filter and respond. The trace is fed in as it happens with g.run({mode:"live"}) — start / finish / spawn / fail — and every step carries the payload a debugger would want: prompt, model, tokens in/out, latency. The safety filter blocks the first draft, so the chain takes its bounded retry edge back to compose answer.

  • Runtime fan-out: retrieve docs gets run.spawn(id, 3) on top of its own token — the ×4 occupancy badge is four chunk reads sharing one node.
  • join:"all": compose answer has two non-loop in-edges, so it waits for both branches; the join tile counts arrivals, and all five context tokens (4 chunks + the profile) sit on the node before it starts.
  • The block: run.fail("safety", {reason}) is finish()'s terminal sibling — it consumes every occupant and fans nothing out, so respond stays dark. Watch the node turn red and the caption name the rule.
  • The retry: the dashed arc back to compose answer is loop:true, maxIterations:2. Restarting the failed branch with an explicit start() is what ticks it — the badge reads 1/2.
  • Time travel: once the trace ends, clicking a node scrubs the live run back to that step (run.seek) and shows its payload; Back to live is run.follow(). The transport bar under the graph scrubs the same log.

Chips under each node are data.duration — the latency that step actually took. Dashed pips are live occupancy; the highlighted node is g.highlight({variant:"focus", dim:true}), the spotlight the inspector is pointed at.
