Prompt chain debugger — live mode, replaying one LLM request

A single customer turn walks through a six-step LLM chain: classify intent fans out to retrieve docs (one embedding query spawning four chunk reads) and load user profile, both AND-join into compose answer, then safety filter and respond. The trace is fed in as it happens with g.run({mode:"live"}) — start / finish / spawn / fail — and every step carries the payload a debugger would want: prompt, model, tokens in/out, latency. The first draft runs over its declared budget and the safety filter then blocks it, so the chain takes its bounded retry edge back to compose answer.

  • Runtime fan-out: retrieve docs gets run.spawn(id, 3) on top of its own token — the ×4 occupancy badge is four chunk reads sharing one node.
  • join:"all": live mode honours join, so compose answer's two non-loop in-edges really gate it: arrivals are held on the node (the pips fill, state().nodes.compose.waiting counts them) and each group of two is released as one unit of work — five context tokens (4 chunks + the profile) do not become five drafts downstream.
  • Over budget: each node's chip is its declared data.duration, which in live mode is an expectation, not a schedule. The first draft outruns its 1.2 s budget, so state().nodes.compose.overBudget flips and the renderer marks the node data-over-budget — the dashed boundary. The retry comes in under budget and the mark clears.
  • The block: run.fail("safety", {reason}) is finish()'s terminal sibling — it consumes every occupant and fans nothing out, so respond stays dark. Watch the node turn red and the caption name the rule.
  • The retry: the dashed arc back to compose answer is loop:true, maxIterations:2. Restarting the finished branch with start("compose", {spawn:true}) — the explicit "yes, mint a token here" form — is what ticks it; the badge reads 1/2.
  • Time travel: once the trace ends, clicking a node scrubs the live run back to that step (run.seek) and shows its payload; Back to live is run.follow(). Clicks arrive on g.on("nodeclick"), so a pan never reads as a tap and Enter on a focused node inspects it too. The transport bar under the graph scrubs the same log.

Chips on each node are data.duration — the budget that step is allowed; the real latency it reported is in the inspector. Dashed pips are live occupancy; the highlighted node is g.highlight({variant:"focus", dim:true}), the spotlight the inspector is pointed at.
