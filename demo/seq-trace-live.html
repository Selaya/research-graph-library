What to look for

  • Click any activation — or the message arrow that delivered it — to read the span behind it: g.on("nodeclick") / g.on("edgeclick"). The inspector bar shows where that span sits inside the 1 322 ms request.
  • Every lifeline is declared container: true, so a service is a dashed, header-only column from the first frame and fills in as its activations arrive.
  • Rows are trace order. reserveStock and GET /v2/quote share a row because orders-svc fanned out to both at once — one finish(), two tokens.
  • pricing-svc answers 500: run.fail() consumes that token and fans out nothing, so the branch simply dies mid-diagram. It also blew the 60 ms p99 budget the span declares as data.duration, so the box picks up the dashed data-over-budget boundary and the meter counts it.
  • A parent's dispatch instant is its child's start instant in a real trace — every hop would be zero-length. minHopMs holds the crossing open so the ball is visibly on the wire; the timestamps are the raw span stamps, untouched.
  • orders-svc handles it with a fallback span — an explicit start(), the only thing that gets a token back after a failure. It is a leaf: nothing leaves it.
  • Each postgres statement is a nested span on the same lifeline, so the ball stays in that column until COMMIT returns.
  • At the end the view clock scrubs back to the 500 while the frontier keeps running — then follow() snaps it to now.
