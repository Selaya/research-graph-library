# Research: Cyclic graphs in layered layout

> One of 7 parallel research passes behind docs/PLAN.md · 2026-08-29

## Summary

Sugiyama/layered layout requires an acyclic input, so cyclic pipeline graphs are handled by a Cycle-Breaking phase: detect a feedback-arc-set (FAS) and reverse those edges in-model only (never in the semantic direction shown to the user), layer/route as a DAG, then restore + re-mark the reversed edges as "back edges" for distinct rendering. Two proven heuristics dominate practice: cheap DFS back-edge detection (what dagre uses by default) and the Eades-Lin-Smyth greedy degree-bucket heuristic (dagre's `acyclicer:'greedy'`, and ELK's default `GREEDY_MODEL_ORDER`/`GREEDY` cycle breaker) — both are O(V+E)-ish, NP-hard-optimal FAS is never used in real layout engines. Back edges must be routed and styled distinctly (curved/side-routed, not just a reversed straight segment) or a loop reads as a rendering glitch — this is a documented, still-open pain point in Mermaid, and a well-solved one in Graphviz/dagre (side-arcing self-loops) and in the 2025 VEIL CFG-layout paper (grouping all back-edges to one consistent side). For compound/container interaction, the strongest pattern from BPMN and CFG tools is to avoid spanning back-edges across container boundaries at all where possible — represent an internal loop as a marker/badge on the (collapsed) container node itself, and only draw a routed arc when the loop genuinely crosses sibling containers. Incremental stability (append/expand-collapse without back-edges flipping) is a known hard sub-problem; dagre just shipped a "dynamic" mode (3.1.0, 2026) that consults the previous graph's ranks to keep the same edges reversed across re-layouts, following the older DynaDAG mental-map-preservation lineage. A minimal from-scratch DFS-cycle-breaking + distinctive-routing implementation is realistically 350–550 LOC, closely bounded by dagre's own real module sizes (acyclic.ts 112 LOC + greedy-fas.ts 150 LOC = 262 LOC for detection/reversal alone, plus ~70–100 more LOC elsewhere in layout.ts for self-loop extraction/insertion/positioning).

## Recommendation

Adopt a 4-part design:

1. **Detection: DFS back-edge detection as the default, greedy-FAS as an opt-in upgrade.** Run a plain DFS from source nodes (then any unvisited node) and classify any edge to a node currently on the recursion stack as a back edge (this is exactly dagre's `dfsFAS`, ~40 lines of real logic). This is deterministic, cheap, stable under a fixed traversal order, and "good enough" for the target use case (human-authored pipeline graphs, not large messy digraphs) where minimizing reversed-edge count matters less than predictability. Offer the Eades-Lin-Smyth greedy heuristic (dagre's `greedy-fas.ts`/ELK's `GREEDY`) behind a config flag for users who want fewer/better-chosen back edges on dense cyclic graphs — do not make it the default; it adds real complexity (degree-bucket priority queue) for a benefit that mostly matters at graph sizes above what "embeddable in a static HTML page" implies.

2. **Reversal bookkeeping must be non-destructive and reversible.** Mirror dagre's `acyclic.run`/`undo`: on each layout pass, flip reversed edges only in the internal ranking graph, tag them (`edge.reversed = true`, keep `forwardName`), run the normal layered algorithm, then walk the result and (a) restore semantic direction for hit-testing/labels/arrowheads, (b) keep a `reversed` flag on the render model so the edge renderer can style it differently. This tagging is also exactly the hook needed for the "loop stepping" animation to know which edges represent a loop-back transition vs. forward progress.

3. **Route and style back edges so a loop unmistakably reads as a loop, and prefer node-local loop markers over spanning arcs for self-contained loops.**
   - **Self-loops** (single-node retry/iterate-on-self): don't animate a token flying around an edge on every iteration. Real tools (Temporal timeline, Airflow graph view, Argo Workflows) show retries as an in-place badge/counter on the node ("Retry 2 of 3") rather than literal loop traversal — replicate this: render a small side-arcing self-loop glyph (dagre/Graphviz style: a 7-point spline bowing out from one side of the node and back, NOT looping through the node like Mermaid's known-buggy default) plus an animated counter/pulse for stepping through iterations. This sidesteps layout instability entirely since the loop never touches the layered coordinate system.
   - **Loop wholly inside one (possibly collapsed) compound container**: treat it like case above at the container's boundary — either keep it as an internal self-loop-style arc if the container is collapsed, or let it be a normal internal back-edge among the container's children when expanded (case 4).
   - **Loop spanning ranks/nodes** (retry-from-step-3-back-to-step-1): route as a curved or orthogonal arc placed consistently to one side of the layout (pick "left of the main flow" or "below the row," but be consistent graph-wide) rather than reusing the same channel forward edges use — this is the concrete fix for what Mermaid gets wrong and what VEIL's 2025 paper explicitly does ("grouping back edges to the left... more readily exposes nested loops"). Give back-edges a distinct visual channel (dashed stroke, different color/opacity, or an arc bowing outward past the node column) so the eye distinguishes "flow forward" from "loop back" without reading the arrowhead direction.
   - **Loop spanning multiple compound containers**: route the arc entirely outside both containers' combined bounding boxes (analogous to CFG tools shading the convex hull of a loop's nodes and highlighting the back edge) — never punch a back-edge through a container's interior. If the loop is meant to look "contained," prefer BPMN's own answer: don't draw a spanning edge at all — express it as a loop-marker glyph (small curled-arrow icon, BPMN's "standard loop" marker) on the outer/collapsed container node, and only reveal the literal retry arc when the user expands into substeps.

4. **Stability under incremental append/expand-collapse: pin the FAS decision, don't recompute it blind.** Keep a per-edge stable ID and a `wasReversed` flag from the prior layout pass; when re-running cycle-breaking after an append or an expand/collapse, seed DFS traversal in the same node-insertion order as before and prefer leaving previously-reversed edges reversed unless the structural change genuinely forces a different choice (mirrors dagre 3.1.0's new `useDynamic`/`corePath` mode, which consults `oldGraph` ranks specifically to avoid re-flipping edges on unrelated changes, and the older DynaDAG "penalize deviation from previous assignment" principle). Without this, every append can silently flip which edge in a cycle is drawn as the "back edge," causing an unrelated loop elsewhere in the diagram to visibly jump — a serious animation/mental-map violation given this library's "smooth transition on any change" requirement.

**LOC estimate**: budget ~150–200 LOC for DFS cycle-breaking + reversal/undo bookkeeping, +100–150 LOC for self-loop extraction/side-arc rendering, +100–150 LOC for distinctive multi-node back-edge routing (consistent-side arc computation + style hook), +~50 LOC for the stability/pinning bookkeeping across relayouts = **~400–550 LOC** total for a minimal but real implementation, skip greedy-FAS (~150 LOC saved) unless dense-cycle graphs are a priority. This is directly bounded by dagre's real, shipping numbers (262 LOC for `acyclic.ts`+`greedy-fas.ts` alone, using TypeScript at similar terseness to what a from-scratch minimal engine would target).

## Details

## 1. Cycle detection / feedback-arc-set algorithms

- **Problem framing**: Minimum FAS is NP-hard; all production layout engines use heuristics, not exact solvers. (Feedback arc set, Wikipedia; corroborated by dagre and ELK docs.)
- **DFS back-edge detection** (simplest, what a "from scratch" engine should start with): standard DFS; any edge to a node currently on the recursion stack is a back edge → reverse it. This is exactly dagre's default (`acyclicer` unset ⇒ `dfsFAS`). Source, `/lib/acyclic.ts` (dagrejs/dagre, cloned & read directly, 112 LOC total file):
  ```ts
  function dfsFAS(graph, oldGraph) {
    const fas = []; const stack = {}; const visited = {};
    function dfs(v) {
      if (Object.hasOwn(visited, v)) return;
      visited[v] = true; stack[v] = true;
      graph.outEdges(v).forEach(e => {
        if (Object.hasOwn(stack, e.w)) fas.push(e);
        else dfs(e.w);
      });
      delete stack[v];
    }
    graph.sources().forEach(dfs);
    graph.nodes().forEach(dfs); // catches nodes unreachable from any source
    return fas;
  }
  ```
  Notably dagre also ships a **`dfsDynamic`** variant used only when a previous layout (`oldGraph`) is supplied: it additionally reverses an edge if the *old* rank ordering combined with reachability-without-that-edge suggests the new edge would otherwise flip an unrelated part of the graph — this is dagre's mechanism for **incremental layout stability** across cyclic graphs (see §4).

- **Eades–Lin–Smyth greedy heuristic** ("A fast and effective heuristic for the feedback arc set problem," Information Processing Letters 47(6), 1993): repeatedly strip sinks (indegree considerations) and sources from the graph into an ordering; leftover cycle edges become the FAS. Runs in linear time; produces FAS ≤ m/2 − n/6 edges (better on sparse graphs, ~m/3). This is dagre's `acyclicer:'greedy'` option and ELK's default `GREEDY`/`GREEDY_MODEL_ORDER` cycle breaker (ELK's `GreedyCycleBreaker.java`, 286 lines, explicitly cites Eades-Lin-Smyth in its javadoc — confirmed by reading the raw source at `github.com/eclipse-elk/elk` `plugins/org.eclipse.elk.alg.layered/src/.../p1cycles/GreedyCycleBreaker.java`).
  - dagre's implementation (`/lib/greedy-fas.ts`, 150 LOC, read directly): maintains degree "buckets" (a `List[]` indexed by `out-in+zeroIdx`) so it can repeatedly dequeue current sources/sinks in O(1) amortized, giving near-linear performance; multi-edges are aggregated by weight before running, then expanded back out afterward.

- **Practical comparison**: DFS is simpler, faster to implement (~40 core lines), and deterministic given a fixed node/edge iteration order, but its FAS quality (which edges get flagged as "back") depends entirely on DFS root/traversal order — a different insertion order can produce a different, non-minimal set of back edges. Greedy-FAS gives better (smaller, more "natural") back-edge sets independent of arbitrary traversal order, at ~3-4x the implementation cost and added data-structure complexity (bucket priority queue). Both are what's actually shipped in dagre/ELK — no widely used JS/Java layout engine implements an exact minimum-FAS solver.

## 2. How dagre and ELK handle cyclic input in practice

- **dagre** (`dagrejs/dagre`, verified against the live 2026 source, v3.1.0):
  - Pipeline order (from `layout.ts`, confirmed by reading the file, order preserved): `makeSpaceForEdgeLabels → removeSelfEdges → acyclic.run → nestingGraph.run → rank → ... → order → insertSelfEdges → adjustCoordinateSystem → position → positionSelfEdges → removeBorderNodes → normalize.undo → acyclic.undo (implied later) → ...`
  - **Self-loops are pulled out before cycle-breaking even runs** (`removeSelfEdges`) so a node's own self-loop never participates in FAS computation or ranking at all — it's stashed on the node as `node.selfEdges[]` and re-inserted post-layout (`insertSelfEdges`) as a dedicated dummy node of type `"selfedge"` placed adjacent to its owner in the same rank/order, then given a **fixed 7-point spline** bowing out from one side of the node: `[{x:0,y:-10},{x:0,y:-10},{x:0,y:0},{x:0,y:10},{x:0,y:10},{x:0,y:0},{x:0,y:0}]`, later re-projected onto real node coordinates in `positionSelfEdges` (`{x:nodeX+dx,y:nodeY-dy} → {x:nodeX,y:nodeY} → {x:nodeX-dx,y:nodeY+dy} → ...` where dx/dy derive from node width/height/2). This is the concrete "side-arc loop" convention worth copying wholesale.
  - **Cycle-breaking proper** (`acyclic.run`, described in §1) runs on the remaining (self-loop-free) edges; reversed edges get `label.reversed = true` and `label.forwardName` set, are removed and re-inserted in the opposite direction under a fresh `uniqueId("rev")` name; `acyclic.undo` walks all edges post-layout, finds `reversed` ones, and swaps them back to their original name/direction so the caller/renderer sees semantically correct direction with a `reversed` flag available for styling.
  - **New in 3.1.0 (2026)**: "Dynamic Graph Layout Support" (`useDynamic`, `corePath` options) — explicitly built for "persistent node ordering and layout stability when modifying graph structures" (project CHANGELOG.md, read directly from the cloned repo). This feeds a `previous` layout's graph/ranks into `dfsDynamic` so re-running layout after a graph edit doesn't arbitrarily re-choose different back-edges. Directly validates that incremental append/edit stability for cyclic graphs is a real, recently-addressed problem in the most popular JS layered-layout engine — worth adopting the same "seed from previous FAS decision" pattern from day one rather than retrofitting it later.

- **ELK layered** (Eclipse Layout Kernel, used via `elkjs` in the browser):
  - `cycleBreaking.strategy` option offers: `GREEDY` (default; `GreedyCycleBreaker.java`, in/out-degree based with random tie-break, cites Eades-Lin-Smyth + Di Battista et al.'s "Graph Drawing" textbook §9.4 directly in its javadoc), `DEPTH_FIRST` (`DepthFirstCycleBreaker.java`), `GREEDY_MODEL_ORDER` (ties broken by input/model order — useful for *stability*, since re-running layout on the same textual node order reproduces the same FAS choice), `INTERACTIVE` (uses previously-set node positions — ELK's own answer to incremental stability), `SCC_CONNECTIVITY` / `SCC_NODE_TYPE` (Tarjan's SCC decomposition first, then break within each SCC).
  - Reversed edges are documented to render pointing the opposite direction of normal flow ("reversed edges will point left if edges usually point right" — i.e., ELK's baseline convention is *direction-only* distinction, not automatically a distinct visual style — an application-level styling pass on top is still needed for a "reads as a loop" effect).
  - Self-loops: `insideSelfLoops.activate` option lets a self-loop be routed *inside* a node (turning it into a compound node with hierarchical ports) instead of the more common "route around the outside" approach; `edgeRouting.selfLoopDistribution`/`selfLoopOrdering` control spacing/stacking of multiple self-loops on one node, but only apply under `PortConstraints.FREE`.

## 3. Visual conventions for loops in real tools

- **BPMN**: "Standard loop" = a small curled-arrow marker glyph placed at the bottom of the activity/task shape itself (not a spanning edge) — indicates "this single activity repeats until a condition holds." Multi-instance loop = three vertical/horizontal bars (III / ≡) marker, same placement pattern. Key insight: BPMN's default answer to "how do you show a loop on a task" is a **node-local marker**, not a routed back-edge — this is the strongest, most battle-tested precedent for the "loop inside a container" question in your requirements. (Camunda BPMN reference, Creately BPMN guide, Lucidchart BPMN activity guide.)
- **UML state machine diagrams**: self-transitions/loops are drawn as small looped arcs to the side of the state, and multi-state loops as two arcs facing each other (concentric, slightly different radii for the label) — i.e., always curved, never a straight reversed line. (uml-diagrams.org.)
- **Mermaid flowcharts/state diagrams**: documented, currently-tracked bug where self-loops render with an ugly kink — "the edge was about to point to a different node, but then realized it was heading in the wrong direction and doubled back on itself" — explicitly contrasted against Graphviz's cleaner side-arcing loops as the target fix (mermaid-js/mermaid issue #6336, "Approved," linked to PR #7711). Concrete cautionary example: **don't** synthesize a self-loop by just reusing generic edge-routing code with source==target; special-case it like dagre does.
- **VEIL (Schaad, Ben-Nun, Hoefler, 2025, "Reading Control Flow Graphs Like Code")**: a very recent (Nov 2025) CFG-layout paper whose key layout innovation is **grouping all back-edges consistently to one side of the layout** (e.g., "to the left"), which the authors show "more readily exposes the presence of a 2-level nested loop" — i.e., consistent-side routing (not case-by-case shortest-path routing) is what makes nested loops legible at a glance. Directly informs recommendation §3 above.
- **General CFG visualization literature** ("Domain-Centered Support for Layout, Tasks, and Specification for Control Flow Graph Visualization," arXiv 2108.03047, found via search snippet): loop rendering convention = shade the convex hull/background of the loop body's nodes *and* separately highlight the back edge itself — a two-part visual cue (region + edge), which is stronger than styling the edge alone and worth considering for compound-node loops.
- **Workflow/CI retry visualization (Temporal, Airflow, Argo Workflows)** — the load-bearing finding for "stepping through loop iterations": none of these tools animate a token literally traveling backward around a loop edge for each retry. Temporal's Timeline View shows "a retry icon with the current attempt number" on the same activity row. Airflow's graph view logs "Retry 1 of 3" as a per-task-instance status/counter, recoloring the same node. Argo Workflows models retries via a `retryStrategy` that re-executes/reconciles the *same* node in place rather than drawing a fresh loop traversal. **Implication**: for the "animated progression through loop iterations" requirement, favor an in-place badge/counter + pulse/recolor animation on the looping node/edge over literally re-animating a token around a drawn back-edge every iteration — cheaper, more legible, and avoids re-triggering layout-stability concerns on every iteration tick. Reserve the literal "animate along the back-edge arc" treatment for a first-iteration or user-triggered "show me the loop" moment, not for routine per-iteration ticking.

## 4. Compound nodes and stability

- **Loop inside one expanded container**: treat identically to a normal loop among sibling nodes in that container's own sub-layout — no special handling needed beyond running cycle-breaking scoped to the container's internal subgraph.
- **Loop spanning containers / crossing a collapsed container's boundary**: general compound-graph guidance (yFiles hierarchical-layout docs, cytoscape.js-expand-collapse) — route such edges around/outside the collapsed container's box rather than through it; "recursive edges" (edges that re-enter/exit at a stable port on the group boundary) are noted to be more stable across expand/collapse specifically *because* their attachment point on the container doesn't move when internal children get rearranged — worth adopting as a rule: back-edges that cross a container boundary should attach to a fixed boundary port, not to a point on whichever internal node happens to be nearest, so collapsing/expanding that container doesn't perturb the arc's endpoint.
- **Stability under incremental append/expand-collapse (general problem)**: this is the classic "mental-map preservation" problem in dynamic graph drawing (surveyed under that name broadly). The canonical historical reference is North's **DynaDAG** (GD'95/96, "Incremental Layout in DynaDAG") — adds explicit variance-penalty constraints so a new layout stays close to the previous one's rank/position assignment rather than being solved fresh each time; its descendant "Online Hierarchical Graph Drawing" (North & Woodhull) extends this to streaming/online graphs. Both predate FAS-stability specifically for cycles, but the mechanism generalizes directly: **pin the previous FAS choice as a soft constraint** when re-running cycle-breaking, exactly what dagre 3.1.0's new dynamic mode now does concretely for cyclic inputs (see §2). Without this, a layout engine re-run from scratch after every append can non-deterministically choose a *different* edge in the same cycle to reverse, causing a loop drawn on one side of the diagram to visibly "jump" to the other side after an unrelated, distant edit — a direct violation of this library's "smooth animated transitions on any graph change" requirement.

## 5. Implementation cost estimate (grounded, not guessed)

Measured directly from the dagre source (cloned `dagrejs/dagre`, `git rev-parse HEAD` confirms current default branch, read via `Read` tool):
- `lib/acyclic.ts`: 112 LOC (DFS/dynamic-DFS cycle detection + reverse + undo, dispatch between DFS/greedy modes)
- `lib/greedy-fas.ts`: 150 LOC (Eades-Lin-Smyth greedy heuristic with degree-bucket priority structure)
- Self-loop extraction/insertion/positioning logic lives inline in `lib/layout.ts` (772 LOC total file) across `removeSelfEdges`, `insertSelfEdges`, `positionSelfEdges` — roughly 70–90 LOC combined based on the excerpted functions.
- ELK's equivalent Java `GreedyCycleBreaker.java` is 286 lines, but Java's verbosity (imports, javadoc blocks, explicit typing) inflates this well past the equivalent JS/TS line count — dagre's own 150-line greedy-fas.ts implements the same algorithm.

**Estimate for a minimal from-scratch layered engine**: 
- DFS-based cycle-breaking + reversal/undo bookkeeping: **150–200 LOC**
- Self-loop special-casing (extraction + side-arc spline + positioning): **100–150 LOC**
- Distinctive multi-node back-edge routing (consistent-side arc/orthogonal detour computation + style hook): **100–150 LOC**
- Stability/pinning bookkeeping across incremental relayouts (stable edge IDs, "prefer previous reversal choice"): **~50 LOC**
- **Total: ~400–550 LOC.** Add greedy-FAS as an optional upgrade for +120–150 LOC if dense/large cyclic graphs turn out to matter for this library's actual use cases (they likely don't, given the target is human-authored pipeline/workflow graphs with modest node counts).

## Risks & caveats

- **Egress restrictions limited primary-source verification for several items.** Direct WebFetch access to arxiv.org, eclipse.dev, docs.yworks.com, link.springer.com, deepwiki.com, and r.jina.ai was blocked by the environment's proxy for this session. Claims sourced from those domains (VEIL's back-edge-grouping specifics, ELK's full strategy-list nuances, yFiles "recursive edges" stability claim, DynaDAG's exact mechanism) rest on WebSearch's own indexed/summarized snippets of those pages rather than a full-text read I performed myself — treat these as good leads to re-verify with direct access before citing them as load-bearing design justification in a public-facing spec. The dagre source-code claims (§1, §2, §5), by contrast, were verified by cloning the actual repository and reading the files directly, so those are high-confidence.
- **DFS-based cycle breaking is order-dependent and not unique.** Two logically-equivalent graphs built via different node/edge insertion order can produce different back-edge sets, which matters a lot for the stability requirement — the recommended mitigation (seed from previous FAS choice) reduces but does not eliminate this; a structural change that genuinely removes the previously-reversed edge will still force a fresh, potentially different choice, and that transition should get its own smoothing animation rather than an instant jump.
- **Greedy-FAS quality bound (≤ m/2 − n/6 edges, or ~m/3 for sparse graphs) is an upper bound on a heuristic, not a guarantee of a "natural-looking" back-edge set** — on adversarial or unusually structured graphs (e.g., many overlapping cycles sharing few nodes) it can still choose a back edge that looks arbitrary to a human reader; visual QA on real motivating-use-case graphs (retry loops + parallel branches together) is advisable before shipping either heuristic as default.
- **Interaction between cycle-breaking and the "parallel branches at different rates" requirement is out of this dimension's scope** but worth flagging for the synthesis step: a back edge from a slow parallel branch rejoining an earlier rank can force that branch's whole rank range to be re-treated as part of a cycle, potentially entangling fan-out/fan-in layout with loop layout in ways not covered by dagre/ELK's largely independent phase pipelines (cycle-breaking runs once, globally, before ranking) — the other research dimension on parallel branches should confirm this doesn't create a conflicting layout requirement.
- **BPMN's "node-local loop marker instead of spanning edge" pattern is a strong recommendation but is a UX/semantics choice, not purely a layout one** — it works well when a loop is a self-contained "retry-this-step" construct, but a genuine explicit "step 5 retries back to step 2" pipeline model (named in the motivating use case) is not well served by hiding it as a marker; the two representations (marker vs. routed arc) likely need to coexist and the criterion for choosing between them (single-node self-loop vs. multi-node/cross-container loop) should be made an explicit rule in the graph spec design, not left ambiguous.
