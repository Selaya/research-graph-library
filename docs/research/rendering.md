# Research: Rendering technology & animation machinery

> One of 7 parallel research passes behind docs/PLAN.md · 2026-08-29

## Summary

For 10–2000-node pipeline graphs with discrete, event-triggered animations (not continuous force simulation), native SVG + CSS/WAAPI for transform/opacity + a small custom rAF tween engine for path-geometry morphs is the right primary approach. Measured evidence: every off-the-shelf graph engine blows the <50KB budget by itself (cytoscape core 133KB gzip, sigma+graphology ~61KB gzip, konva 57KB gzip, pixi.js 230KB gzip), so a custom renderer is mandatory regardless of technology choice — which removes "adopt an existing engine" from consideration and makes SVG's near-zero code cost (it's just DOM you're building anyway) decisive. Canvas/WebGL performance advantages (cytoscape's own WebGL-preview benchmarks: 20→100+FPS at 1,200 nodes/16,000 edges, 3→10FPS at 3,200 nodes/68,000 edges) only bite at edge counts an order of magnitude above what a 2,000-step pipeline DAG will ever have, and they cost real complexity for hit-testing (manual quadtree or GPU color-ID picking pass), text (sigma itself punts SVG-free WebGL text and draws labels on a separate Canvas2D overlay layer), and accessibility (must build a fully parallel shadow DOM). SVG gives native hit-testing, native text layout, native accessible DOM nodes, trivial SVG/PNG export, and — critically for this library's requirements — CSS transitions/WAAPI on transform+opacity run on the browser compositor thread, decoupled from the main-thread JS driving layout/morph logic, which is exactly the robustness profile a "playhead + morphing + expand/collapse" library needs.

## Recommendation

**Primary rendering: pure SVG (inline `<svg>`, no canvas/WebGL) with a hybrid animation engine: CSS/WAAPI for anything expressible as transform+opacity+color, a tiny (~2–4KB) custom rAF tween scheduler for path/`d` geometry and choreography WAAPI can't do.**

Architecture:
- **Scene model**: one `<svg><g id="viewport">…</g></svg>`. Each node is `<g class="node" transform="translate(x,y) scale(s)">` containing a shape (`rect`/`circle`/`path`) + native `<text>`/`<tspan>` (only opt into `foreignObject` for rich HTML node content, since it complicates PNG export and has Safari quirks). Each edge is a `<path>` with `marker-end`, plus a `<text>` at the midpoint for labels. Compound nodes are nested `<g>` subtrees, toggled between a "summary" child and an "expanded" child.
- **Node move / enter / exit**: driven by `Element.animate()` (WAAPI) directly on `transform` and `opacity` — zero bytes of dependency, browser-native easing, compositor-thread execution (survives main-thread jank from the rest of the app), and `.finished` promises for sequencing (e.g., "fade out summary → then swap DOM → then fade in children"). No CSS-class-transition indirection needed; WAAPI gives programmatic control (pause/reverse/seek) that a state-driven pipeline visualization needs (e.g., scrubbing the playhead backward).
- **Edge geometry / morph**: NOT via CSS transitions on the `d` attribute — the `d` CSS property is not yet Baseline/universal across engines, and WAAPI cannot animate raw SVG attributes at all (only CSS properties) in any current browser. Instead, drive edge `d` recomputation from the small custom rAF loop: each active "geometry tween" stores endpoint/control-point pairs (from → to) and an eased progress `t`; every frame it lerps the points and rewrites the `path`'s `d` string. This sidesteps cross-browser gaps entirely and is ~1KB of code (simple linear/quadratic interpolation is sufficient for edge rerouting — no need for general topological shape-morphing libraries like flubber, measured at 18.2KB min+gzip, which solve a harder problem than this library needs).
- **Expand/collapse (compound nodes)**: FLIP-style. On expand: capture the compound node's collapsed bbox (First), swap in the child subgraph laid out normally (Last), then set each child's initial transform to the parent's collapsed position/scale/opacity-0 and let WAAPI animate every child's transform+opacity to its real layout position simultaneously (staggered by a few ms per child via `animate({...}, {delay: i*12})` for a "bloom" feel). Collapse reverses the same tweens. This is the same FLIP technique GSAP's Flip plugin packages (9.7KB gzip) — cheap enough to hand-roll here since it's just "compute two rects, animate one transform," so no dependency needed.
- **Morph / condense (N→1)**: compute a target point (centroid or the merged node's final position). Each source node gets a WAAPI transform+opacity tween converging on that point (shrinking scale to ~0, fading out) while the merged node's tween grows from scale~0.2/opacity 0 at that same point to its full layout position/size — this reads as "several things collapsing into one." Any edges whose endpoint changes from an old node to the merged node are handled by the geometry-tween engine (rAF-driven `d` rewrite) run with the *same* progress clock as the transform tweens so everything is visually synchronized. Use an ease-in-back or overshoot cubic-bezier on the merged node's entrance to add "impact" emphasis communicating the speed-up; this is a plain `cubic-bezier()` easing string, zero additional bytes.
- **Playhead**: a single WAAPI `Animation` (or the custom scheduler if the path is non-linear) advancing a `t` over the pipeline's cumulative duration, positioning a marker via `transform` each frame (composited, cheap even during scrubbing) and toggling `data-state="pending|active|done"` attributes on step nodes as thresholds are crossed — state recoloring itself becomes a plain CSS transition (`transition: fill 200ms`), no JS per-node work needed. WAAPI's native `playbackRate`, `pause()`, `currentTime` give free play/pause/scrub/speed controls without extra code.
- **Zoom/pan**: hand-rolled (~1–2KB): pointer events update `translate/scale` on the single `#viewport` `<g>`, rAF-throttled. Do not pull in d3-zoom (3.45KB alone, but requires d3-selection+d3-drag+d3-interpolate+d3-transition, ~12–15KB combined, measured) or panzoom (9.2KB gzip, measured) — budget is too tight and the feature is simple 2D affine-transform math plus wheel/pinch handling.
- **Export**: SVG export is `new XMLSerializer().serializeToString()` plus inlining used styles — a few lines, no dependency, always available because SVG *is* the source of truth. PNG export: serialize → data URL → draw into an offscreen canvas at target DPI → `toBlob()`. This is a decisive practical advantage: Canvas/WebGL-primary designs (cytoscape, sigma) need a *separate* SVG-emitting code path to support vector export (cytoscape ships this as the separate `cytoscape-svg` extension) because their draw calls aren't naturally serializable.
- **Accessibility**: because nodes/edges are real DOM elements, attach `role="graphics-symbol"`/`button`, `aria-label` (step name + duration + status), and model compound expand/collapse with the WAI-ARIA treeitem pattern (`role="treeitem"`, `aria-expanded`, arrow-key nav) essentially for free. Still ship a linearized text/table fallback of the pipeline (step list with durations/status) regardless of renderer — real screen-reader graph comprehension needs a non-visual alternative representation either way (true for SVG or Canvas equally), but SVG removes the cost of building and keeping in sync a fully parallel shadow-DOM overlay, which is the only way to get any accessibility out of a Canvas/WebGL-primary renderer.
- **Escape hatch, not a rewrite**: if a user pushes past ~2,000–5,000 simultaneously-visible/animating nodes, the fix is viewport culling (only mount/animate on-screen nodes, same technique React Flow and Cytoscape use) rather than switching rendering technology — keep this as a documented (v-next) optimization, not a v1 requirement, since it's outside the stated 10–500 (stretch 2000) target.

## Node-count thresholds (from search/benchmarks, dates noted)

- **D3 force-directed SVG, continuous simulation**: lag reported starting at **300–400 nodes** when the physics tick updates SVG attributes (x1/y1/x2/y2) every animation frame for every element; profiling showed ~80% of frame time in DOM attribute writes (Starlog "Force-Graph: Why Canvas Beats the DOM," Bugzilla #1214365/#1259142, d3/d3#1519). This is the *continuous, whole-graph, every-frame* case — not our use case (our animations are discrete, event-triggered, and touch a bounded subset of nodes at a time).
- **General SVG DOM-element ceiling** (multiple 2025/2026 comparison articles, consistent claims): SVG "works well up to a few thousand elements," degrades noticeably past that; ">5,000 elements usually causes lag." Canvas is described as "the clear winner" once you're juggling "hundreds if not thousands" of objects needing per-frame redraw.
- **Cytoscape.js Canvas2D vs. its new WebGL-preview renderer** (official blog, Jan 2025, `blog.js.cytoscape.org/2025/01/13/webgl-preview`): EnrichmentMap network, ~1,200 nodes / **16,000 edges** — 20 FPS (Canvas2D) → 100+ FPS (WebGL). NDExbio network, ~3,200 nodes / **68,000 edges** — 3 FPS (Canvas2D) → 10 FPS (WebGL). Note the stress factor in both cases is **edge count** (16K–68K), not node count (1.2K–3.2K). A pipeline DAG at even the 2,000-node stretch goal with, say, 2–4× edges (4,000–8,000 edges) is well below the regime where Canvas2D itself started struggling for cytoscape, let alone where SVG would.
- **WebGL text rendering**: sigma.js — despite being WebGL-primary for nodes/edges — renders **labels on a separate Canvas2D layer** (`sigma-labels`/`sigma-hovers` canvases) rather than in WebGL, because WebGL text (glyph atlases/SDF) is expensive to build well. This is direct evidence that WebGL doesn't actually solve text-quality/complexity for a diagram library; it just relocates it.
- **WebGL hit-testing**: no free lunch — must maintain either a CPU-side spatial index (quadtree, as Cytoscape/sigma do) or a GPU color-ID picking pass (render every object as a flat unique color to an offscreen framebuffer, read back the pixel under the cursor) — a nontrivial extra render pipeline (webglfundamentals.org "WebGL Picking"), justified only at node/edge counts where CPU-side hit-testing itself becomes the bottleneck (tens of thousands+).

## Animation-primitive research

- **CSS transitions/WAAPI on `transform`/`opacity` run on the browser compositor thread**, separate from main-thread JS — they stay smooth even while the main thread is busy with layout/morph bookkeeping, whereas rAF-driven JS animation is main-thread and "vulnerable to jank whenever the main thread gets blocked" (multiple 2026 sources, e.g. webperf.tips "Eliminating Choppy Animations," Motion Magazine "Web Animation Performance Tier List"). This directly supports offloading node move/enter/exit/state-recolor to CSS/WAAPI and reserving the custom rAF loop only for geometry that has no CSS/WAAPI path.
- **WAAPI cannot animate SVG attributes, only CSS properties** — confirmed by multiple 2026 sources (browser-unplugged.net "The Web Animations API and SMIL/SVG: not there yet"); this rules out `element.animate()` for raw path `d`, or for `x1/y1/x2/y2` on `<line>`, motivating the custom rAF geometry-tween approach for edges.
- **CSS `d` property (path shape via CSS) is animatable in spec but not Baseline** — cross-engine support gaps remain (MDN/caniuse), and even where supported requires equal point-count/type between start and end paths — another reason to hand-interpolate edge endpoints in JS rather than rely on CSS path animation.
- **ARIA Tree View pattern** (W3C WAI-ARIA APG, `w3.org/WAI/ARIA/apg/patterns/treeview/`) is a ready-made, standard mapping for expand/collapse compound nodes: `role="treeitem"`, `aria-expanded`, `role="group"` for children, arrow-key expand/collapse navigation — directly reusable for compound pipeline steps since it's DOM/attribute-based and "free" on an SVG (or any real-DOM) renderer.
- **Canvas accessibility requires either `role="img"`+`aria-label"` (coarse, no per-node semantics) or fully duplicated fallback DOM content** (general accessibility literature, e.g. Chart.js accessibility docs, pauljadam.com canvas a11y demos) — for a library whose whole point is per-node interactivity (hover a step, expand it, click to scrub the playhead to it), the coarse `role="img"` option is inadequate, and the duplicate-DOM option means you pay the "DOM node count" cost you picked Canvas to avoid, just for the accessibility layer instead of the visual one — undermining Canvas's main rationale in this exact use case.

## Why small libraries chose what they chose (context for the recommendation)

- **Sigma.js → WebGL**: explicitly for large-graph GPU-accelerated throughput; sigma's own docs/community guidance says for "small graphs (a few hundred nodes) and/or highly customized rendering," reach for d3 (i.e., SVG/DOM) instead — sigma's own positioning agrees WebGL is the wrong tool at this library's target scale.
- **Cytoscape.js → Canvas2D** (with a 2025 WebGL-preview renderer added only for very large networks): chosen for the general "SVG is slow beyond a few hundred/thousand elements" concern typical of network-biology-scale graphs (thousands of nodes, tens of thousands of edges) — a scale regime well above this library's pipeline use case.
- **React Flow / xyflow → hybrid**: DOM (HTML) for nodes (so arbitrary rich interactive content is trivial and gets accessibility "for free"), SVG `<path>` for edges (cheap vector curves, easy `stroke-dasharray` "animated edge" effects out of the box) — validates the pattern of "real DOM/SVG for everything, no canvas," used successfully at node counts far beyond this library's target, and is architecturally the closest existing precedent to what's recommended here (though React Flow's node layer is HTML `div`s under `transform`, whereas this library can use SVG `<g>` throughout for a single coordinate/serialization system that also makes SVG/PNG export trivial).
- **Mermaid → SVG**: chosen because diagrams are typically small-to-medium and it needs high-quality text/typography and easy static export (docs, READMEs, wikis) — mermaid's cost is entirely in its multi-grammar parsing/layout engine, not in SVG-as-renderer (see bundle table above), reinforcing that SVG itself is not what makes a library big.

## What this rules in/out concretely for this library
- **Ruled out as primary**: WebGL (code cost for text/picking/accessibility unjustified below tens of thousands of elements; none of this library's targets reach that), adopting any existing full graph engine (all blow the size budget alone).
- **Ruled out as primary, viable as escape hatch only**: Canvas2D — real perf ceiling is edge-count in the tens of thousands, far above target; but if ever needed, a canvas fallback renderer could sit behind the same declarative API later without changing the public spec format.
- **Chosen**: SVG DOM + WAAPI/CSS (transform, opacity, color) for all discrete state-change animations, thin custom rAF scheduler (~2–4KB) purely for path-geometry tweening (edge rerouting/morphing) and for coordinating multi-element choreography timing, hand-rolled pan/zoom (~1–2KB) instead of d3-zoom/panzoom, and no shape-morphing dependency (flubber-class libraries solve a harder/bigger problem than "N boxes converge to 1 box" needs).

## Risks & caveats

- **Text-heavy/very dense views**: if a future feature renders per-node rich HTML (e.g., markdown descriptions, tables inside a node), pure SVG `<text>` can't do arbitrary layout — would need `foreignObject`, which has historically had Safari rendering/printing quirks and complicates the "just serialize the SVG" export story (foreignObject content sometimes fails to rasterize correctly across browsers when converting to PNG via canvas). Mitigate by keeping foreignObject opt-in/rare, not the default node-content path.
- **Mass-simultaneous animation**: if a user action animates a very large fraction of a 2,000-node graph at the same instant (e.g., "expand all" with no stagger, or a global re-layout), SVG could approach the jank territory documented for continuous force-directed updates (~300–400 nodes) even though our per-event animations are normally bounded and short-lived. Mitigate with built-in staggering (which also looks better) and viewport culling (skip animating fully off-screen nodes) as a documented pattern, not a rewrite trigger.
- **`d`-property/geometry-attribute cross-browser gaps are a moving target**: the "WAAPI can't animate SVG attributes, only CSS properties" and "`d` property not Baseline" facts were current as of the sources checked (2026); if this changes (browsers converging on Houdini/CSS Typed OM animating arbitrary attributes), the recommended rAF-based geometry tweening becomes a legacy-compat layer rather than a hard requirement — worth re-checking caniuse/Baseline status before finalizing, since MDN/caniuse.com itself were blocked by the sandbox's egress proxy during this research and could not be fetched directly (relied on WebSearch snippets referencing them, not the primitive tables themselves).
- **Numbers are for "primary technology," not "impossible with the alternative"**: canvas-based libraries do support animation and accessibility with enough engineering (Chart.js, Cytoscape do both) — the claim here is about incremental engineering cost inside a <50KB budget for a library with rich per-node interactivity and accessible expand/collapse, not that Canvas/WebGL animation or a11y is unachievable in general.
- **Egress restrictions limited primary-source verification**: bundlephobia.com, unpkg.com, developer.mozilla.org, jointjs.com, svggenie.com, and medium.com were all blocked by the sandbox's network egress policy; bundle-size numbers above were instead independently verified by downloading the actual npm tarballs from registry.npmjs.org (which was reachable) and gzipping the real `dist/*.min.js` files directly — arguably more rigorous than trusting a bundlephobia snapshot, but caniuse/MDN browser-compat-matrix claims rely on WebSearch result snippets rather than the primitive tables themselves and should be spot-checked before being treated as exact version numbers.
- **DOM-memory claim is qualitative, not measured**: I did not find (and the research budget didn't allow deriving) a solid, current per-DOM-node byte-memory benchmark to cite; the "our scale is well within normal web-app DOM sizes" claim is reasoned from general web-dev consensus (apps commonly run 10K+ DOM nodes) rather than a specific citation, and should be treated as directionally reliable rather than a hard number.
