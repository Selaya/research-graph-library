# Use-case pass: Systems, control and simulation modeling
> Part of the [feature-gap research corpus](../README.md) · 2026-09-05 · opus agent adopting the perspective of a systems / control / simulation modeler (state machines, Petri nets, queueing networks, supply chains, digital twins, discrete-event simulation replays).

**Coverage tally:** 9 use-cases: 5 good, 4 partial, 0 poor.

## The agent's stance

Systems / control / simulation modeler — state machines and statecharts, Petri nets, queueing networks, discrete-event simulation (DES), supply chains, and digital twins. My unit of interest is not "a graph" but a *marking that moves over time*: tokens/entities occupying places, transitions firing, queues filling, a clock advancing, and the ability to replay a run, stop at t=…, and explain to a colleague why the system jammed there. This library is unusually well-aimed at that: it has tokens as first-class citizens, two time models (compiled schedule vs. append-only live log with a frontier/view two-clock), first-class cycles and back edges, join policies (all/any/quorum) that are literally Petri-net-style synchronization, occupancy badges, seek/step/scrub that restores state instead of re-firing, and a narration/recording toolchain that turns any of it into an embeddable page or an mp4. What it lacks is the *stochastic and capacity* half of the modeling vocabulary (XOR/probabilistic routing, server capacity, queue/blocking semantics, token classes), a time-axis view, and any importer for the file formats this field already uses (PNML, SCXML, XES, OTLP).

## 1. Discrete-event simulation trace replay viewer

- **Coverage today:** `partial` · **Demand:** medium · **Effort:** medium
- **What the user is doing:** A modeler runs a DES model (SimPy, Salabim, AnyLogic, Arena, JaamSim) and gets a CSV/JSONL event log out. They want to watch the run back — entities entering, servers busy, the queue that grows at minute 340 — instead of squinting at output statistics, and they want to scrub back to the moment the jam started.
- **Example scenario:** A hospital ED model: 12 hours of simulated arrivals, triage, 3 exam rooms, imaging, discharge. The modeller exports 40k events, feeds them through run.start/finish/spawn with {at} timestamps, and scrubs to t=6h20m where the imaging queue hit 14 and the triage AND-join stalled.
- **Required features:** Mode B live/log replay with timestamped events; seek/scrub that restores state rather than replaying side effects; occupancy badges (multiple entities at one node); join policies for synchronization points; transport bar with speed control; performance on tens of thousands of events
- **Missing pieces:** Event-log importer that maps a columnar log (entity_id, activity, timestamp, resource) onto start/finish/spawn calls — today the consumer hand-writes the adapter; Token identity/class attributes (entity type, priority) so distinct entity classes are visually distinguishable, and a token's own path is followable; Simulated-clock display and calendar mapping — run.time() is ms only; no 'sim day 3, 14:20' readout or configurable time-scale label ('1 min = 1 hour'); Per-node queue-length series / max-occupancy watermark readout, not just an instantaneous occupancy badge; Storyboard + smv-record are Mode-A-only, so a log replay cannot be narrated or exported to video; Token pulses are not culling-aware, so large models past 150 elements show orphan pulses
- **Tools used for this today:** AnyLogic / Arena / Simio built-in animation, Simulation-package-specific viewers (Salabim's animation, JaamSim GUI), Custom d3 replays, Nothing at all — most SimPy users have only matplotlib output

## 2. Petri net / workflow-net token animation for teaching and model review

- **Coverage today:** `partial` · **Demand:** medium · **Effort:** large
- **What the user is doing:** Show a marking evolving: tokens sitting in places, a transition becoming enabled, firing, consuming and producing tokens. Used both in teaching (formal methods, business process courses) and in model review meetings where a modeller must convince stakeholders the net behaves as claimed.
- **Example scenario:** A producer/consumer net with a bounded buffer place: the lecturer scrubs to show that when the buffer place holds 3 tokens the producer transition is no longer enabled, then plays forward through a deadlock scenario, with a caption on each beat and the whole thing packed to a single HTML file for the course site.
- **Required features:** Tokens as first-class visual objects with counts per node; AND-join (all) and quorum ({count:k}) arrival semantics; Cycles/back edges as normal structure, never rejected; Step-by-step advance to the next event boundary; Captions + camera + storyboard to narrate each firing; Single-file HTML embed for a course page
- **Missing pieces:** Bipartite place/transition rendering — only rounded rects exist; no circle (place) vs. bar (transition) shapes, so the standard notation cannot be drawn; Arc weights as consumption/production multiplicities — edge.weight exists but is a meta-edge aggregation count, not a firing multiplicity honored by the token engine; Place capacity / enabling predicate: a transition should not fire when an output place is full (no inhibitor arcs, no capacity, no blocking); XOR / conflicting-transition semantics: fan-out is implicit AND, so a token at a place with two competing out-transitions spawns both instead of choosing one; Parallel edges between adjacent ranks render coincident — nets with two arcs between the same pair lose one visually; PNML importer
- **Tools used for this today:** CPN Tools, WoPeD, Snoopy / TAPAAL, GreatSPN, Hand-drawn slides and GIFs

## 3. Statechart / state machine execution debugger embedded in an app

- **Coverage today:** `good` · **Demand:** high · **Effort:** small
- **What the user is doing:** A developer or control engineer wants to see which state a machine is in right now, which transition just fired, and the history of transitions — embedded directly in the tool the machine lives in (an internal admin page, a device dashboard, an XState inspector-style panel), not in a separate desktop app.
- **Example scenario:** An order-fulfilment XState machine embedded in an internal ops console: the active state glows, hierarchical states are containers you can expand, the last 20 transitions are replayable with a scrubber, and an operator can rewind to see why an order reached 'payment_review'.
- **Required features:** Live event feed driving an active-state highlight; Compound/hierarchical states via containers with expand/collapse; Self-loops and back edges rendered cleanly; Time-travel scrub back through the transition history; Embed with one script tag, no build step, framework-free; Accessible/keyboard-navigable for internal tooling requirements
- **Missing pieces:** Parallel/multi-edge separation — two transitions between the same pair of states (the common case: 'submit' and 'cancel' both A→B) draw as one coincident line with one label winning; Orthogonal (AND) regions: containers hold children but there is no concurrent-region semantics where two sub-states are active simultaneously and roll up as one state; Guard/trigger labels as structured edge metadata with a distinct visual channel (event / [guard] / action) rather than one free-text label; Ports — self-transitions and multiple transitions to the same target all attach at the same node anchor; SCXML / XState machine-definition importer; Mode B 'failed' is sticky and only start() clears it, which does not map onto a state machine's error-state exit semantics
- **Tools used for this today:** Stately/XState visualizer and inspector, Mermaid stateDiagram (static), Graphviz dot renders, yEd / draw.io hand-drawn diagrams

## 4. Bottleneck story for a queueing / capacity model, as an executive-facing video

- **Coverage today:** `good` · **Demand:** high · **Effort:** medium
- **What the user is doing:** An operations analyst has modelled a service network and knows where the bottleneck is. The deliverable is not a chart, it is a two-minute narrated animation that a VP will actually watch: tokens pile up at one station, camera pushes in, caption names the number, then the 'after' configuration plays and the pile does not form.
- **Example scenario:** A claims-processing network: 'today' shows a manual-review station accumulating tokens while downstream stations idle; the storyboard condenses three manual steps into one automated node, replays, and the total-duration bar drops from 6 days to 9 hours, all recorded to mp4 with a fitted voice-over.
- **Required features:** Compiled simulate mode with declared durations; Condense/split choreography for the before/after configuration change; Camera moves, spotlight/emphasis, captions on a declared timeline; Cue sheet + voice-over fitting; Deterministic frame-by-frame mp4 recording; Occupancy visualization showing accumulation
- **Missing pieces:** Service capacity / concurrency per node (c servers) and a queue that visibly accumulates — occupancy is a badge count, there is no queue-vs-in-service distinction and no capacity-driven waiting; Utilization / throughput metric overlays that derive from the run (per-node busy %, per-edge entities-per-hour) instead of static duration chips; Stochastic durations (distribution grammar, e.g. 'exp(30m)' or 'tri(1h,2h,4h)') and multi-replication playback; today duration is a single deterministic scalar; Side-by-side or ghost-overlay comparison of two runs (baseline vs. scenario) in one frame; No Gantt/time-axis mode, so 'where did the time go' has to be told through motion alone
- **Tools used for this today:** AnyLogic screen recordings, Simul8 / ProModel animation, PowerPoint build animations over a static diagram, After Effects over a Figma diagram

## 5. Digital-twin status panel for a physical line or plant, embedded in a control dashboard

- **Coverage today:** `good` · **Demand:** high · **Effort:** medium
- **What the user is doing:** A live view of a real production line / conveyor / packaging system: each station shows running, blocked, starved, or faulted; WIP moves between stations as it actually moves; an operator can rewind ten minutes to see what preceded the stop.
- **Example scenario:** A bottling line panel in Grafana/an internal HMI: MQTT station events feed run.start/finish/fail; the capper faults at 14:07, the filler starves, and the shift lead scrubs back through the frontier/view two-clock to the first anomaly before the fault.
- **Required features:** Live append-only event log with a real-time frontier and a detachable view clock; fail() with a reason as a terminal, sticky status; Never-throw ingestion (unknown ids warn and self-heal) for messy real feeds; Custom status vocabulary via CSS with no specificity fight; Small bundle, embeddable in an existing dashboard, no framework; Long-running memoized replay so an idle panel is cheap
- **Missing pieces:** Log windowing/compaction: the log is append-only and run.log() copies it whole, so a panel running for days grows without bound and has no retention or snapshot-and-truncate API; Blocked vs. starved as first-class statuses distinct from failed — today both are just 'not running' or an ad-hoc data-status; Live per-edge rate/throughput labels updating from the event stream (units/min on the link) — edge labels are static free text; Alarm/threshold binding (e.g. emphasize a node when occupancy exceeds k) without the consumer writing a polling loop over run.state(); Tooltip system for hover-inspecting a station's current metrics — only a CSS hover stroke exists; Reconnect gap semantics: reset({log}) re-seeds, but there is no notion of 'data was missing between t1 and t2' rendered as an uncertainty band
- **Tools used for this today:** Ignition / Wonderware HMI screens, Grafana node-graph and Canvas panels, PlantUML/static SVG with hand-wired JS, Custom d3 or Konva dashboards

## 6. Supply-chain / logistics flow narration for S&OP and risk reviews

- **Coverage today:** `partial` · **Demand:** medium · **Effort:** medium
- **What the user is doing:** Explain how material actually flows across suppliers, plants, DCs and customers, where the lead time sits, and what a disruption does — as an interactive page a planning team clicks through, or a recorded briefing.
- **Example scenario:** A single-source component review: tokens flow supplier→port→plant→DC, the storyboard fails the port node with reason 'customs hold', downstream branches stop, the camera frames the alternate lane being added live, and the whole thing packs into one HTML file mailed to the risk committee.
- **Required features:** Declared lead times in human units (d/h/m) with sum rollups; Containers for region/plant grouping with expand/collapse; Declared failure with a reason to model a disruption; Structural mutation mid-story (add the alternate lane) with automatic animation; Captions and camera for a briefing narrative; Self-contained HTML packaging
- **Missing pieces:** Probabilistic / share-based routing: fan-out is implicit AND, so 'this supplier serves 70% of volume' cannot be expressed; edge.weight is not honored by the token engine as a split ratio; Quantity-carrying tokens (units, cost, mass) with conservation across splits and merges — tokens are unit-count only; Geographic or fixed-position layout: layered Sugiyama only, so a lane map with real relative geography is impossible; Inventory/buffer nodes with a level that draws down and replenishes (a stock, not a step); Multi-echelon rollup metrics (total lead time, cost, service level) beyond the pipeline preset's duration bar; Scenario diffing: two supply configurations side by side with a shared clock
- **Tools used for this today:** Kinaxis / o9 / Blue Yonder network views, Supply-chain-guru style network optimizers, PowerPoint maps with animated arrows, Tableau/Sankey network charts

## 7. Distributed-system incident replay from real traces

- **Coverage today:** `partial` · **Demand:** high · **Effort:** large
- **What the user is doing:** After an outage, an SRE wants to replay the request flow through services during the incident window — which hop stalled, where retries piled up, where the fan-in never completed — and attach that replay to the postmortem doc so readers see the failure instead of reading about it.
- **Example scenario:** A checkout outage: OTLP spans for 12 minutes are folded into per-service nodes; the retry edge to the payment service ticks its iteration badge to 5/5, the AND-join at order-confirm never fires, and the postmortem page embeds the scrubbable replay with captions at each contributing beat.
- **Required features:** Live log replay from real timestamps; Bounded retry loops with iteration badges; Join semantics that show an unfired synchronization point (arrived/needed pips); Drop/ghost events for late arrivals; fail() with a reason string; Embeddable, self-contained page for the postmortem
- **Missing pieces:** OTLP / Jaeger / Zipkin trace importer, including span→node folding and per-service aggregation; Aggregation across many concurrent traces (thousands of requests) into rates and percentiles rather than one token per request — no sampling or binning layer exists; Latency-proportional visual encoding (edge length or a time axis); a slow hop looks exactly like a fast one; No Gantt/waterfall mode, which is the canonical trace view engineers expect alongside the topology; Storyboard/recording refuse Mode B, so an incident replay cannot be narrated or exported as the postmortem's video; Per-edge error-rate / latency labels updating from the event stream
- **Tools used for this today:** Jaeger / Tempo / Honeycomb trace waterfalls, Datadog service map, Lightstep / Grafana service graphs, Static architecture diagrams pasted into the postmortem

## 8. Control-logic and operating-procedure training material (interlocks, mode transitions, SOPs)

- **Coverage today:** `good` · **Demand:** medium · **Effort:** small
- **What the user is doing:** Turn a control narrative or standard operating procedure into a stepped, narrated animation used for operator training and certification: what happens when you press this, which interlocks must be satisfied before the transition is permitted, what the wrong order looks like.
- **Example scenario:** A reactor startup sequence: the storyboard steps through purge → inert → charge → heat, showing the quorum interlock (3 of 4 permissives satisfied) as arrival pips filling, then replays an incorrect sequence where the interlock never satisfies and the sequence halts with a 'failed' reason.
- **Required features:** Quorum join ({count:k}) rendered as filled/unfilled slot pips; Step/wait-driven storyboard with per-step pacing; Captions with a cue sheet exported as SRT for subtitled training video; Deterministic mp4 recording for an LMS; Reduced-motion and a11y compliance for corporate training requirements; Keyboard navigation and a linearized table fallback
- **Missing pieces:** Guard/condition expressions on edges evaluated against a small state context — the engine has no notion of a boolean permissive, only arrival counts; Learner interactivity: no click-a-node-to-choose branch, no quiz/decision-point hook; interaction is pan/zoom/toggle only, and there is no selection API; No stated WCAG conformance level or audit, which corporate LMS procurement usually asks for explicitly; SCORM/xAPI or LMS packaging beyond a raw HTML file; Timed hold on a node awaiting operator acknowledgement (a 'pause until input' storyboard op)
- **Tools used for this today:** Articulate Storyline / Captivate, Vendor-specific simulator training modules, Screen recordings of the HMI, Static P&ID plus a written narrative

## 9. Model-behaviour regression harness: a visual diff of two simulation runs in CI

- **Coverage today:** `good` · **Demand:** low · **Effort:** medium
- **What the user is doing:** A modeller changes a routing rule or a service-time parameter and wants proof of what changed in behaviour, not just a table of KPIs. CI renders the run deterministically and attaches frames/video to the PR so a reviewer sees the divergence.
- **Example scenario:** A warehouse picking model: a PR changes the zone assignment rule; CI runs smv-record on both the baseline and the candidate storyboards, and the reviewer sees that in the candidate, tokens start backing up at the packing join around t=4h.
- **Required features:** Byte-identical deterministic frame rendering (manual ticker, forced full motion, pinned font); Headless Chromium + PNG-sequence output that needs no ffmpeg; Golden-file style stability guarantees and zero relayout drift on unchanged graphs; CLI-drivable, no GUI; Chapter re-render (--from/--to) frame-identical to the full take
- **Missing pieces:** Run-vs-run diff primitive: no API to overlay or difference two RunStates (e.g. colour nodes by 'occupancy delta vs. baseline'); Headless state extraction without frames — no Node-side way to compute sim().stateAt(t) for assertions; the whole engine assumes a browser for anything past compile; Per-frame numeric export (a CSV of node status/occupancy per frame) alongside the PNGs, for machine-checkable regressions; A perceptual/structural frame-diff step in the toolchain (today the guarantee is byte-identity on one machine, and --font is the only cross-machine lever)
- **Tools used for this today:** KPI tables in CI logs, Percy / Chromatic on static screenshots, Nothing — most model changes are reviewed by reading the diff

## Cross-cutting needs from this perspective

- Routing semantics beyond implicit AND fan-out: XOR/exclusive choice, probabilistic or share-weighted splits, and guard predicates. Every modeling formalism in this domain (Petri nets with conflict, statecharts with guards, DES routing rules, supply-chain volume splits) needs a token to *choose* an out-edge; today 2+ out-edges always spawn 2+ tokens. This single gap is named in 5 of the use cases and is the largest semantic hole.
- Capacity and queueing semantics: per-node server count / buffer capacity, a visible waiting-vs-in-service distinction, and blocking/starving as first-class statuses. Occupancy today is a badge integer with no capacity, so the central phenomenon of the field — accumulation caused by a constraint — cannot be modeled, only faked with durations.
- Token identity and payload: token classes/types (colour, priority, entity id) and quantity-carrying tokens with conservation across splits/joins. Needed for DES entity types, coloured Petri nets, supply-chain units, and per-request trace following. Tokens are currently anonymous and unit-valued.
- A time axis. The absence of a Gantt/temporal layout mode (explicitly skipped in the plan) is felt by DES replay, trace analysis, bottleneck stories, and control sequences alike — practitioners expect a topology view AND a time view sharing one scrubber. Related: no simulated-clock/calendar display or configurable time-scale label (run.time() is bare ms).
- Live-mode parity for the narration and recording toolchain. Storyboards, smv-record and smv-fit are Mode A only, so every use case whose data is a real log (DES trace replay, digital twin, incident postmortem) can be watched interactively but never narrated, chaptered, or exported to video — which is exactly the deliverable those audiences want.
- Metric overlays derived from the run: per-edge throughput/rate labels and per-node utilization/queue-length/max-watermark readouts that update from live or compiled events. Edge labels are static free text and the pipeline preset only shows declared durations, so no run-derived number can appear on the drawing without a custom preset.
- Importers for the formats this field already exports: PNML, SCXML/XState JSON, columnar/XES event logs, and OTLP/Jaeger traces. The spec shape is fine, but every use case currently begins with the user hand-writing an adapter, which is the main adoption tax. The solver seam shows the project is comfortable with pluggable entry points; there is no equivalent seam on the data-in side.
- Rendering vocabulary for formal notations: shapes beyond rounded rects (circles for places, bars for transitions, diamonds for decisions), separated parallel edges between adjacent ranks (currently coincident — breaks state machines and multi-arc nets), and node ports so multiple transitions between the same pair are distinguishable.
- Scale and inspection for real models: culling-aware token pulses (documented open issue) plus a tooltip/hover-inspect surface and log windowing/compaction for panels that run for days. Long-lived twins and 40k-event replays hit all three.
- Comparison as a first-class operation: baseline-vs-scenario overlay or side-by-side with a shared clock, and a RunState diff primitive. Modelers almost never look at one run — they look at two — and nothing in the API today expresses that.
