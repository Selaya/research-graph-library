# Use-case pass: Business process and operations analysis
> Part of the [feature-gap research corpus](../README.md) · 2026-09-05 · opus agent adopting the perspective of a business-process / operations analyst (approval workflows, order fulfillment, incident response runbooks, automation ROI storytelling: manual steps replaced by automated ones).

**Coverage tally:** 9 use-cases: 3 good, 6 partial, 0 poor.

## The agent's stance

Business-process / operations analyst: approval workflows, order fulfillment, incident runbooks, and automation ROI storytelling. I evaluate the library as a tool for (a) explaining a process to people who must fund, approve, or execute it, and (b) watching a real process run. Notes on competing tools are from memory, not verified in this pass; no version numbers claimed.

## 1. Automation ROI before/after: manual steps condensing into one automated step

- **Coverage today:** `good` · **Demand:** high · **Effort:** small
- **What the user is doing:** An ops analyst builds the business case for automating part of a process. The visual argument is literally the library's condense() choreography: five manual handoff boxes highlight, converge, and become one 'RPA bot' node, while a duration odometer rolls 2h 40m -> 8s and a delta badge shows the saving. This is the single strongest fit — the pipeline preset already ships manual/auto glyphs, sum/max duration rollups, an odometer and a total-duration bar.
- **Example scenario:** Supplier invoice approval: 'Receive PDF -> Manual key-in -> AP clerk match -> Cost-centre owner email approval -> Manual GL post' condenses into 'OCR + 3-way match bot', with the storyboard narrating the before run at 1x, then the after run, and a caption stating the annual FTE-hour saving. Recorded to mp4 and dropped into the CFO's steering-committee deck.
- **Required features:** condense() with staged highlight->converge->reveal; data.duration grammar + durationAgg rollups; pipeline preset odometer + delta badge + manual/auto mode badges; storyboard with captions and per-step dur pacing; smv-record to mp4 / smv-pack single-file HTML
- **Missing pieces:** Cost/currency as a first-class aggregate alongside duration (preset computes seconds only; FTE-hours -> money must be hand-computed and pushed as caption text); Annualized/volume multiplier on the rollup (duration x cases-per-month) so the badge can read '3,400 h/yr' rather than per-case seconds; A built-in 'before vs after' twin-graph or split-pane comparison mode — today you must script two sequential runs in one storyboard or mount two instances and sync them yourself
- **Tools used for this today:** PowerPoint with hand-drawn arrows, Visio / Lucidchart, Miro board walkthroughs, Camtasia/Loom screen recordings of a Celonis or UiPath screen, Bespoke After Effects animations from a design team

## 2. Live incident-response runbook cockpit

- **Coverage today:** `partial` · **Demand:** high · **Effort:** large
- **What the user is doing:** During a major incident, the bridge call needs one screen showing which runbook step is running, which branch failed, how long the current step has been burning, and what is blocked waiting on a join. Mode B's append-only event log plus the frontier/view two-clock model is a near-exact fit: an on-call automation posts start/finish/fail as steps execute, and a latecomer can scrub back to see what already happened without disturbing the live view.
- **Example scenario:** Sev-1 payment outage: the runbook graph has 'Declare incident -> [page DBA | page network | comms draft] -> Diagnose -> (loop) Mitigate -> Verify -> All-clear'. PagerDuty/Slack webhooks drive run.start()/finish()/fail(); the 'Verify' loop edge ticks iteration 2/5 while the incident commander scrubs back four minutes to see exactly when the failover was declared failed.
- **Required features:** Mode B live event log with {at} timestamps; frontier vs view clock + follow(); fail() as a sticky terminal status with reason string; run.log()/reset() for reconnect after a page refresh; join pips and loop iteration badges; embed-anywhere single script tag for a status wall
- **Missing pieces:** Per-node elapsed-time / SLA countdown chip driven by the live clock (a 'this step has been running 14m, breaches at 15m' badge) — the preset's duration chips are static declared values, not live elapsed; Threshold-driven automatic emphasis (auto data-emph=warn when a node exceeds its declared duration) — highlight is currently a manual director op only; Storyboards cannot drive Mode B at all, so no scripted camera/caption follow-the-action on a live board; camera must be hand-driven from event handlers; No tooltip/detail-on-hover, so runbook step detail (owner, ticket link, last log line) has no place to live; Token pulses are not culling-aware, so a large runbook wall zoomed in shows orphan pulses
- **Tools used for this today:** Grafana / Datadog dashboards (tables and timeseries, not topology), PagerDuty and incident.io incident timelines, ServiceNow / Jira Service Management workflow views, A Confluence runbook page with static Mermaid diagrams and a manual checklist

## 3. Approval-workflow bottleneck explainer for a process review

- **Coverage today:** `partial` · **Demand:** high · **Effort:** medium
- **What the user is doing:** Show where cases actually queue in a multi-approver workflow, so a steering group can agree which gate to remove. The distinctive value is that queueing is shown as tokens piling on a node with an occupancy badge and a slow branch visibly crawling, rather than as a bar chart of cycle times.
- **Example scenario:** Purchase requisition >EUR 25k needs manager + finance + legal (join: 'all'), while <EUR 25k needs any one (join: 'any'). Playing both variants shows the >25k path stalling three days on 'Legal review' with a 12-token occupancy badge while the <25k path clears in an hour; the caption proposes raising the threshold.
- **Required features:** join policy 'all'|'any'|{count:k} with arrival pips and drop events; occupancy badges; per-branch run.speed() to show a slow lane; declared durations from real mean cycle times; storyboard + captions + camera for a walkthrough
- **Missing pieces:** Queue-depth / WIP as a data-driven node property with its own badge (occupancy today is token count from the run, not an imported 'currently 340 cases waiting' figure); Duration distributions (p50/p95) rather than a single scalar — an approval gate's story is the tail, and only one number per node is expressible; No Gantt/temporal layout mode (x = time), which is the natural second view for a bottleneck conversation and is explicitly not built; Per-edge case-volume / split-percentage label fed from data (edge weight exists but is defined as meta-edge aggregation count, not a routing-share label)
- **Tools used for this today:** Celonis, Disco, Apromore process mining, Excel cycle-time pivots, BPMN modelers (bpmn-js, Camunda Modeler, Signavio) which draw the model but do not animate real volumes

## 4. Order-fulfillment exception and rework-loop analysis

- **Coverage today:** `partial` · **Demand:** medium · **Effort:** large
- **What the user is doing:** Make rework visible: what fraction of orders bounce back from QC to pick-pack, how many iterations before they clear, and where orders drop out entirely. Bounded retry loops with iteration badges and declared-failure nodes are unusually well matched to this — most diagramming tools cannot show a loop executing a bounded number of times.
- **Example scenario:** D2C order flow: 'Order -> Payment auth -> Pick -> Pack -> QC -> Ship'. QC->Pack is loop:true, maxIterations 3; 'Address validation' carries data.fail:'undeliverable address'. The animation shows one token looping twice through repack and another failing out at address validation, with the caption quoting 4.1% rework and 0.8% loss.
- **Required features:** loop:true edges + maxIterations + 'loop' events with iteration badges; data.fail with a reason string carried to the fail event; implicit fan-out and drop events for abandoned tokens; traversed-edge progressive width for showing the walked path
- **Missing pieces:** Probabilistic routing on edges (edge.data.probability so N tokens split 96/4 across branches) — fan-out is currently all-branches-always, so proportions must be faked with hand-placed tokens; Multi-token cohort runs ('release 100 cases and watch them distribute') — Mode A compiles a single logical run, not a population; Per-edge throughput/percentage label that updates from live or replayed events; Rework-cost rollup (iterations x step duration) surfaced as an aggregate figure
- **Tools used for this today:** Process mining tools (Celonis variant explorer), Tableau/Power BI Sankey diagrams of order states, Static swimlane diagrams in Visio plus a separate exception-rate table

## 5. Process-mining replay: a month of real ERP events compressed into ninety seconds

- **Coverage today:** `partial` · **Demand:** medium · **Effort:** large
- **What the user is doing:** Take a real event log (case id, activity, timestamp) exported from an ERP or ticketing system and replay it as visible tokens moving through the discovered process, time-compressed. Mode B is architecturally right for this — append-only log, seekable, O(n log n) replay measured at 40k events in ~73ms — and this is a use-case no generic graph library serves.
- **Example scenario:** Export 30 days of ServiceNow change-request state transitions, map activities to node ids, feed the log through run.reset({log, mode:'live'}), and play at 20,000x so a whole month of CAB approvals streams past in a demo at the quarterly ops review.
- **Required features:** Mode B append-only log with {at} timestamps; run.reset({log}) / options() round-trip for snapshot restore; seek/time-travel over the frontier; min-heap replay performance; viewport culling for large discovered process graphs
- **Missing pieces:** A CSV/XES event-log importer that maps (case, activity, timestamp) columns to the run log — today the caller writes the mapping by hand, and there are no data-source adapters at all; Process discovery: deriving nodes/edges from the log rather than requiring a pre-authored spec; Global time-compression / speed factor on Mode B beyond catch-up scaling, plus a readable wall-clock date overlay ('Tue 14 Mar, 09:20') tied to the view clock; Aggregate heat: node/edge colour or width driven by cumulative event counts during replay, not just current occupancy; No per-branch speed() in Mode B (documented no-op)
- **Tools used for this today:** Celonis, Disco, Apromore, PM4Py + custom matplotlib animations, Home-grown d3 replays, Sankey/state-transition dashboards in Power BI

## 6. SOP and onboarding training clips generated from the process spec

- **Coverage today:** `good` · **Demand:** medium · **Effort:** small
- **What the user is doing:** Produce short narrated videos of 'how this process works' that stay correct when the process changes, because the video is generated from the same JSON spec that documents the process. smv-record plus smv-fit (stretching wait steps to match a recorded voice-over's landing marks) and --cues SRT output is a complete production pipeline that most ops teams currently do by hand in Camtasia.
- **Example scenario:** Warehouse returns SOP: a 90-second clip per role. The analyst records a voice-over, runs smv-fit against marks.json so each caption lands on the narration, then smv-record --from/--to emits one MP4 per chapter plus an .srt for the LMS, and regenerates all of them when the returns policy adds a step next quarter.
- **Required features:** storyboard JSON as the portable script artifact; captions + g.cues() cue sheet; smv-fit voice-over fitting, smv-record deterministic frames, --cues srt/txt; --from/--to chapter re-render, --font pinning for stable cross-machine layout; motion:'full' + manual ticker for byte-identical output
- **Missing pieces:** No audio muxing — smv-record produces silent video, so the voice-over must be married in ffmpeg or an editor as a separate step; No branding/title-card or lower-third layer (logo, role name, step numbering) beyond the single caption overlay; run.play steps cannot be priced by smv-fit at all, so any clip whose narration must track a token run has to be paced with explicit wait steps; Localization: captions are literal strings in the storyboard, with no locale map, so N languages means N storyboard copies
- **Tools used for this today:** Camtasia / Loom / Descript screen recordings, Articulate Storyline and Rise for LMS content, Scribe and Tango for click-through SOP capture, PowerPoint Morph exported to video

## 7. Embedded live process status widget in an internal ops portal or wiki

- **Coverage today:** `good` · **Demand:** high · **Effort:** small
- **What the user is doing:** Drop the current state of a named process onto a Confluence page, a SharePoint ops dashboard, or an emailed single-file HTML attachment, with no build step and no framework. smv-pack producing one self-contained file that opens over file:// is a real distribution advantage in locked-down enterprise IT, where npm builds and CDN allowlists are the blocker.
- **Example scenario:** Month-end close: a single HTML file, regenerated hourly by a scheduled job from the close checklist system and posted to the finance wiki, showing which of 40 close tasks are done, active, failed, or blocked on a join, colour-coded by the theme the wiki already uses.
- **Required features:** single <script> IIFE from CDN or smv-pack single-file HTML; CSS custom-property theming to match host styling; data-status driven colouring with no JS; containers with collapse for the 40-task list; a11y tree + table fallback for portal accessibility rules; exportSVG for a static thumbnail
- **Missing pieces:** No tooltip system and no click handler on ordinary (non-container) nodes, so 'click a task to open its ticket' requires writing a custom preset against g.renderer; No polling/refresh helper — the caller must re-fetch and diff into addNode/update themselves (the animated diff then handles the visuals); exportPNG and exportSVG are excluded from the IIFE bundle, so a no-build wiki embed cannot offer 'download this picture'; No legend/key component for status colours, which reviewers in a portal context always ask for
- **Tools used for this today:** Confluence + Mermaid or draw.io macros (static), SharePoint status tables, Power BI embedded tiles, Monday.com / Smartsheet board views

## 8. As-is vs to-be process design workshop

- **Coverage today:** `partial` · **Demand:** medium · **Effort:** large
- **What the user is doing:** Run a redesign workshop where the current process is played, then mutated live in front of stakeholders — remove an approval gate, split a lumped 'Fulfilment' box into its real four steps, merge two teams' duplicate checks — with each change animated so the room can see what moved. Diff-based auto-animation plus split()/condense() and anchored viewport correction make live editing legible instead of jarring.
- **Example scenario:** Order-to-cash workshop: the analyst runs the as-is at 3x, then splits 'Credit check' into 'Automated score / Manual review / Escalation', removes the redundant sales-ops approval, and replays — 6.5 days becomes 2.1 days on the total-duration bar while everyone watches the same screen.
- **Required features:** split()/condense() with slot-preserving reseat; diff-based enter/update/exit animation; anchored viewport (focal node holds still); batch() for multi-op single-transition edits; re-run after mutation with recomputed durations
- **Missing pieces:** No editing UI whatsoever — every mutation is a JS call, so a workshop needs a facilitator typing in a console or a hand-built control panel; No node dragging, so a stakeholder cannot say 'put that step over there' and have it stick; No swimlane/role-band layout (rows by department), which is the default mental model for every process workshop and is not expressible with containers alone; No annotation or comment layer for capturing workshop objections against a step; batch() is non-transactional, so a mistyped bulk edit cannot be rolled back — and there is no undo/redo
- **Tools used for this today:** Miro / Mural with sticky notes, Lucidchart and Visio live editing, Camunda Modeler and Signavio collaborative BPMN editing, Whiteboard plus a photo

## 9. Compliance walkthrough and control-evidence pack

- **Coverage today:** `partial` · **Demand:** low · **Effort:** medium
- **What the user is doing:** Auditors ask 'walk me through how a payment gets approved and show me where the segregation-of-duties control sits'. The storyboard produces a repeatable, dated walkthrough: each control point framed by the camera, spotlit with dim:true, captioned with the control id, and exported as a still per beat plus a cue sheet listing every control in order with timestamps.
- **Example scenario:** SOX walkthrough of vendor payments: an eight-beat storyboard spotlights the segregation-of-duties join (requester cannot approve), the dual-authorisation quorum join {count:2}, and the exception path; exportSVG({viewport:true}) writes one PNG-ready still per control into the audit file, and g.cues() becomes the walkthrough index.
- **Required features:** storyboard camera + highlight(dim) + caption ops; join {count:k} to depict dual authorisation; exportSVG({viewport:true}) matching the framed shot exactly; g.cues() as an ordered index with ms offsets; deterministic recording for a re-runnable evidence artifact
- **Missing pieces:** exportSVG is ESM-only and per-call, with no 'export every storyboard beat as a numbered still' batch helper (smv-record --png-dir is close but renders every frame, not one per label); No PDF output, which is the format audit files actually want; No provenance/watermark stamp (spec hash, generated-at date, source system) baked into an export, which is what makes a still admissible as evidence; No structured warning objects — diagnostics are console.warn strings, so a generation job cannot assert 'this pack built clean'
- **Tools used for this today:** Visio walkthrough diagrams pasted into Word, AuditBoard / Workiva narrative modules, Screenshots plus a Word narrative, Confluence pages with static diagrams

## Cross-cutting needs from this perspective

- Data-source adapters for real operational systems: a CSV/XES event-log importer mapping (case id, activity, timestamp) into a Mode B log, and ideally BPMN/DOT import into the {nodes,edges} spec. Five of the nine use-cases start from data that already exists in an ERP, ITSM, or mining tool, and today every one of them requires hand-written mapping glue.
- Business quantities as first-class node/edge data with rendered badges: cost per step, case volume, queue depth/WIP, routing share percentage, SLA threshold. Duration is the only quantity the library models, but every ops conversation is duration x volume x cost, and the preset can only roll up seconds.
- Data-driven emphasis rules (a declarative 'when node exceeds its SLA, set emph=warn') rather than emphasis being exclusively a manual director op — needed by the live cockpit, the bottleneck explainer, and the status widget alike.
- Live-mode narration parity: storyboards, smv-record, and smv-fit are Mode A only by design, yet the incident cockpit, the ERP replay, and the status widget are all Mode B. Even a subset (camera + caption ops bound to live events, with recording still refused) would unblock three use-cases.
- Detail-on-demand on a node: a tooltip or a click/hover event on ordinary nodes carrying arbitrary data payload, so a step can link to its ticket, owner, or last log line. Absent everywhere, and every embedded/portal use-case hits it immediately.
- Swimlane / role-band layout (rows or columns by department or system), the default mental model for process work. Containers give nesting but not orthogonal role bands, and the layered engine has no lane concept.
- Comparison rendering: a first-class as-is vs to-be twin view or overlay with a shared clock, since the ROI story, the workshop, and the bottleneck review all fundamentally argue 'this version vs that version'.
- Population/cohort simulation rather than single-token runs: probabilistic edge routing, N cases released, resource capacity limits. This is the gap between 'an illustration of the process' and 'an analysis of the process', and it is where process-mining and discrete-event tools currently win.
- Aggregate-figure output alongside the animation: a machine-readable summary (total duration before/after, steps automated, FTE-hours saved, failure rate) that a slide, a wiki page, or a business case can cite — today the numbers only exist as pixels inside the preset's badges.
