# Use-case pass: Education and technical writing
> Part of the [feature-gap research corpus](../README.md) · 2026-09-05 · opus agent adopting the perspective of an educator or technical writer producing explainers (algorithm walkthroughs, distributed-systems protocols, request lifecycles, animated documentation, conference talks, YouTube videos).

**Coverage tally:** 9 use-cases: 2 good, 7 partial, 0 poor.

## The agent's stance

Educator / technical writer producing explainers: algorithm walkthroughs, distributed-systems protocol animations, request-lifecycle and trace explainers, living documentation, conference talks and YouTube videos. What I care about: a diagram that moves through *time*, that I can narrate, that scrubs backwards when someone asks a question, that embeds in an MDX doc or renders to a frame-exact mp4 — and that I can author as data (JSON) rather than as keyframes. sparkle-motion-visualizer's distinctive assets for me are the token engine, the storyboard/director op array with a declared timeline, g.cues()/smv-fit/smv-record, and the one-script-tag embed. Its distinctive gaps for me are: no pointer/hover event surface on nodes, no importers from formats I already have, storyboards refusing Mode B (live) runs, one plain-text caption as the entire text layer, no temporal/Gantt layout or clock readout, and coincident parallel edges (fatal for peer-to-peer message passing).

## 1. Animated algorithm walkthrough embedded in a written tutorial

- **Coverage today:** `partial` · **Demand:** high · **Effort:** large
- **What the user is doing:** Teach a graph algorithm (BFS, Dijkstra, topological sort, union-find) by stepping a marker through the graph inside the article itself, with the reader scrubbing back and forth rather than watching a video. The author writes the trace as data, not as keyframes.
- **Example scenario:** A blog post on Dijkstra: the graph mounts under the paragraph that introduces it; each storyboard beat pops the min-distance node, relaxes its out-edges, updates each neighbor's distance label, and dims settled nodes. A caption per beat says why. The reader drags the scrubber back to beat 3 to re-see the relaxation that changed d(C).
- **Required features:** per-step tape of discrete beats with scrub-backward correctness; per-node value labels that mutate per beat (dist, visited, parent); edge emphasis for 'currently relaxing this edge'; spotlight/dim to separate frontier from settled; embed in a static docs page with no build step
- **Missing pieces:** Node label/badge mutation as a cheap non-relayout op — g.update() re-diffs and can reflow box size from measured text, so a per-beat distance readout jitters the layout; Auxiliary state panel bound to the storyboard step (queue/stack/priority-queue contents, distance table) — nothing in the library renders non-graph state; A 'value chip' or secondary-text slot on a node distinct from label, styleable, excluded from box measurement; Non-layered layout for algorithm graphs (grid/fixed-coordinate/force) — Sugiyama ranking is wrong for an undirected weighted graph where the author wants a specific spatial arrangement; Author-supplied fixed node positions (x/y passthrough into the solver) as an escape hatch; Edge weight *display* as a first-class numeric (weight is aggregation-count semantics today; teaching weights means abusing edge label strings)
- **Tools used for this today:** Manim, hand-rolled D3 + custom step arrays, Excalidraw/Figma frame-by-frame GIFs, Observable notebooks, VisuAlgo-style bespoke widgets, Motion Canvas

## 2. Distributed-systems protocol animation (Raft election, 2PC, gossip)

- **Coverage today:** `partial` · **Demand:** high · **Effort:** large
- **What the user is doing:** Show messages actually flying between peers as a protocol runs, with node role changes, timeouts, and induced failures — the thing static box diagrams cannot convey.
- **Example scenario:** A Raft leader-election explainer: five peers in a ring; the candidate's RequestVote tokens fly out to four peers, votes fly back, the node flips follower->candidate->leader with its label and color, then a partition drops two peers and the audience watches the term bump and a new election start.
- **Required features:** independent tokens in flight on edges, both directions; per-token identity and label (which RPC is this); node state-machine label/status swap mid-run; deliberate message drop / delay; peer topology layout (ring/radial), not a pipeline
- **Missing pieces:** Parallel/bidirectional edges between adjacent ranks render as coincident polylines — a request and its reply between two peers draw on top of each other, which is exactly the pair the explainer exists to show; Per-token labels, colors, and payload text (tokens are anonymous pulses today); A public 'drop this token' / 'delay this token' API — token drop exists only as a join-overflow side effect; Ring/radial/circular layout for peer sets; layered ranking forces a false hierarchy on symmetric peers; Node status vocabulary beyond pending/active/done/failed for protocol roles (follower/candidate/leader) without CSS-only workarounds; Simultaneity control: firing N tokens at the same instant with jitter/skew per branch (per-branch speed is Mode A only and coarse)
- **Tools used for this today:** Manim, After Effects / Keynote Magic Move, the Raft visualization (thesecretlivesofdata) and similar bespoke JS, Motion Canvas, hand-drawn sequence diagrams in Mermaid (static)

## 3. Request-lifecycle / trace explainer built from a real distributed trace

- **Coverage today:** `partial` · **Demand:** high · **Effort:** large
- **What the user is doing:** Take an actual OpenTelemetry/Jaeger trace of one request and turn it into a narrated animation: the request enters the gateway, fans out to three services, one is slow, one retries, the join waits.
- **Example scenario:** An engineer writes 'why is p99 checkout slow' for the team: the trace's spans become nodes with data.duration from real span durations, the fan-out to inventory/pricing/fraud is implicit, the fraud service retries twice (loop edge), and the AND-join at the response assembler visibly waits on the slowest branch. Camera zooms to the 400ms gap.
- **Required features:** durations driving playback timing; fan-out + AND-join semantics; retry loops with iteration count; camera + caption narration; import from an existing trace format
- **Missing pieces:** Trace importer (OTLP JSON / Jaeger / Zipkin -> GraphSpec with data.duration) — today the author hand-writes the spec; Temporal/Gantt layout mode (x = time) — the explicit non-goal; a trace's whole point is that spans overlap on a time axis, and layered ranking discards that; Wall-clock / elapsed-time readout tied to the run clock (there is a scrubber but no visible ms/timestamp); Per-edge latency labels that update from the run (edge label is static free text); Critical-path emphasis derived from the compiled schedule (the sim knows it; there is no API asking 'which chain determined total duration'); Overlap representation: two concurrent spans on one service are two nodes, not one node with occupancy over time
- **Tools used for this today:** Jaeger/Tempo/Honeycomb waterfall UIs (static, not narratable), screen-recorded walkthroughs of those UIs, hand-drawn sequence diagrams, Excalidraw + voiceover

## 4. Narrated conference-talk / YouTube segment rendered to frame-exact video

- **Coverage today:** `good` · **Demand:** high · **Effort:** medium
- **What the user is doing:** Author a 90-second animated system explanation as JSON, record voice-over, fit the animation's holds to the voice-over, and render an mp4 that is byte-identical on re-render so a late script fix means re-rendering one chapter, not re-recording the screen.
- **Example scenario:** A talk on an event-driven order pipeline: 12 storyboard beats, camera moves per beat, condense() showing three manual approval steps collapsing into one automated one, captions doubling as subtitles. g.cues() -> .srt for YouTube and .txt for chapter markers; smv-fit stretches waits to the recorded VO marks; --from/--to re-renders act 3 alone after a wording change.
- **Required features:** deterministic frame renderer; declared per-step timeline shared by scrubber, cues, and renderer; voice-over fitting; cue sheet -> SRT/chapters; camera/highlight/caption director ops
- **Missing pieces:** Audio muxing in smv-record — it emits silent video; joining the VO track is a manual ffmpeg step the CLI already has ffmpeg for; Text layer beyond one single-line caption: no title cards, no lower-thirds, no bulleted build-on lists, no two simultaneous text elements, no rich text/markdown in captions; Callout annotations anchored to a node or to world coordinates (arrow + label pointing at a specific edge) — props()/highlight can recolor but cannot point; Scene transitions between two different graphs (cut/dissolve from spec A to spec B); today a talk with two unrelated diagrams needs two recordings stitched externally; Aspect/safe-area presets for 9:16 and 1:1 social cuts (width/height exist, but nothing reserves caption-safe area or reflows the camera for a vertical frame); Reverse of smv-fit: emit the timing the *animation* wants so a narrator can record to it
- **Tools used for this today:** Manim, After Effects, Motion Canvas, Keynote/Figma + screen recording, Descript/ScreenFlow over a live browser tab, Rive

## 5. Living documentation generated from the repo's own config

- **Coverage today:** `partial` · **Demand:** medium · **Effort:** medium
- **What the user is doing:** The pipeline diagram in the docs is generated from the CI workflow / Airflow DAG / Step Functions definition that actually runs, so it cannot drift, and it animates a typical run instead of sitting still.
- **Example scenario:** A Docusaurus page on 'how our release pipeline works' imports the repo's .github/workflows/release.yml at build time, renders the job graph with needs: edges, marks the matrix fan-out, and animates a nominal run with each job's median duration from the last 30 runs pulled from the Actions API.
- **Required features:** build-time generation from an existing definition; embed into an MDX/React docs site; static first paint, animation on interaction; durations from real data
- **Missing pieces:** Importers/adapters for the formats authors already have: GitHub Actions YAML, Airflow DAG, Step Functions ASL, BPMN, Graphviz DOT, Mermaid flowchart; Node-side static render: exportSVG requires a mounted browser instance, so a docs build cannot emit an SVG at build time and hydrate it later — there is no headless/JSDOM-safe render path short of driving chromium; Official React/MDX wrapper component (mount/destroy lifecycle, spec-as-prop diffing, StrictMode double-mount safety) — the seam is imperative DOM only; URL/hash deep-linking to a storyboard label so a doc can link to 'the fan-out beat'; A documented 'progressive enhancement' recipe: static SVG in the HTML, upgraded to the live instance on hydration
- **Tools used for this today:** Mermaid in Markdown (static, ubiquitous), Graphviz/DOT in CI, Structurizr/C4, Diagrams.net exports checked into the repo, D2

## 6. Explorable-explanation widget the reader drives

- **Coverage today:** `partial` · **Demand:** high · **Effort:** medium
- **What the user is doing:** An interactive figure where the reader is the driver: hover a node to see its details, click to expand a subsystem, toggle 'what if this step fails', and watch the consequence propagate.
- **Example scenario:** An article on backpressure: the reader clicks the slow consumer to set its duration to 5s, and the queue node's occupancy badge climbs as tokens back up; hovering the queue shows a tooltip with current depth; a 'fail the writer' switch turns a branch red and shows the join never firing.
- **Required features:** pointer events on nodes/edges exposed to the page; tooltip/detail popover; reader-driven parameter changes re-driving the run; expand/collapse under reader control; state persisted across the interaction
- **Missing pieces:** No node/edge pointer event surface at all: g.on() carries structural events only, and the sole built-in pointer behavior is tap-to-toggle on containers — a consumer cannot get 'user clicked node X' without reaching past the public API; No hover/focus events, therefore no tooltip layer (the acknowledged limit) and no hover-linked prose highlighting ('this sentence and that node light together'); No selection state/API (no g.select(id), no data-selected) for a 'currently inspected' node; Recompile ergonomics for reader-changed durations: the path from 'reader edits a duration' to 'run re-compiles and resumes at the same clock position' is not a documented single call; No per-node live metric badge (queue depth, throughput, error count) that updates from run events — occupancy badges exist but are token-count only
- **Tools used for this today:** bespoke D3 + Svelte/React widgets, Observable, p5.js sketches, Idyll, Distill-style hand-built figures

## 7. Live-lecture / slide-deck driven presentation

- **Coverage today:** `partial` · **Demand:** medium · **Effort:** small
- **What the user is doing:** The diagram advances one beat per slide click during a talk, in sync with the presenter, with the ability to jump back to any earlier beat when someone asks a question mid-Q&A.
- **Example scenario:** A Reveal.js deck: slide 7 mounts the graph and holds at beat 0; each right-arrow advances one storyboard beat; slide 8 leaves and the instance resets. During Q&A the presenter types a chapter name and the storyboard seeks to that label instantly.
- **Required features:** step-forward/step-back on external input; seek to a named label; reset on slide re-entry; no autoplay drift while the presenter talks; second-screen presenter notes
- **Missing pieces:** Keybinding conflict: arrow keys are owned by the a11y focus navigation, so the obvious presenter binding collides with the accessibility layer and there is no documented arbitration or opt-out short of a11y:false (which disables keyboard nav wholly); No storyboard step-forward/step-back transport method on the handle equivalent to run.step() (there is seek(label) and a position, but stepping beats is not the same surface as stepping tokens); No slide-framework lifecycle helper (mount on slide enter, pause/reset on exit, destroy on deck teardown) for Reveal/Slidev/Deckset; No presenter view: cues exist as a sheet, but nothing renders speaker notes on a second screen aligned to the current beat; No 'hold here until I advance' step type — pacing is declared in ms, which is exactly wrong for a human speaker whose beat length varies per delivery
- **Tools used for this today:** Reveal.js fragments over static SVG, Slidev, Keynote builds, playing a pre-rendered video in the deck (loses interactivity)

## 8. Incident post-mortem replay from real logs

- **Coverage today:** `partial` · **Demand:** medium · **Effort:** medium
- **What the user is doing:** Replay a real outage as it happened — the actual event log, actual timestamps — and narrate what went wrong, scrubbing back to the moment the retry storm started.
- **Example scenario:** A post-mortem doc for a Friday outage: the team feeds 40k real events (service starts/finishes/failures) into Mode B, then narrates over it: 'at 14:07 the DB node fails; watch every retry loop light up simultaneously; the queue occupancy badge triples in 90 seconds.' Readers scrub the same replay themselves.
- **Required features:** replay of a real append-only event log; time travel backwards through it; failure as a first-class status; narration synced to the replay; real timestamps on screen
- **Missing pieces:** Storyboards cannot drive Mode B runs — the one hard, deliberately-enforced boundary, and it removes narration, camera and caption from exactly the case (real logs) that most needs them; a 'frozen log' mode where a finite recorded log is compiled like Mode A would close this without touching live semantics; smv-record refuses any storyboard containing run.play on a live run, so a post-mortem replay cannot be rendered to video at all; No wall-clock timestamp display bound to the frontier/view clock (the audience needs '14:07:22', not a bare scrubber); No log importer / field-mapping config (JSON Lines or CSV -> start/finish/fail/spawn calls) — every team writes the same adapter; Past events are deliberately not re-resolved against later topology, which is correct, but there is no documented recipe for 'the topology changed mid-incident' (a node added during the outage); No per-node live metric badge fed from log fields (error rate, queue depth) beyond token occupancy
- **Tools used for this today:** Grafana/Datadog dashboard screenshots pasted into the doc, screen recordings of Kibana, static timeline tables in the post-mortem template, hand-drawn incident timelines in Miro

## 9. Before/after automation story for onboarding and internal comms

- **Coverage today:** `good` · **Demand:** medium · **Effort:** small
- **What the user is doing:** Show a process as it is today and as it will be after a change, with the change itself animated — three manual steps merging into one automated one, and the wall-clock total collapsing.
- **Example scenario:** An enablement doc for a new deploy tooling rollout: the current 8-step manual release plays at declared durations totalling 2h; then condense() merges the three approval steps into one automated gate with the 2h -> 8s odometer, and the total-duration bar visibly shrinks. Packed by smv-pack into a single .html attached to the announcement email.
- **Required features:** condense/split choreography; duration rollups and totals; single-file self-contained embed; captions for the narrative; theme matching the intranet
- **Missing pieces:** Side-by-side / split-screen comparison of two specs in one view (today it is strictly a temporal before->after, which does not survive being screenshotted); Callout annotations pointing at the changed region ('this is the part that went away'); Multi-line or formatted caption for the two or three sentences this narrative actually needs; No PDF/slide export path for the same story when it has to go into a deck instead of a page
- **Tools used for this today:** Lucidchart/Miro before-after boards, two static Mermaid diagrams side by side, PowerPoint builds, Whimsical

## Cross-cutting needs from this perspective

- Pointer event surface on nodes and edges (click/hover/enter/leave/focus) exposed via g.on(), plus a selection state — blocked for explorables, live-lecture control, and any tooltip; today the only pointer behavior is container tap-toggle and CSS :hover
- A tooltip/popover layer built on that event surface (named as a known limit, but it gates three of the use-cases above)
- Importers from formats authors already possess: Graphviz DOT, Mermaid flowchart, OpenTelemetry/Jaeger trace JSON, GitHub Actions YAML, Airflow DAG, Step Functions ASL, and a field-mapping config for JSON Lines event logs -> Mode B calls
- A narratable path for recorded (finite, real) event logs: either lifting the storyboard/Mode B ban for logs that are closed rather than live, or a 'compile a finished log like Mode A' conversion — this single boundary blocks post-mortems, trace explainers, and any video made from real data
- A real text/annotation layer: multi-line and formatted captions, more than one text element at a time, title cards/lower-thirds, and callout arrows anchored to a node or to world coordinates
- Time made visible: a wall-clock/elapsed readout bound to the run clock, and the skipped temporal/Gantt layout (x = time) that trace and post-mortem work fundamentally needs
- Parallel and bidirectional edge separation between adjacent ranks — currently coincident polylines, which breaks request/reply pairs in every protocol explainer
- Per-element live data labels driven by run events (per-edge throughput/latency, per-node queue depth/error count), distinct from static edge labels and from token occupancy badges
- Node-side/headless static render to SVG without a browser, for docs-site build steps and progressive enhancement, plus an official React/MDX wrapper and URL-hash deep-linking to storyboard labels
- Layout families beyond layered Sugiyama — ring/radial for peer topologies, and author-supplied fixed coordinates as an escape hatch for algorithm figures where spatial arrangement is pedagogical
- Token identity: per-token label, color, and payload text, plus a public API to drop or delay an individual token
- Audio in the recording toolchain: VO muxing in smv-record (ffmpeg is already a dependency for --out), and the inverse of smv-fit — emit the timing the animation wants so a narrator can record against it
- Presenter ergonomics: a step-forward/step-back transport on the storyboard handle, a 'hold until advanced' step type, arbitration of arrow keys between presenter control and a11y focus navigation, and a second-screen notes view fed by g.cues()
