> Part of the [feature-gap research corpus](../README.md) · 2026-09-05 · opus agent adopting the perspective of an engineer building or explaining LLM agent systems (multi-agent orchestration traces, tool-call graphs, planning trees, RAG pipelines, eval harnesses, agent replays for debugging).

**Coverage tally:** 9 use-cases: 4 good, 5 partial, 0 poor.

## The agent's stance

Engineer building and explaining LLM agent systems — multi-agent orchestration traces, tool-call graphs, planning/search trees, RAG pipelines, eval harnesses, and agent replays used for debugging, review, and teaching. Evaluated sparkle-motion-visualizer (v0.1.0, repo-local package.json) against the work of turning agent execution into something a human can watch, scrub, and share. ## 1. Agent run replay for debugging (trace log → scrubbable animation)

- **Coverage today:** `good` · **Demand:** high · **Effort:** medium
- **What the user is doing:** An engineer has a completed multi-agent run — an append-only log of agent starts/finishes, tool calls, sub-agent spawns, retries, failures — and wants to *watch* it rather than read 4,000 lines of JSONL. Scrub to the moment the planner fanned out, see which sub-agent branch stalled, step to the next event boundary, rewind past a retry loop. This is the single closest match to what the library already is: Mode B is literally an append-only event log replayer with a frontier/view two-clock model and time-travel scrub.
- **Example scenario:** A supervisor agent spawns 3 researcher sub-agents; one calls a flaky search tool, retries 3× then fails; the join is configured 'any' so the supervisor proceeds on the first return. The engineer loads the run's JSONL into Mode B, plays at 4×, sees the pulse pile up on the failing tool node, seeks back 8s, steps forward event-by-event to find the point where the join fired before the third researcher returned.
- **Required features:** append-only live event log replay with seek/step; fail() as a first-class terminal status distinct from done; spawn/occupancy so N concurrent tokens on one node are visible; bounded retry loops with iteration badges; containers for sub-agent scope, collapsed by default, expandable; join policy any/all/count matching real orchestrator semantics; O(n log n) replay so a 40k-event log scrubs at interactive rates; embeddable in an internal dashboard with no build step
- **Missing pieces:** A trace-format importer (OpenTelemetry/OTLP spans, or LangSmith/Langfuse/AI-SDK export JSON) → {nodes,edges} + event log; today the consumer hand-writes the mapping; Payload inspection: no tooltip/detail-panel API to show a node's prompt, tool arguments, or response text on hover/click — the whole reason to pause on a node in a debug session; Selection state (g.select(id) / 'selected' event) to drive an external detail pane; only CSS :hover and read-only query sugar exist; Token pulses are not culling-aware, so a >150-element trace zoomed in shows orphan pulses floating over hidden nodes; Mode B deliberately does not re-fan past events over topology added later — correct for time travel, but a streaming importer that discovers nodes as spans arrive must pre-register topology or accept dropped fan-outs
- **Tools used for this today:** LangSmith trace view, Langfuse, W&B Weave, Arize Phoenix, Braintrust, Jaeger/Tempo/Grafana span waterfalls, AgentOps, raw JSONL + jq

## 2. Live agent-run monitor embedded in an internal ops dashboard

- **Coverage today:** `partial` · **Demand:** high · **Effort:** medium
- **What the user is doing:** An on-call engineer or an ops team watches an agent fleet execute *right now* — nodes light up as steps start, occupancy badges show how many in-flight items sit on each stage, failures go red the instant they happen, and the viewer can detach from the frontier to scrub back 30 seconds without losing the live tail. Mode B's frontier/view clock split (follow() snaps back to live) is purpose-built for exactly this and is rare in graph libraries.
- **Example scenario:** A document-processing agent pipeline runs 200 documents/hour: extract → classify → (fan-out) enrich/summarize → join → write. An SSE stream feeds run.start/finish/fail into a mounted graph on the team's internal status page. A spike of fail() on the enrich node turns it red; the engineer hits pause, scrubs back to see the first failure, then follow() to rejoin live.
- **Required features:** live mode fed by start/finish/fail/spawn with {at} timestamps; never-throws contract on unknown ids (self-healing as topology arrives) so a stream race can't crash the page; frontier vs. view clock with follow(); occupancy badges + traversed-edge width; single <script> embed with no build step for a plain internal HTML page; viewport culling for a big fleet graph
- **Missing pieces:** No streaming source adapter — no SSE/WebSocket/EventSource ingestion helper; every consumer writes the same socket→run.start/finish glue; Unbounded log growth: run.log() is a full copy and there is no windowing/compaction/retention API for a monitor left open for hours; No per-node or per-edge live numeric labels bound to run state (throughput/min, in-flight count beyond the occupancy pip, p95 latency, error rate) — the pipeline preset proves the mechanism exists for durations but there is no generic 'live metric label' channel; No threshold-driven styling from run state (e.g. auto data-emph='warn' when a node's fail rate crosses X) — highlight is a director op, not a rule; Mode B has no duration/total, so there is no 'expected vs. actual' progress arc on a node that is running long
- **Tools used for this today:** Grafana dashboards, Temporal Web UI, Airflow/Dagster/Prefect run graphs, LangGraph Studio, custom React Flow dashboards

## 3. Narrated architecture video for an agent system (docs, launch post, conference talk)

- **Coverage today:** `good` · **Demand:** medium · **Effort:** small
- **What the user is doing:** Explaining 'how our agent works' to people who will not read a sequence diagram: a scripted, voiced 60–120s animation where the camera pans to each subsystem as it appears, captions narrate, tokens flow through the real topology, and a retry loop actually ticks. This is the library's most distinctive capability — a JSON storyboard, deterministic headless-Chromium frame rendering, cue-sheet/SRT export, and a voice-over fitting CLI is a toolchain essentially nobody else ships for graphs.
- **Example scenario:** A team publishes 'Inside our RAG agent': the storyboard grows the graph phase by phase (retrieval → rerank → synthesize → verify → tool loop), the camera frames each new container as it fills, captions carry the script, `smv-record --cues out.srt` produces subtitles, and `smv-fit` stretches the waits to land on the recorded narrator's actual timestamps. Output is a byte-reproducible mp4 dropped into the docs site and a YouTube chapter list.
- **Required features:** serializable storyboard op array with per-step dur; director camera/highlight/caption/props ops; manual ticker + forced full motion for deterministic frames; smv-record → mp4/PNG sequence via headless Chromium + ffmpeg; --from/--to chapter re-render, frame-identical to the full take; g.cues() → .srt/.txt chapter list; smv-fit voice-over alignment from marks.json; font pinning so layout is stable across machines
- **Missing pieces:** No audio track muxing in smv-record — the mp4 is silent; the voice-over must be married in a separate ffmpeg/editor step even though smv-fit already knows the marks; No node shapes or iconography beyond rounded rects — an explainer usually wants a distinct silhouette for 'LLM call' vs. 'tool' vs. 'datastore' vs. 'human', currently only achievable through --smv-* color/props; Chromium + ffmpeg dependency chain makes this hard to wire into a CI docs build without a custom image; No transition between two *different* graphs (scene cut) — a storyboard grows one spec; showing 'v1 architecture → v2 architecture' means hand-authoring the removals; No storyboard preview/lint that reports total duration and per-label offsets without a browser (smv-fit refuses any run.play step, which most agent explainers contain)
- **Tools used for this today:** Excalidraw/Figma + screen recording, Motion Canvas, Remotion, Manim, After Effects, Mermaid + a static screenshot, tldraw

## 4. Shareable single-file incident postmortem of an agent failure

- **Coverage today:** `partial` · **Demand:** medium · **Effort:** medium
- **What the user is doing:** When an agent does something expensive or wrong, the artifact that circulates is usually a wall of pasted log. Instead: pack the topology, the actual event log, and a short storyboard into one self-contained .html file with no CDN dependency, attach it to the incident ticket, and let anyone open it offline and scrub the failure. smv-pack producing a single file that opens from file:// is a genuinely differentiated distribution story for an internal-tooling audience.
- **Example scenario:** An agent loops 47 times between 'plan' and 'critique' before hitting a budget cap, burning $180. The on-call engineer runs smv-pack over the exported spec + storyboard, attaches incident-4412.html to the Jira ticket; the reviewer opens it, watches the loop iteration badge climb, sees the critique node never reaching 'done', and reads the caption explaining the missing termination condition.
- **Required features:** smv-pack single-file HTML bundling IIFE + spec + storyboard; offline/file:// operation, no fetch or CDN; loop iteration badges (iter N/M) and declared-failure rendering; captions for the narrative annotations the reviewer needs; transport bar with scrub for a non-author viewer
- **Missing pieces:** smv-pack takes spec + storyboard only — there is no way to pack a Mode B **event log** into the file, which is exactly what an incident replay is; today one must transcode the real log into a Mode A simulation with fabricated durations (and storyboards are Mode-A-only anyway); No permalink/deep-link state (?t=12400&node=critique) so a comment can point at an instant — nothing serializes the current time + camera into a URL; No annotation-on-top-of-a-live-run path: captions are storyboard ops, and storyboards cannot drive Mode B, so a narrated *real* replay is structurally blocked; No cost/token counters — an incident about spend needs a running $ or token total, which has no equivalent of durationAgg
- **Tools used for this today:** pasted logs in Slack/Jira, LangSmith shared trace links, Loom recordings, Grafana snapshot links

## 5. RAG pipeline latency walkthrough (where the seconds actually go)

- **Coverage today:** `good` · **Demand:** medium · **Effort:** small
- **What the user is doing:** Showing a team, or a customer, why a RAG answer took 4.2 seconds: parallel retrievers fanning out at visibly different rates, a rerank join that waits for the slowest, an LLM synthesis dwell that dominates the bar. Mode A compiles a schedule from declared durations, so a measured trace becomes a proportional-time animation for free, and the pipeline preset already renders duration chips and sum/max rollups.
- **Example scenario:** Query → embed (40ms) fans out to vector search (180ms), BM25 (60ms), and a web tool (1.9s); join:'all' on rerank makes the wait for the web tool visually obvious; synthesis dwells 1.8s. The team then condenses the three retrievers into one 'hybrid retrieval' node to show the proposed caching change, and the preset's odometer rolls 4.2s → 2.1s.
- **Required features:** duration grammar on nodes and compiled Mode A schedule; implicit fan-out and AND-join with visible waiting; join:'all' semantics matching a real gather(); condense() N→1 choreography with the duration delta badge; pipeline preset duration chips + sum/max rollups + total bar; per-branch speed control to slow down the interesting branch
- **Missing pieces:** No Gantt/temporal layout mode (x = time with a sweeping scrubber line) — explicitly skipped; a latency audience frequently wants the waterfall next to the graph, and today the two views cannot be reconciled; No critical-path computation or highlight (which chain of nodes determines the total) — the query layer has no path-finding at all; Durations must be hand-entered into the spec; no helper to derive node.data.duration from a trace's span durations (p50/p95 across many runs); Parallel edges between adjacent ranks render coincident, so two retrievers wired identically between the same rank pair can visually merge; No units/precision control on duration display beyond the preset's own formatting
- **Tools used for this today:** Jaeger/Tempo waterfalls, Chrome DevTools performance panel, LangSmith latency breakdown, hand-drawn slides

## 6. Planning / tree-search replay (ReAct, ToT, MCTS, deep-research agents)

- **Coverage today:** `partial` · **Demand:** medium · **Effort:** large
- **What the user is doing:** Watching a search agent think: nodes appearing as the planner expands candidates, branches dimming as they're pruned, the chosen path spotlighted, backtracking visible as it happens. The diff-based auto-animation means the consumer just calls addNode/addEdge as the trace advances and gets the growth animation free, which is precisely the hard part in every other library.
- **Example scenario:** A deep-research agent expands 5 sub-questions, spawns searches under 3 of them, abandons 2 branches as low-value, and merges the surviving evidence. The replay adds nodes in trace order at a paced rate, uses highlight({variant:'mute',dim:true}) on pruned branches, and camera-follows the frontier of expansion.
- **Required features:** incremental addNode/addEdge with automatic keyed enter/FLIP animation; anchored viewport so the focal node holds still as the tree reflows; containers for grouping a branch's sub-search; highlight/dim spotlight for pruned vs. live branches, replace-not-accumulate; batch() to commit a whole expansion wave in one transition; componentOrder to keep sibling branch order stable across re-layouts
- **Missing pieces:** No tree-specific layout mode — a Sugiyama layered engine draws a 200-node search tree wide and flat where a tidy-tree (Reingold–Tilford) or radial layout is what the domain expects; the solver seam exists but no tree solver is shipped; No incremental/local layout: every addNode triggers a full relayout, so a fast-expanding tree animates the whole graph rather than just growing at the frontier (no measured cost data for the append-heavy case in the repo); No automatic 'follow the frontier' camera — camera targets are explicit ids in a storyboard, and there is no camera.follow(nodeId) that tracks the newest node during a live feed; No score/value display channel on nodes (a search tree wants the node's value estimate visible) beyond writing it into the label text; No collapse-by-depth / level-of-detail control for a tree that outgrows the pane
- **Tools used for this today:** D3 tree/tidy-tree, React Flow, Cytoscape.js, Graphviz dot renders, LangGraph Studio, custom notebook plots

## 7. Embedded interactive explainer in product docs or an onboarding page

- **Coverage today:** `good` · **Demand:** high · **Effort:** small
- **What the user is doing:** A docs page for an agent framework or an internal platform that ships a *live* diagram: the reader hits play, watches a request traverse the orchestrator, expands the 'tool layer' container to see the individual tools, collapses it again. Zero build step, one script tag, CSS-custom-property theming that inherits the docs site's dark mode, and a real accessibility story (ARIA tree + keyboard nav + linearized table) make this deployable on a public docs site where most JS diagram libraries fail review.
- **Example scenario:** The 'Architecture' page of an internal agent platform embeds a 40-node graph. Tapping the 'Retrieval' container expands it into 6 sub-steps with a shared transition; the theme follows the site's light/dark toggle via data-smv-theme; a screen-reader user tabs the tree and gets '<label> · status' announcements; the whole thing is 47.5KB gzipped.
- **Required features:** single-script IIFE, no build step, CDN-loadable; tap-to-toggle containers, never hijacking page scroll (ctrl/cmd+wheel zoom only); --smv-* theming with three-tier cascade including prefers-color-scheme; ARIA tree + keyboard navigation + optional linearized table fallback; enforced <50KB gzip budget; transport bar for reader-driven play/pause
- **Missing pieces:** No official React/Vue/Svelte wrapper — most modern docs sites are Docusaurus/Next/Astro-with-React, and every team writes the same useEffect mount/destroy shim; No tooltip system — a docs diagram almost always wants 'hover a node for one sentence of explanation'; the README's answer is 'write a preset', which is a real barrier for a docs author; Only one a11y surface at a time: turning the interactive tree off to use the table makes the graph non-keyboard-navigable entirely, and there is no stated WCAG conformance level or audit result for a public-site review; No responsive/mobile layout behavior documented (a 40-node LR graph on a phone is a pan-hunt); no auto direction switch or breakpoint-driven collapse; No lazy/IntersectionObserver mount helper for a long docs page with several embeds
- **Tools used for this today:** Mermaid, Excalidraw embeds, static PNG/SVG diagrams, React Flow, tldraw, D3 hand-rolls

## 8. Eval-suite fan-out view: where cases die across a test set

- **Coverage today:** `partial` · **Demand:** medium · **Effort:** large
- **What the user is doing:** Running an eval harness over N cases through the same agent graph and visualizing the aggregate — a token per case, occupancy showing how many are queued at each stage, failure counts accumulating on the nodes that break, edge weight showing how many cases took which branch. The token/occupancy model is the right abstraction; the aggregation reporting is the gap.
- **Example scenario:** 200 eval cases run through classify → route → (tool A | tool B | escalate) → verify. The view shows 200 tokens entering, 34 dying at the tool-B node, 12 at verify; edge weights render as heavier lines with badges on the dominant route; the engineer clicks the tool-B node to pull the 34 failing case ids into a side list.
- **Required features:** spawn(id, n) multi-occupancy and occupancy badges; edge weight rendering (heavier line + count badge); fail() per node with reason strings carried as event payload; live mode fed by a harness as cases complete; condense/collapse to keep a wide graph readable
- **Missing pieces:** Edge weight is a static spec field, not derived from run state — there is no 'N tokens have traversed this edge' counter that updates from the live log; No aggregate counters per node (passed/failed/skipped) as a first-class visual channel; the pipeline preset shows badges are possible but nothing generic exists; No drill-down: no selection API or click-payload event to get from a node to the list of case ids behind it; No histogram/distribution channel — an eval view wants per-node score distribution, not just a status; Query layer cannot answer 'which nodes are on paths that end in failure' (no path-finding, no cycle-listing API)
- **Tools used for this today:** Braintrust, LangSmith eval views, Arize Phoenix, W&B tables, pandas + matplotlib, spreadsheets

## 9. Before/after comparison of two agent architecture versions

- **Coverage today:** `partial` · **Demand:** medium · **Effort:** medium
- **What the user is doing:** Showing that v2 of an agent is better than v1 — fewer LLM calls, a tool loop removed, three sequential steps collapsed into one parallel gather — as an animated transformation rather than two side-by-side static diagrams. condense()/split() with the highlight → converge → reveal choreography, plus the pipeline preset's duration odometer and delta badge, is built almost exactly for this beat.
- **Example scenario:** A design review deck: v1's serialized 'retrieve → summarize → retrieve again → answer' animates into v2's parallel gather; the three retrieval steps condense into one node while the total-duration bar rolls 6.4s → 2.2s with a '−65% · 2.9× faster' badge; the storyboard captions carry the argument.
- **Required features:** condense(ids, newNode) with convexity guard, and split() as its mirror; staged 3-phase condense choreography reseated into the source nodes' layout slot; pipeline preset odometer + delta badge; storyboard + camera + caption for the review narrative; batch() so a multi-op restructuring commits as one transition
- **Missing pieces:** No graph-diff API: given spec A and spec B, nothing computes the add/remove/rename/condense op sequence between them — the author hand-writes the storyboard, which is the entire cost of this use case; condense() requires a convex id set and throws otherwise, which many real 'these three steps became one' refactors violate (a path leaves and re-enters); No side-by-side/split-pane or ghost-overlay mode to show v1 and v2 simultaneously; the library is one graph per mount; Cost/token deltas have no equivalent of durationAgg — the odometer only knows seconds, so '$0.14 → $0.03' or '9 LLM calls → 3' must be hand-built in a custom preset; No scene cut between two unrelated specs (see explainer-video limits)
- **Tools used for this today:** two static diagrams in a slide, Mermaid before/after, Figma, Graphviz diffs, hand-animated Keynote builds

## Cross-cutting needs from this perspective

- Trace-format ingestion: an official adapter from OpenTelemetry/OTLP spans (and/or common agent-trace exports) to {nodes,edges} plus a Mode B event log — every agent-facing use case here starts by hand-writing the same mapping, and the library today accepts only its own spec shape (no importers of any kind are shipped).
- A streaming source helper (SSE/WebSocket/EventSource → run.start/finish/fail/spawn), including log windowing/compaction, so a monitor left open for hours does not grow an unbounded in-memory log.
- Payload inspection and selection: a tooltip/detail-panel contract plus a selection API and click/hover events carrying the node's data payload. Debugging, eval drill-down, and docs explainers all need 'what is inside this node', and the current answer for every one of them is 'write a preset'.
- Live-derived numeric labels bound to run state — per-node counters (passed/failed/in-flight, tokens, $ cost) and per-edge traversal counts that update from the event stream. The pipeline preset proves the rendering mechanism; what is missing is a generic channel and a cost/token analogue of durationAgg with rollups.
- Narrating a REAL run: storyboards, captions, camera and smv-record are all Mode-A-only by design, so every use case built on an actual event log (debug replay, incident postmortem, live monitor) is cut off from the entire narration/recording toolchain. A Mode-B-compatible director layer (even without deterministic video) is the single highest-leverage gap for this perspective.
- Sharable state: deep-link/permalink serialization of (time, camera, emphasis) and a way to pack a Mode B log into smv-pack's single-file HTML, so a replay can be attached to a ticket or pointed at in a review comment.
- A framework wrapper (React first) — the platform/docs/dashboard surfaces where these graphs belong are overwhelmingly React, and the imperative DOM-only API forces the same mount/destroy/props-sync shim in every consumer.
- Layout family beyond layered Sugiyama, reached through the existing solver seam: a tidy-tree/radial solver for planning trees, and incremental/local relayout for append-heavy live feeds where a full relayout per event is the wrong cost model.
- Large-trace legibility: culling-aware token pulses (a known open defect), level-of-detail / collapse-by-depth, and a documented ceiling for how many nodes and how many log events the library is actually good for — agent traces routinely exceed the 150-element culling threshold and the 300-node figure the repo benchmarks.
- Node visual vocabulary: shapes or icon slots to distinguish LLM call / tool / retriever / human / datastore. Color via --smv-* is the only differentiator today, which is both accessibility-fragile and insufficient for explainer and architecture use cases.
