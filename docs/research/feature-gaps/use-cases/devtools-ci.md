# Use-case pass: Developer tooling, CI/CD and build systems
> Part of the [feature-gap research corpus](../README.md) · 2026-09-05 · opus agent adopting the perspective of a developer-tooling / CI-CD / build-system engineer (build graphs, CI pipelines, monorepo task graphs, deployment rollouts, dependency graphs).

**Coverage tally:** 9 use-cases: 4 good, 5 partial, 0 poor.

## The agent's stance

Developer tooling / CI-CD / build-system engineer — build graphs, CI pipeline DAGs, monorepo task graphs, deployment rollouts, dependency graphs. I judged the library on whether it can be the *live* and *narrated* view of work executing over a DAG, not on whether it can draw a static dependency diagram (any of graphviz/mermaid/elkjs/cytoscape do that better and cheaper). The distinctive assets from my seat are: Mode B's append-only event log with a frontier/view two-clock time-travel model, Mode A's compiled token schedule with joins and bounded retry loops, containers with animated expand/collapse and meta-edge aggregation, condense/split choreography, the storyboard/cue/record toolchain, and single-script embeddability with a <50KB budget. The recurring blockers are equally consistent: no time axis (a CI graph without duration-to-x is half a view), no per-node live text/metric channel, no node activation (click→open log) event, no importers from the formats CI graphs actually live in, and the Mode A/Mode B split that keeps every narration and recording feature away from real runs.

## 1. Live CI run viewer embedded in a build UI

- **Coverage today:** `partial` · **Demand:** high · **Effort:** medium
- **What the user is doing:** Replace (or sit beside) the stage-list/table view in a CI product or an internal build dashboard with a job DAG that animates as the run happens: jobs light up on start, tokens cross edges as artifacts pass downstream, fan-out to parallel matrix jobs and fan-in at the join step are visible, failures stop a branch and the rest keeps going. Engineer watching a build sees where the wave is and what is blocking, without reading 40 rows of status text.
- **Example scenario:** A platform team embeds the graph in their internal Buildkite dashboard. A webhook stream feeds run.start('test:unit')/run.finish('build:web')/run.fail('e2e:chrome',{reason:'timeout'}) into a Mode B run. Ten matrix shards fan out from 'build', join at 'package' with join:'all'; the shard that fails greys its branch while the other nine keep flowing, and the 'package' join pips show 9/10 arrived so it's obvious why the run is stuck.
- **Required features:** Mode B live append-only event log (start/finish/fail/spawn) with {at} timestamps; join policy 'all'/'any'/{count:k} with visible join-slot pips; implicit fan-out/fan-in token animation; frontier vs view clock, follow() to snap back to live; memoized state() so an idle live graph is cheap per frame; viewport culling for large runs; IIFE/ESM embed with no build step, CSS-custom-property theming to match the host UI
- **Missing pieces:** Per-node live secondary text line fed from events (elapsed timer, shard count, queue depth) — node text is a static label sized once at commit; Node activation event for non-container nodes (click/Enter → payload) so a job box can open its log; today only container tap-toggle exists and there is no 'nodeclick' in GraphEventMap; Hover tooltip/popover surface (commit SHA, runner, duration) — only a CSS :hover stroke ships; data-status vocabulary for CI-native states beyond pending/active/done/failed: queued, skipped, cancelled, cache-hit (renderable via custom data-status + CSS today, but not driven by Mode B, which only emits start/finish/fail); Mode B 'cancel'/'skip' primitive that terminates a branch without the red failure semantics; Framework wrapper (React) — CI UIs are React and mount/destroy lifecycle + prop-diff wiring is hand-rolled per consumer
- **Tools used for this today:** GitHub Actions' built-in job graph view (from memory), Buildkite pipeline/waterfall view, Jenkins Blue Ocean pipeline view, Argo Workflows UI DAG, Tekton Dashboard, Dagster / Airflow run graph views, hand-rolled d3 + dagre-d3 dashboards

## 2. Post-mortem scrub of a failed build ('rewind the run')

- **Coverage today:** `partial` · **Demand:** high · **Effort:** medium
- **What the user is doing:** Take the recorded event log of a build that already finished and let an engineer scrub it like a video: drag back to t=4m12s to see which jobs were in flight when the flaky one blew up, step event-by-event through the collapse, share a URL that opens at that instant. This is the single strongest fit for the frontier/view two-clock design — time travel over a real log is exactly what CI debugging needs and almost nothing offers.
- **Example scenario:** Nightly release build fails. The CI system already stores per-job started_at/finished_at/conclusion; a small mapper turns that into an smv log and calls run.reset({log, mode:'live'}, t). The on-call engineer scrubs to the moment 'db-migrate' failed and sees that 'deploy-staging' had already started (a real ordering bug), then hands the link to the owning team.
- **Required features:** run.log() / run.reset({log,mode:'live'}, time) round-trip for snapshot and restore; run.seek(ms) as state restore rather than replay, clamped to [0,frontier]; binary-heap replayLive (40k events at ~73ms) so a long build scrubs smoothly; transport bar with scrub slider (opts.controls); token/occupancy/loop state exposed as RunState for a side panel; smv-pack single self-contained HTML so the replay can be attached as a build artifact
- **Missing pieces:** Wall-clock time axis / timestamp readout: the scrubber shows ms-since-run-start, with no mapping back to absolute timestamps or to the log lines an engineer will grep; Duration-to-x (Gantt/temporal) layout mode with a sweeping playhead — explicitly never built; for post-mortems 'which jobs overlapped and for how long' is the primary question and rank position answers it only indirectly; Replay-rate decoupling: replaying a 40-minute historical log in 30s needs frontier scaling; today the frontier is real elapsed ms and speed() only scales catch-up of a detached view clock, so fast historical playback is a reset+seek loop the consumer writes; Log→schedule transcoder (Mode B log compiled into a Mode A sim) — without it, none of the storyboard, cue-sheet or smv-record tooling can touch a real run; Deep-link/permalink of run position (serialize {time, camera, highlight} to a URL fragment and restore) — has to be hand-built on seek()/camera(); Per-node 'first failure' navigation (jump camera to the earliest failing node) — run.timeOf exists for Mode A only
- **Tools used for this today:** CI job logs + timestamps (the actual status quo), Datadog CI Visibility / Trace-view flame charts, Honeycomb / Jaeger trace waterfalls used for build traces (from memory), Buildkite waterfall, BuildBuddy invocation timing view for Bazel

## 3. Monorepo task-graph explainer: 'what actually happens when you run turbo/nx/bazel build'

- **Coverage today:** `good` · **Demand:** medium · **Effort:** small
- **What the user is doing:** A recorded, narrated animation of the repo's own task graph — packages as containers, task nodes inside, cache hits collapsing away, the critical path highlighted — shipped in the platform team's docs and in new-hire onboarding. The point is not an interactive tool but a video/embed the team can reuse and re-render when the graph changes.
- **Example scenario:** Build-platform team records a 90-second clip: camera opens fitted on 12 package containers, caption 'apps/web depends on 9 packages', highlight the critical path in 'warn', expand 'packages/ui' to show its 4 tasks, then run tokens through so viewers see why lint parallelises and typecheck does not. Recorded with smv-record --out onboarding.mp4 --cues chapters.txt, re-rendered from CI whenever the project graph JSON changes.
- **Required features:** Storyboard JSON op array with per-step dur, snapshotted for backward scrub; Director camera/highlight(dim spotlight)/caption/props ops; g.cues() → SRT/YouTube chapters, smv-fit for voice-over alignment; smv-record deterministic frame renderer (byte-identical, --from/--to chapter re-render, --font pinning); containers with expand/collapse and meta-edge aggregation for package-level vs task-level views; componentOrder for stable slot ordering of disconnected package clusters
- **Missing pieces:** Importer/adapter for real project-graph formats: `nx graph --file`, `turbo run --graph` (dot), `bazel query --output=graph`, `pnpm list --json` → GraphSpec. Today the spec is hand-written or a bespoke script per repo; Auto-grouping helper (derive containers from an id path prefix, e.g. 'packages/ui/*' → one container) so a generated graph becomes a nested one without hand-authoring parents; Critical-path query (longest weighted path over durations) to feed highlight() — no path-finding in the query layer at all, only children/descendants/roots; Node shape/icon vocabulary (a cache-hit task vs a real task vs a gate) — rounded rects only; ffmpeg + chromium dependency chain makes 'render in CI' a container-image problem (--png-dir avoids ffmpeg but not chromium)
- **Tools used for this today:** nx graph interactive viewer, turbo --graph piped to graphviz, bazel query + dot, Mermaid in the repo README, screen recordings of the terminal (asciinema), hand-made Excalidraw/Figma diagrams

## 4. Progressive delivery / rollout console (canary waves, regions, rollback)

- **Coverage today:** `partial` · **Demand:** medium · **Effort:** medium
- **What the user is doing:** Visualise a deployment rollout as it happens: waves as ranks, regions or clusters as containers, canary analysis gates as join nodes, and rollback as a real back edge with iteration badges. The operator watches occupancy move region by region and sees the rollback arc fire rather than reading it in a changelog.
- **Example scenario:** An Argo Rollouts-style progressive delivery: 'canary 5%' → 'analysis (5m)' → 'canary 25%' → … → 'full'. Analysis fails at 25%, a loop:true edge back to 'canary 5%' with maxIterations:2 renders the retry as an arc with an 'iter 1/2' badge, and the third failure marks the node data.fail with the reason string 'error-rate 3.4%' carried through as the fail event.
- **Required features:** Back edges as first-class consistent-side arcs with loop iteration badges; Bounded retry loops with maxIterations and 'loop' events (Mode A) / start-clears-failed retry semantics (Mode B); Containers for region/cluster grouping, status roll-up from earliest-failing descendant; occupancy badges (how many pods/instances are at a stage); emphasis variants ok/warn/focus + spotlight dim for the wave currently moving; theme tokens so it drops into an existing ops console
- **Missing pieces:** Numeric occupancy semantics beyond token counts: '412/2000 pods healthy' needs a per-node live metric label and a progress-fill within the node box, neither of which exists (progress exists in RunState but only as dwell fraction for Mode A); Per-edge live throughput/rate label updated from events — edge labels are static free text set at commit; Loop iteration badges in Mode B: the loop/iteration event vocabulary is Mode A only (Mode B never emits 'loop'), so a live rollback shows as a plain re-start with no iter N/M badge; Gate/decision node shape (diamond) to distinguish an automated analysis gate from a deploy step; Threshold/alert visual channel driven by a numeric datum (e.g. auto-warn variant when error rate crosses a value) — must be hand-coded on top of props()
- **Tools used for this today:** Argo Rollouts dashboard / Argo CD app view, Spinnaker pipeline UI, Flagger + Grafana panels, AWS CodeDeploy / CloudWatch deployment views, Harness rollout UI (from memory)

## 5. Per-PR build-impact preview posted as a self-contained artifact

- **Coverage today:** `good` · **Demand:** medium · **Effort:** small
- **What the user is doing:** On every pull request, generate a small animated view of what this change affects: the touched packages, the propagation wave through dependents, which tasks are cache hits and which must rerun, and the projected critical path. Packed as one HTML file (or an mp4/GIF) and attached to the PR so a reviewer sees blast radius without running anything.
- **Example scenario:** A PR touches packages/logger. CI runs the affected-graph query, emits spec.json + a 6-step storyboard (highlight touched → animate propagation to 23 dependents → collapse unaffected packages to mute → caption 'adds 11 min to CI'), then smv-pack -o impact.html and uploads it as a check artifact; the bot comments with a link.
- **Required features:** smv-pack: IIFE + spec + storyboard into one file:// openable HTML, no CDN fetch; storyboard build-time validation so a generated script fails in CI, not in the reviewer's browser; highlight with dim:true spotlight to show blast radius against a muted rest-of-repo; exportSVG/exportPNG for a static thumbnail in the comment body; size budget (<50KB gzip) keeps the artifact small
- **Missing pieces:** A programmatic 'affected set' input path is fine, but there is no reverse-reachability query (ancestors/dependents of a node) in the library — g.descendants() is container children, not edge-following; consumers reimplement graph traversal; GIF/animated-WebP output from smv-record (PR comments cannot embed mp4 inline on GitHub; PNG sequence → gif is a manual ffmpeg step); Server-side/Node rendering of a still: exportPNG is browser-only and exportSVG is ESM-only, so a bot generating a thumbnail needs headless chromium just for a picture; Fallback for artifact viewers that strip scripts (a static SVG-with-CSS-animation degradation mode)
- **Tools used for this today:** nx affected --graph, Bazel target diff scripts + graphviz, GitHub check annotations and plain markdown tables, danger.js bots with mermaid diagrams, Buildkite annotations

## 6. Automation migration story: manual release process → automated pipeline

- **Coverage today:** `good` · **Demand:** medium · **Effort:** small
- **What the user is doing:** Show, as a narrated animation, how a release process changed: five manual approval steps condense into one automated gate; a monolithic deploy step splits into per-service deploys. This is exactly what condense()/split() were built for and is a real recurring artifact for platform teams (internal RFCs, architecture-decision records, all-hands slides, conference talks, vendor pitch decks).
- **Example scenario:** The demo/sdlc.html story generalised: a platform team's 'we cut release lead time from 4 days to 40 minutes' deck. Chapter 1 shows the manual pipeline with durations in days; chapter 2 condenses 'ticket → approve → QA sign-off → change board' into one 'automated gate' node with the 3-phase highlight/converge/reveal choreography; chapter 3 splits 'deploy' into six service deploys running in parallel; captions and camera moves carry the narration, recorded to mp4 with chapter markers.
- **Required features:** condense(ids,newNode)/split(id,{nodes,edges}) with staged 3-phase choreography and slot reseating; convexity guard so an invalid condense fails at build time; storyboard snapshotting so backward scrub through structural changes works; camera framing (node/nodes/fit/absolute/relative) and caption overlay; smv-record + smv-fit to land beats on a recorded voice-over; two comparable durations (4d vs 40m) via the duration grammar
- **Missing pieces:** Side-by-side / before-after split-screen mode (two mounts on one recorded canvas with a shared clock) — has to be composed in ffmpeg by hand; Duration comparison rendering: no way to show 'this step was 4d, now 40m' as a visual length; without a temporal layout the durations are only in labels; Presenter/step-through mode driven by keyboard (space = next storyboard beat) for live talks; the transport bar is play/scrub, not slide-advance; No export of the storyboard as slides/PDF frames per label (PNG-dir + --from/--to gets close but is per-chapter video, not one still per beat)
- **Tools used for this today:** Keynote/PowerPoint build animations, Excalidraw + screen recording, Mermaid diagrams in an RFC (static), Whimsical / Miro, hand-authored d3 transitions

## 7. Flaky-test and retry-budget visualisation

- **Coverage today:** `partial` · **Demand:** medium · **Effort:** medium
- **What the user is doing:** Make retry behaviour legible: which steps in the pipeline actually retry, how many iterations they burn, and how much wall-clock the retries cost. The loop-edge + iteration-badge + compressed in-place tick model is unusually well suited to this and no mainstream CI UI shows retries as anything but repeated log lines.
- **Example scenario:** A team's e2e suite is retried up to 3× on failure. Over a week's runs, the aggregated graph shows 'e2e:checkout' with a loop edge at iter 2.7/3 average and a weighted meta-edge (weight badge) into 'package' representing 340 runs; scrubbing a single run shows the 2 retries as in-place ticks, then a third failure marking the node failed with reason 'selector timeout'.
- **Required features:** loop:true edges with maxIterations, first hop as a real arc then compressed in-place ticks; 'loop' events {iteration,max} and iter N/M badges; edge weight (>1 renders heavier line + count badge) for aggregation across many runs; data.fail with a reason string carried into the fail event; iterations option to cap a compile below maxIterations
- **Missing pieces:** Aggregate/statistical mode: no notion of a distribution over many runs (p50/p95 duration per node, retry rate per edge) — edge weight is a count only, and every visual channel is per-run; Per-node histogram/sparkline slot (a small inline visual under the label) for duration spread; Loop vocabulary in Mode B (no 'loop' events, no iteration badge from a live log) so retry visualisation only works in simulated mode; Edge label updated from live events (retry count ticking up) — static labels only; Selecting/filtering to 'only nodes that retried' — the query layer has predicates but no interactive selection or filter-to-subgraph view
- **Tools used for this today:** Datadog CI Visibility flaky-test dashboards, BuildPulse / Trunk flaky test detection, Jenkins test-result trend charts, home-grown Grafana panels over a CI events table

## 8. Terraform/IaC plan-and-apply visualiser

- **Coverage today:** `partial` · **Demand:** medium · **Effort:** large
- **What the user is doing:** Show a plan as a dependency DAG with create/update/replace/destroy encoded visually, then animate the apply as it happens — resources going active in dependency order, parallelism visible, a failure stopping its subtree while siblings continue. Both halves (static plan review, live apply) matter and the second is the one nobody serves.
- **Example scenario:** A platform engineer runs terraform apply on a 300-resource stack. `terraform graph`/plan JSON becomes the spec, modules become containers, and a wrapper streams the apply's per-resource start/complete lines into a Mode B run. When aws_rds_cluster.main fails after 11 minutes, the graph freezes the branch and the engineer scrubs back to check what had already been created before the failure — the exact question 'what state am I in now' that the CLI output answers poorly.
- **Required features:** Mode B live log fed from streamed CLI output, unknown-id calls self-healing (no-op + warn until the node appears); containers for module nesting at arbitrary depth; failure stops a branch, container status rolls up from earliest failing descendant; viewport culling at 300+ elements (measured 1.6–1.8ms median frame); expandAll/collapseAll in one shared transition for module-level vs resource-level views
- **Missing pieces:** Importer for `terraform graph` DOT / plan JSON → GraphSpec (no DOT/GraphML importer of any kind); Per-node action styling as a first-class channel (create/update/replace/destroy) — expressible as custom data-status + CSS, but nothing maps it to run state; Long-running-node affordance: an 11-minute resource shows as a node that is simply 'active' with no elapsed counter or progress; Mode B has no declared duration to derive progress from, and there is no live text channel to print one; Scale headroom above a few hundred nodes is unverified for layout (culling is a render-side measurement; the ~630-line engine's ranking/ordering cost at 2–5k nodes is not documented); Search / focus-a-node-by-name with camera framing — camera can frame a node id but there is no search UI or filter-to-neighbourhood view; Node dragging is absent, so a reviewer cannot untangle a dense region by hand (documented, deliberate)
- **Tools used for this today:** terraform graph | dot -Tsvg, Terraform Cloud/HCP plan UI (list-based), Pluralith (from memory), Rover (terraform visualizer, from memory), Infracost/Spacelift run views, Crossplane/ArgoCD resource trees

## 9. Status-page / NOC wall pipeline board

- **Coverage today:** `good` · **Demand:** low · **Effort:** small
- **What the user is doing:** A big-screen, always-on view of the org's release trains or data pipelines: one embedded graph per train, tokens moving, failures pulsing, no interaction expected. The embed-anywhere, no-build-step, small-bundle, CSS-themed design fits an internal wiki page or a Grafana text panel where a heavyweight React app cannot go.
- **Example scenario:** A team drops a <script> tag into a Confluence page (or a Grafana text panel) showing the nightly data pipeline: 6 containers, live-fed from a polling endpoint every 15s via run.finish/run.fail, theme dark, controls off, interaction off, camera fit. The panel is never clicked; it just has to be correct and cheap for 12 hours a day.
- **Required features:** single <script> IIFE, global SparkleMotion, no build step, CDN or vendored; viewport.setInteractive(false) and controls:false for a display-only board; one shared ticker per instance and memoized live state() so an idle board costs a comparison per frame; dark theme + prefers-color-scheme auto, --smv-* tokens to match the wall's palette; pulse emphasis modifier (ticker-driven, not CSS animation) for the attention beat on a failure; prefers-reduced-motion respected for accessibility-sensitive displays
- **Missing pieces:** Unattended long-run robustness is undocumented: an append-only Mode B log grows without bound over a 12-hour board with no log compaction/windowing API (reset({log:trimmed}) is the manual workaround); Auto-recovery on feed loss (stale-data indicator, reconnect banner) — nothing distinguishes 'nothing is happening' from 'the websocket died'; Multi-instance-per-page cost is only partly addressed (one deduped stylesheet, but each mount owns its own ticker — N boards means N rAF loops); No headless/screenshot cadence helper for wall displays that poll an image instead of running JS
- **Tools used for this today:** Grafana dashboards with stat panels, Statuspage / internal status pages, Jenkins Build Monitor plugin / Radiator views, custom React TV dashboards

## Cross-cutting needs from this perspective

- Spec importers for the formats CI graphs already exist in — Graphviz DOT (terraform graph, turbo --graph, bazel query), GitHub Actions / GitLab CI workflow YAML, nx/turbo project-graph JSON, OpenTelemetry-style span trees. Every use case above currently begins with the consumer writing a bespoke mapper; this is the single highest-leverage missing surface and it fits the library's own 'adapters' seam.
- A log→schedule transcoder (Mode B event log compiled into a Mode A sim). This one bridge unlocks storyboards, cues, smv-fit and smv-record over *real* runs, which is what post-mortems, PR artifacts, incident reviews and onboarding videos all actually want. Today the entire narration/recording toolchain is walled off from every live data source by design.
- A per-node and per-edge live text/metric channel updated from events (elapsed timer, occupancy count, throughput, queue depth, retry count), rendered as a secondary line/badge and re-measured on change. Six of nine use cases name a variant of this; node text today is a static label sized once at commit.
- Node activation as a first-class event: a non-container node click/Enter emitting {id, data} so a box can open a job log, a resource in the state file, or a package's README. Currently only containers respond to taps and GraphEventMap has no click event at all, which forces consumers to reach past the public surface into the renderer.
- Temporal/Gantt layout mode (x = time, sweeping playhead) plus a wall-clock time axis and timestamp readout on the scrubber. Explicitly skipped in the plan; for CI, build systems and rollouts, duration and overlap are the primary questions and rank position only approximates them. This is the biggest single capability gap for this whole domain.
- Graph-algorithm queries in the read layer: reverse reachability (dependents/ancestors along edges), path between two nodes, and longest/critical path weighted by declared durations. g.descendants() is container nesting, not edge traversal, so every consumer reimplements traversal to feed highlight().
- A hover/tooltip and detail-on-demand surface (or a documented preset that supplies one). CI nodes carry commit SHAs, runner names, exit codes and durations that cannot all fit in a label, and the shipped affordance is a CSS stroke on :hover.
- Scale and shape headroom for generated graphs: documented layout (not just render) cost above ~1k nodes, an auto-grouping helper that derives containers from id path prefixes, search/filter-to-neighbourhood with camera framing, and separated parallel edges between adjacent ranks — generated dependency graphs routinely hit all four.
- A distinguishable shape/icon vocabulary beyond rounded rects (gate/decision, cache-hit, external/third-party, manual-approval) so a machine-generated graph can encode node kind without relying on colour alone.
- An official React wrapper. Every CI product UI and internal dashboard in this space is React; imperative mount/destroy with prop-diffing is workable but is friction on the exact first-contact path where the library must feel effortless.
