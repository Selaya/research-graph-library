# Use-case pass: SRE and observability
> Part of the [feature-gap research corpus](../README.md) · 2026-09-05 · opus agent adopting the perspective of an SRE / observability engineer (service maps, distributed traces, dependency health, incident timelines, chaos experiments, capacity flows).

**Coverage tally:** 9 use-cases: 5 good, 3 partial, 1 poor.

## The agent's stance

SRE / observability engineer — service maps, distributed traces, dependency health, incident timelines, chaos experiments, capacity and queue flows. My daily artifacts are: a dependency graph that changes state over time, an event log with real timestamps, and a story I have to tell to other humans (postmortem, exec review, on-call training). Judged against that, sparkle-motion-visualizer's distinctive assets are Mode B (append-only live event log + frontier/view two-clock time travel), the storyboard/director/caption layer, the deterministic recorder, and single-script embeddability — not its layout quality. Its distinctive gaps for me are: no time-axis (Gantt) layout, no numeric/metric channel on edges, no continuous "rate" concept (only discrete tokens), and the hard wall that storyboards/recording work on Mode A only, which is exactly backwards for incident work where the truth lives in a real log.

## 1. Incident postmortem replay as a narrated video

- **Coverage today:** `partial` · **Demand:** high · **Effort:** large
- **What the user is doing:** Turn a real incident's event log (alerts firing, services degrading, failover kicking in, rollback landing) into an animated, captioned replay of the dependency graph that can be scrubbed in the review meeting and exported as an mp4 attached to the postmortem doc. Today this is rebuilt by hand as slides or a screen recording of Grafana that ages out when dashboards change.
- **Example scenario:** Checkout latency incident: at T+0 the payments-gateway node turns active, at T+2m it fails (run.fail(id,{reason:'upstream 503'})), the retry loop edge to payments-provider ticks its iteration badge, the AND-join at order-confirm never fires, and downstream nodes stall with occupancy pips filling. An SRE feeds the exported Alertmanager + deploy + trace-summary events as a Mode B log with real {at} timestamps, adds captions per phase ('03:14 — provider starts 503ing', '03:19 — we retried into the failure'), and records a 90-second mp4 for the incident review.
- **Required features:** Mode B live log replay with {at} timestamps clamped to a frontier; run.seek / two-clock time travel for scrubbing backward in the meeting; fail() as a terminal sibling of finish(), sticky 'failed' status; loop edges with iteration badges (retry storms); join policy 'all'/'any'/{count:k} with drop/ghost events (quorum, partial failover); caption overlay + cue sheet; smv-record deterministic mp4 + --cues SRT/chapters; run.log()/run.reset({log}) for archiving and re-opening the replay
- **Missing pieces:** Storyboard/director ops (camera, highlight, caption, props) driving a Mode B run — currently enforced as Mode A only at multiple layers, so the exact case that matters most (narrating a REAL log) cannot be scripted; smv-record refusal on any storyboard containing a Mode B run.play — no video export path for real-log replays at all; A log importer/normalizer from common sources (Alertmanager/Prometheus alert state changes, OpenTelemetry span start/end, Kubernetes events, PagerDuty timeline) into the start/finish/fail/spawn vocabulary; Wall-clock timestamp display bound to the view clock (an absolute '03:14:22 UTC' readout, not just elapsed ms) and wall-clock-labelled chapter markers; Non-token status transitions on a node from the log (e.g. 'degraded', 'saturated') without an occupancy token being present — today Mode B state is occupancy-driven; Log-driven props/emph channel: mapping a numeric severity in an event onto --smv-emph without hand-writing a listener
- **Tools used for this today:** screen recordings of Grafana/Datadog dashboards (from memory), incident.io / Jeli / FireHydrant incident timelines (text, not graph), Google Slides / Miro hand-built sequence diagrams, Datadog Service Map replay (time-window scrubbing, no narration export), Jaeger/Tempo trace views

## 2. Live blast-radius wallboard for an active incident

- **Coverage today:** `partial` · **Demand:** high · **Effort:** medium
- **What the user is doing:** An always-on embedded view of a service dependency graph where nodes reflect current health and the graph shows what is downstream of the thing that is burning right now — mounted on the incident bridge screen or inside the on-call runbook page, driven by a websocket/SSE feed of health transitions.
- **Example scenario:** During a Redis cluster degradation, the war-room tab shows session-store in 'failed', a spotlight (dim:true) drops everything not reachable from it to 28% opacity, and the four downstream services that depend on it pulse. As mitigation lands the operator scrubs back 10 minutes to check whether the API gateway degraded before or after the cache did.
- **Required features:** Mode B append-only log fed from a live stream, none of whose calls throw on unknown ids (self-heals as topology catches up); frontier vs view clock with follow() to snap back to live; memoized state() so an idle live graph costs a comparison per frame; highlight/dim spotlight surviving relayouts; viewport culling for large maps; single-script CDN embed into an existing internal page
- **Missing pieces:** Reachability/impact query (descendants along edges from a failed node) — g.descendants() walks parent/container nesting, not edge reachability; no path-finding or downstream-closure API; Continuous metric channel per node/edge (error rate, saturation, RPS) mapped to color/width, distinct from the discrete token/occupancy model; Per-edge live throughput/latency label that updates from events without a full re-render authoring effort; A stable 'degraded' (partial) status between done and failed, in both the status vocabulary and the a11y announcer; Log windowing/retention — an append-only log on a wallboard running for days grows unbounded with no documented compaction or truncate-before(t); Auto-refit / auto-camera on a newly failing node (camera ops are storyboard/director-driven, and the first camera op permanently disables auto-refit)
- **Tools used for this today:** Kiali (Istio service graph), Datadog Service Map, Grafana Service Graph / node graph panel, Netflix Vizceral (archived, from memory), Lightstep/ServiceNow Cloud Observability service diagram, hand-rolled D3/Cytoscape.js internal wallboards

## 3. Distributed trace explained as an animated call graph

- **Coverage today:** `partial` · **Demand:** medium · **Effort:** large
- **What the user is doing:** Take one representative slow trace and show the request token actually travelling through services — fan-out to three parallel backends, the slow one holding the join, the retry, the timeout — instead of asking a junior engineer to read a 200-span waterfall.
- **Example scenario:** A p99 checkout trace: token enters api-gateway, fans out to inventory / pricing / fraud-score; pricing takes 1.8s while the others finish in 40ms, and the 'all' join visibly waits on it. Durations come straight from span durations via the duration grammar ('1.8s'), and the whole thing is packed with smv-pack into a single HTML file attached to the Jira ticket.
- **Required features:** Mode A compile from declared per-node durations (span durations map 1:1); implicit fan-out / AND-join with visible waiting; duration grammar with ms/s/m units; step() and seek() to walk event boundaries; run.timeOf(nodeId) for callouts; smv-pack single self-contained HTML
- **Missing pieces:** Gantt/temporal layout mode (x = time, sweeping playhead) — explicitly skipped in the plan; without it the animation shows ordering but the classic waterfall comparison of span extents is impossible, and this is the single most-expected view for traces; OTLP/Jaeger/Zipkin trace-JSON importer producing {nodes,edges} + durations (no data-source adapters exist at all); Span-level nesting where a container's own duration is the parent span (containers cannot be executable steps; durationAgg is sum/max rollup, not 'parent span wall time with self-time'); Critical-path highlighting (which chain actually determined total latency) — no graph-algorithm queries; Aggregate mode: N traces collapsed into one graph with p50/p99 per edge
- **Tools used for this today:** Jaeger, Grafana Tempo, Honeycomb trace view, Datadog APM flame graph, AWS X-Ray service map + traces, Zipkin

## 4. Chaos game-day briefing and dry-run

- **Coverage today:** `good` · **Demand:** medium · **Effort:** small
- **What the user is doing:** Before running a chaos experiment, show the room what you intend to break and what you predict will happen — steady state, injection, expected degradation, expected recovery — then replay the actual run against the prediction.
- **Example scenario:** A game day that kills one of three availability-zone replicas: the storyboard opens on the healthy graph, camera pushes into the az-b replica, a caption reads 'we will kill this at 14:00', the node flips to failed via data.fail, the quorum join ({count:2}) still fires because two replicas remain, and the caption asserts the hypothesis 'writes continue, p99 rises under 200ms'. The recorded mp4 goes in the experiment doc; afterwards the real Mode B log is loaded to compare.
- **Required features:** Storyboard JSON with camera/caption/highlight/props ops and per-step dur; data.fail declared failure with a string reason; join {count:k} quorum semantics — a genuinely good fit for replica/quorum reasoning; condense/split choreography for 'these three become one managed service'; smv-record mp4 + cues for the briefing deck; smv-fit to align holds to a recorded voice-over
- **Missing pieces:** Side-by-side or overlay 'predicted vs actual' comparison mode (two runs, or a ghost track) — no such concept; Chaos-tool adapters (Gremlin/Chaos Mesh/LitmusChaos experiment definitions → spec + storyboard); Per-branch speed() in Mode B so the actual replay can be paced like the briefing (documented no-op in live mode); A steady-state/hypothesis annotation channel that is more structured than free-text captions
- **Tools used for this today:** Gremlin's own scenario UI, Chaos Mesh / LitmusChaos dashboards, hand-drawn Excalidraw/Miro diagrams in game-day docs, slide decks

## 5. Runbook and onboarding embed: 'what happens when a request/deploy flows through here'

- **Coverage today:** `good` · **Demand:** high · **Effort:** small
- **What the user is doing:** Embed a playable, self-narrating diagram of a critical path directly in the runbook, service catalog entry, or onboarding doc, so a new on-call can press play and watch the flow rather than read twelve paragraphs of prose that drifted from reality two quarters ago.
- **Example scenario:** The 'payments on-call' runbook page embeds a graph of the payment path with a storyboard: chapter 1 walks the happy path token, chapter 2 fails the provider and shows which alerts fire and which dashboards to open, chapter 3 expands the 'ledger' container to reveal its internal steps. It ships as one <script> tag in a Backstage TechDocs page, or as a packed single HTML file in the wiki.
- **Required features:** Zero-build single-script CDN embed and smv-pack self-contained HTML; storyboard chapters + labels + g.cues() as a table of contents; container expand/collapse for progressive disclosure; tapToggle interaction and keyboard/ARIA tree for accessible docs; theme auto/light/dark to match the host wiki; <50KB gzip budget (survives strict docs CSPs and slow pages)
- **Missing pieces:** Deep-linkable chapter URLs (#chapter=failover) so a page can be linked at a specific beat; Tooltip system for per-node detail (owner, SLO, dashboard link) — explicitly absent; consumers must write a preset; Clickable nodes with a documented click/select event to open the linked dashboard or catalog entry (no selection API, no context menu; only container tap-to-toggle); Generation from a service catalog (Backstage catalog-info.yaml / OpenTelemetry service graph metrics) so the diagram cannot drift from reality; Content-Security-Policy guidance for the injected <style data-smv-styles> block in locked-down wikis
- **Tools used for this today:** Mermaid in Markdown docs, Backstage system/component diagrams, static PNG/Excalidraw diagrams in Confluence, Loom walkthrough videos

## 6. Queue and backpressure visualization for capacity reviews

- **Coverage today:** `poor` · **Demand:** medium · **Effort:** large
- **What the user is doing:** Show where work piles up: occupancy on a node as depth in a queue, tokens draining at the rate a consumer can actually handle, and the moment a bounded stage starts shedding. Used in capacity planning and pre-Black-Friday readiness reviews.
- **Example scenario:** An ingest pipeline: Kafka topic → enrichment workers → sink. The reviewer sets the sink's duration to its measured per-message service time, spawns 500 tokens into the topic node, and the occupancy badge on enrichment climbs while the sink stays saturated — making the bottleneck argument visually instead of with a spreadsheet.
- **Required features:** spawn(id,n) and occupancy badges; per-node duration as service time; per-branch speed() to model relative throughput (Mode A); drop events when a join fires and extras arrive
- **Missing pieces:** A rate/flow model at all: tokens are discrete and individually animated, so hundreds of in-flight tokens are neither performant nor legible — no aggregated 'flow' rendering (edge width or animated dash flux proportional to rate); Bounded queue capacity with shed/drop-on-full semantics (drop exists only as a join-arrival artifact, not as capacity overflow); Per-edge numeric throughput label updating from live events; Server/worker concurrency model (a node processes k tokens at once) — nodes have occupancy but no documented service-rate or concurrency limit; Token pulses are not culling-aware, which bites exactly at the high token counts this use case implies; No histogram/utilization side-channel (this is a chart, but reviews need it adjacent to the graph)
- **Tools used for this today:** spreadsheets and queueing-theory calculators, Grafana dashboards with queue-depth panels, SimPy/AnyLogic simulations, Temporal/Argo UI worker views

## 7. Customer-facing degradation explainer on the status page

- **Coverage today:** `good` · **Demand:** low · **Effort:** small
- **What the user is doing:** On a public status page or a customer-comms email, embed a small animated diagram showing which part of the system was affected and how requests were rerouted — replacing the paragraph of jargon that customers do not parse.
- **Example scenario:** A regional outage: the status page incident entry embeds a 40KB self-contained graph showing traffic shifting from eu-west-1 to eu-central-1, with three captions and a 12-second loop. No CDN dependency, no framework, theme matches the status page, and it degrades to an accessible table for screen readers.
- **Required features:** smv-pack single-file offline HTML / small IIFE embed; storyboard with captions and camera; theming via --smv-* to match brand; a11y table fallback and ARIA tree; exportSVG/exportPNG for the email and the tweet
- **Missing pieces:** Autoplay-once-then-hold and loop-forever playback modes for an unattended embed (transport assumes a driver); Intersection-observer 'play when scrolled into view' behavior; exportPNG being browser-only — no Node/CI path to generate the social-card image in the incident pipeline (would need smv-record --png-dir plus chromium); A deliberately simplified 'customer' abstraction level: condense() exists but there is no saved multi-level view (engineer view vs customer view of the same spec); No animated GIF/WebP output (mp4 only) for embedding in email/Slack
- **Tools used for this today:** static illustrations from a designer, Statuspage.io text updates, Excalidraw exports, Loom clips

## 8. Deploy / rollout pipeline live view (progressive delivery)

- **Coverage today:** `good` · **Demand:** high · **Effort:** medium
- **What the user is doing:** Watch a canary or multi-region rollout as it happens: stage nodes going active, analysis gates passing or failing, automatic rollback firing as a back edge. This is the library's home turf, pointed at delivery rather than data pipelines.
- **Example scenario:** An Argo Rollouts canary: 5% → analysis → 25% → analysis → 100%, where the second analysis gate fails on error-rate SLO and a loop edge back to 'rollback' ticks. The team's deploy dashboard embeds the graph fed live from the rollout controller's events, and the same log replays afterwards in the change-review.
- **Required features:** Mode B live event log with start/finish/fail; loop/back edges as first-class (rollback, retry) with consistent-side arcs; containers for per-region stage groups with expand/collapse; runstatus events for integrating with the surrounding page; transport bar with scrub
- **Missing pieces:** Adapters/examples for the obvious event sources (Argo Rollouts/Workflows, GitHub Actions job graph, Tekton, Spinnaker) — spec must be hand-built; runstatus event payload does not include 'failed' per the typed event map, though failure is a first-class state elsewhere — an integration-visible inconsistency; Elapsed-time-per-node readout in Mode B (Mode A has timeOf; live mode has no per-node observed-duration surface); Progress within a long-running node from external percent-complete (occupancy is discrete; a node at '60% of a 20-minute rollout' cannot be expressed); Attaching a link/artifact per node (job URL, logs) — no per-node action affordance
- **Tools used for this today:** Argo Workflows / Argo Rollouts UI, GitHub Actions workflow graph, Spinnaker pipeline view, Tekton dashboard, Jenkins Blue Ocean (from memory, deprecated)

## 9. Architecture-change review: animated before/after of a dependency graph

- **Coverage today:** `good` · **Demand:** medium · **Effort:** small
- **What the user is doing:** For an RFC or migration review, animate the transition from today's topology to the proposed one — services merging behind a gateway, a synchronous call becoming a queue, a shared database splitting — so reviewers see the delta rather than diffing two static PNGs.
- **Example scenario:** A strangler-fig migration RFC: the storyboard starts on the monolith, split() breaks it into three services with the converge/diverge choreography, condense() merges three legacy cron jobs into one scheduler, and captions state what each move buys. Recorded as a two-minute mp4 embedded in the RFC and replayed in the architecture-review meeting.
- **Required features:** condense(ids,newNode) / split(id,{nodes,edges}) with staged choreography and convexity guard; diff-based auto-animation for arbitrary add/remove/update; storyboard snapshotting so reviewers can scrub backward through structural changes; componentOrder to keep unrelated subsystems in stable slots across the change; camera + caption + props; smv-record for the meeting artifact
- **Missing pieces:** A spec-diff helper: given specA and specB, generate the storyboard op array (today the author hand-writes every add/remove/update step); Import from existing sources of truth (Terraform graph, Kubernetes manifests, DOT/GraphML) — no data-source adapters; Container rectangle overlap residual (60/400 random cluster forests still violate) shows up as visual sloppiness precisely in the multi-container architecture diagrams this use case produces; Parallel edges between adjacent ranks render coincident — two distinct dependencies between the same pair of services look like one, which is semantically wrong in an architecture review; Edge-level change emphasis (added/removed/changed edge styling) as a first-class channel rather than hand-authored props
- **Tools used for this today:** Excalidraw / Miro before-after boards, Mermaid diagrams in RFCs, Structurizr / C4 model tooling, Lucidchart, static PNGs in Google Docs

## Cross-cutting needs from this perspective

- Lift the Mode A-only restriction on storyboards, director ops and smv-record. Every high-demand SRE use case (postmortem replay, live wallboard, rollout review, chaos after-action) has its truth in a REAL event log, i.e. Mode B, and is today locked out of camera/highlight/caption scripting and out of video export entirely. A narrower, tractable version: allow storyboard camera/highlight/caption/props ops over a Mode B run that is being replayed from a FINITE, already-collected log (which is deterministic and priceable), while keeping the refusal for a live-attached, still-growing frontier.
- Data-source adapters. The library has a pluggable layout-solver seam but zero import seam: every use case above starts with 'hand-build the {nodes,edges} spec'. Named, concrete targets in rough priority order: OpenTelemetry trace JSON (OTLP/Jaeger) → spec + durations; Prometheus/Alertmanager alert-state transitions → Mode B log; Kubernetes events + Argo Rollouts/Workflows status → live log; Backstage catalog-info.yaml / service dependency graph → spec.
- A continuous metric channel distinct from discrete tokens. Nodes and edges need a numeric value (error rate, RPS, saturation, latency) that maps to color/width/label and updates from live events, rendered as aggregate flow rather than N individual animated tokens. Concretely: per-edge throughput label updating from live events, edge width bound to a value, and a node 'degraded' status between done and failed. This is the single largest structural gap between 'pipeline narration' and 'observability'.
- A time axis. A Gantt/temporal layout mode (x = time, sweeping playhead) plus a wall-clock readout bound to the view clock, and wall-clock-labelled chapters. Traces, incident timelines and rollouts are all fundamentally time-extent data; the current layered layout shows ordering and the ticker shows elapsed ms, but neither shows 'this span occupied 03:14:02–03:14:19'.
- Edge-reachability queries. Blast radius, critical path, downstream-of-this-failure and impact scoring all need path-finding over edges; g.descendants() only walks container nesting and there are no graph-algorithm queries. Minimally: reachableFrom(id,{direction}) and a path/critical-path helper feeding the existing highlight/dim spotlight.
- Per-node affordances for operational context: a documented node-click/select event, a tooltip or detail-panel hook, and a link/artifact field — so a node can open its dashboard, job log or catalog entry. Currently there is no selection API, no context menu and no tooltip system, and every use case above wants at least one of them.
- Unattended-embed playback semantics: autoplay-on-visible (intersection observer), play-once-and-hold, loop, and deep-linkable chapter URLs. Runbooks, status pages and catalog entries embed the graph in a page nobody is going to press play on.
- Long-running-session hygiene for Mode B: log windowing/compaction or truncate-before(t), and culling-aware token pulses (an open M3 follow-up). A wallboard graph fed by a live stream for days currently accumulates an unbounded log and can draw pulses for culled nodes.
