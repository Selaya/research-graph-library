# Use-case pass: Product management and solutions engineering
> Part of the [feature-gap research corpus](../README.md) · 2026-09-05 · opus agent adopting the perspective of a product manager or solutions engineer (interactive product demos, roadmap dependency maps, customer journey flows, embedded live status pages, before/after automation pitches).

**Coverage tally:** 9 use-cases: 3 good, 5 partial, 1 poor.

## The agent's stance

Product manager / solutions engineer: I ship artifacts that persuade or orient an audience — interactive product demos, before/after automation pitches, roadmap dependency maps, customer journey flows, embedded live status pages, incident replays for exec review. My constraints are that the thing must be embeddable anywhere (marketing site, docs, Notion-ish page, a single .html emailed to a prospect), must be authorable as data (so it can be generated per-customer or from a CRM/config), and must narrate over time rather than just render a static box-and-arrow picture. sparkle-motion-visualizer is unusually well aimed at me: the storyboard/director/caption/camera layer plus smv-record/smv-pack is essentially "make a narrated explainer without After Effects", and the token engine gives motion that means something (a step is running, this branch retried, this join is waiting) rather than decorative animation. Where it is weak for me is everything downstream of "the picture animated": no tooltips or per-node click handlers means it cannot be interactive product-demo furniture; no temporal/Gantt layout and no swimlanes means it cannot do roadmaps; no data-source adapters and no per-edge live numeric labels means the live mode needs a lot of glue before it is a status page; and the hard Mode A / Mode B split means the two things I most want to combine — a scripted narration and real event data — cannot be combined at all. NOTE ON SOURCING: I read README.md, docs/EMBED.md and the demo/ pages in-repo; all claims about competing tools and about market demand are from memory (no web verification in this pass), and I assert no version numbers for any third-party tool.

## 1. Embedded interactive product demo on a marketing or docs page

- **Coverage today:** `partial` · **Demand:** high · **Effort:** medium
- **What the user is doing:** A self-running, looping 'here is what our product does to your data' animation embedded directly on a landing page or docs page, where the visitor can scrub, pause, and poke at steps instead of watching a video. The PM wants it to autoplay when scrolled into view, tell a 30-second story with captions, and let a curious visitor click a step for detail — all without a video player, a build step, or a marketing-eng ticket.
- **Example scenario:** An ETL SaaS puts a 480px-tall block on its /product/pipelines page: a token flows Ingest -> Clean (container, expands to show Dedupe/Validate) -> Enrich -> Warehouse, with captions naming each stage; a visitor clicks 'Enrich' and a side panel explains the transform library. The whole thing is one <script src> tag from a CDN plus a spec object, pasted by a PM into the CMS.
- **Required features:** Storyboard op array with captions and camera moves; Token run with declared durations (Mode A); Transport bar with scrub for visitor control; Single <script> CDN IIFE embed, no build step; Theme auto (light/dark) to match host page; Small bundle so marketing page weight is acceptable; Per-node click handler to open detail panels; Autoplay when scrolled into view; loop the story
- **Missing pieces:** Public per-node/per-edge click (and hover) event on the graph event bus — today g.on() exposes commit/add/remove/update/expand/collapse/condense/split/runstatus, and tap-to-toggle is hardcoded to containers only, so a non-container node click is unreachable without reaching past the public API; Built-in tooltip/popover layer bound to node.data (documented as absent; must be hand-built as a preset); IntersectionObserver-driven autoplay/pause hook ('play when >=50% visible, pause when scrolled away'); Storyboard loop/repeat mode (play to end, reset to step 0, replay) as a mount or storyboard option; Deep-link support: read a chapter label from location.hash and seek the storyboard there, and write it back as the story advances; Anchor/hyperlink affordance on a node (href + accessible link semantics) for 'learn more' targets
- **Tools used for this today:** Recorded product videos (Loom, Screen Studio) embedded via YouTube/Wistia, Interactive demo platforms (Navattic, Storylane, Arcade, Reprise), Hand-built React Flow / D3 animations commissioned from frontend eng, Lottie/Rive animations exported from After Effects, Static Mermaid or Figma diagrams with no motion

## 2. Before/after automation pitch (manual workflow -> automated workflow, with time saved)

- **Coverage today:** `good` · **Demand:** high · **Effort:** small
- **What the user is doing:** The single highest-value thing this library already does: show today's painful multi-step manual process, then collapse the manual steps into one automated step on screen, with the duration total dropping from hours to seconds. Used by PMs in internal funding pitches and by solutions engineers in ROI conversations, where the persuasion comes from watching the collapse happen rather than reading two static diagrams.
- **Example scenario:** A solutions engineer pitching a release-automation product shows the customer's current SDLC: 'Manual QA sign-off', 'Manual changelog', 'Manual deploy checklist' (7h 20m total), then a storyboard step condenses all three into 'Automated release gate' with the odometer running 7h20m -> 40s and a caption reading 'this is the 6 hours per release you get back'.
- **Required features:** condense() with staged highlight -> converge -> reveal choreography; Pipeline preset: duration chips, sum/max rollups, odometer + delta badge, total-duration bar; Duration grammar on node.data.duration; Storyboard with per-step pacing and captions; Camera framing on the condensing group; Export a still for a slide deck; Cost/dollar rollup alongside time
- **Missing pieces:** A generic numeric rollup grammar beyond duration — e.g. data.cost / data.headcount summed and formatted with a unit, so the odometer can show $/run or FTE-hours, not only time (durationAgg is time-specific); Side-by-side synchronized dual-graph mode (before graph and after graph mounted as two instances sharing one clock/scrub position) for slide-style comparison; Deck-shaped still export: exportPNG at a fixed aspect ratio / slide-safe padding preset (today scale only, framing comes from live viewport); exportSVG/exportPNG are ESM-only and absent from the IIFE bundle, so the copy-paste embed a PM uses cannot produce the slide image without a second module script
- **Tools used for this today:** Two static slides in PowerPoint/Google Slides with arrows, Lucidchart / Miro before-after boards, Figma prototype with a click transition, Custom ROI spreadsheets with no visual

## 3. Per-prospect solution walkthrough packed as a single emailable HTML file

- **Coverage today:** `good` · **Demand:** medium · **Effort:** small
- **What the user is doing:** A solutions engineer generates a walkthrough tailored to one prospect's actual systems (their CRM, their warehouse, their ticketing tool named on the nodes) from a config/template, packs it to one self-contained .html, and emails it or drops it in the deal room. It must open from file:// with no CDN, no network, and no install, because enterprise security will block anything else.
- **Example scenario:** After a discovery call, the SE fills a YAML of the prospect's stack, a script renders it into a spec + storyboard, runs smv-pack, and sends 'acme-integration-walkthrough.html' (one file, works offline) to the buying committee, who forward it internally to three people who never joined a call.
- **Required features:** smv-pack: IIFE + spec + storyboard bundled into one offline .html; Spec is plain JSON so it can be generated from a template; Storyboard is a serializable JSON array (also generatable); Theming via CSS custom properties for prospect-ish branding; Company logos/icons on nodes; Knowing whether the prospect opened it
- **Missing pieces:** Spec templating/variable substitution in smv-pack (e.g. --vars vars.json applied to {{placeholders}} in the spec), so an SE does not need a bespoke build script per deal; Image/icon content inside a node (no shapes beyond rounded rects, no <image> slot documented) — prospect and vendor logos cannot be placed on steps; A title/cover frame and a footer/attribution slot in the packed HTML output (smv-pack emits the graph, not a document); Optional analytics/engagement callback in the packed file (a documented hook like onStoryComplete / onChapter that a beacon can hang off) — today there is no view-tracking seam and the file is deliberately offline; Brand preset beyond the --smv-* token list (e.g. a single accent+font pair applied through smv-pack --brand)
- **Tools used for this today:** PDF one-pagers built in Figma or Canva, Navattic/Storylane per-prospect demo links, A Loom recorded per prospect, Slide decks emailed as .pptx

## 4. Customer-facing embedded live status / job progress page

- **Coverage today:** `partial` · **Demand:** high · **Effort:** large
- **What the user is doing:** Instead of a table of job statuses, the customer sees their actual pipeline with tokens moving through it in real time, driven by the vendor's real event stream — plus the ability to scrub backward through the last hour to see where things slowed. This is the natural home for Mode B, but it is the use case with the widest gap between the engine and a shippable page.
- **Example scenario:** A data-integration vendor embeds the graph in its customer console: an SSE stream of {node, event, ts} feeds run.start()/finish()/fail(); the customer watches 'Sync: Salesforce' go active, sees 'Transform' fail red with a reason, scrubs back 20 minutes to see the retry loop tick 3 of 5, and sees per-edge counts like '1,204 records/min' on the live edges.
- **Required features:** Mode B live event log replay with append-only start/finish/fail/spawn; Frontier vs view two-clock model with follow() and time-travel seek; Reconnect/persistence via run.log() and run.reset({log}); Failure as a first-class sticky status; Per-edge throughput numbers updating from live events; A transport that ingests SSE/WebSocket; Relative-time readout and tooltips
- **Missing pieces:** A data-source transport helper: documented adapter that maps an SSE/WebSocket/polling JSON stream onto run.start/finish/fail/spawn with reconnect + backfill from run.log(), so the consumer is not writing that glue per deployment; Per-edge live numeric label bound to run state (records/min, count, latency) that re-renders on run events — edge labels today are static free text and edge weight is a collapse-aggregation count, not a data-bound live metric; Node-level live metric badge from the run bus (queue depth, throughput) distinct from occupancy pips; Wall-clock/relative time readout component ('started 3m ago', 'live' vs 'viewing 14:02:11') — the two clocks exist as numbers, no UI surfaces them; Built-in legend/key component explaining status colors to an end customer who has no context; Tooltip on hover with the node's last event, reason string, and timestamps; Storyboard cannot drive a live run at all, so a 'guided tour of your live pipeline' overlay is out of scope by design
- **Tools used for this today:** Statuspage / Instatus / Better Stack component lists, Grafana or Datadog dashboards embedded via iframe, Airflow/Dagster/Temporal built-in run graphs (vendor-internal, not embeddable in a customer console), Hand-rolled React Flow status views

## 5. Roadmap dependency map that plays forward quarter by quarter

- **Coverage today:** `poor` · **Demand:** high · **Effort:** large
- **What the user is doing:** A PM shows a roadmap not as a Gantt bar chart but as a dependency graph that animates: Q1 items land, Q2 items unblock and light up, the critical path is spotlighted, and a caption explains what slips if a dependency slips. The persuasive move is watching downstream work unblock, which no static roadmap conveys.
- **Example scenario:** In a quarterly planning review, the PM plays a storyboard: 'Auth rewrite' completes, which unblocks 'SSO' and 'Audit log'; camera pans to the SSO cluster; a highlight spotlights the critical path to the compliance deadline; the next step removes 'Auth rewrite' resourcing and the audience sees three downstream items go grey.
- **Required features:** Dependency DAG with containers per team/epic; Storyboard with camera, spotlight highlight, captions; Progressive reveal of nodes over storyboard steps; Time axis (x = calendar) with quarter markers; Swimlanes / rank pinning by team or quarter; Critical-path computation; Manual nudge of node positions during a live review
- **Missing pieces:** Temporal/Gantt layout mode (x = time, sweeping scrubber) — explicitly skipped in the plan and never built; this is the single blocking gap for roadmaps; Swimlane / lane assignment: pin nodes to a named row or column band (by team, by quarter) with lane headers — componentOrder pins disconnected component slots, not lanes across a connected graph; Rank pinning: force a node to a specific rank/date column regardless of longest-path ranking; Date grammar on nodes (start/end ISO dates, or 'Q3 2026') distinct from the duration grammar, plus axis tick rendering for it; Critical-path / longest-path query in the public API (querying is predicate/partial-match only, no path-finding); Node dragging so a PM can nudge one box during a live review without editing the spec
- **Tools used for this today:** Jira Advanced Roadmaps / Aha! / Productboard timelines, Miro or FigJam dependency boards maintained by hand, Monday.com / Asana timeline views, Static Mermaid gantt in Confluence

## 6. Customer journey / conversion funnel flow with drop-off volumes

- **Coverage today:** `partial` · **Demand:** medium · **Effort:** medium
- **What the user is doing:** A growth PM shows the actual user journey as a flow where edge thickness is volume and drop-off branches are visible, then animates a cohort moving through it so the audience feels where users are lost. Distinct from a bar-chart funnel because journeys branch, loop (retry a failed payment), and rejoin.
- **Example scenario:** Signup -> Email verify (18% drop to 'Abandoned') -> Onboarding checklist (container: 4 steps) -> First value; a retry loop from 'Payment failed' back to 'Payment' ticks 2 of 3; the presenter plays 10,000 users through it and the 'Abandoned' node's occupancy badge climbs to 1,800 while the caption reads 'this is the 18% we are chasing this quarter'.
- **Required features:** Branching flow with loops as first-class (retry payment); Containers for multi-step stages; Token occupancy badges and fan-out; Edge width proportional to volume; Numeric edge labels with formatting (counts, %); Per-step conversion % annotation; Hover detail on a step
- **Missing pieces:** Data-bound edge width scale: map a numeric field to stroke width with a documented scale (weight >1 renders heavier + a badge, but it is a collapse-aggregation count, not a continuous volume encoding); Formatted numeric edge labels (thousands separators, percentages, units) as a first-class edge property rather than free-text label strings the caller pre-formats; Conversion/percentage annotation derived from source vs target volumes (edge value / sum of source out-edge values) rendered on the edge or node; Proportional-thickness (Sankey-like) rendering mode, or an explicit statement that it is out of scope — today parallel edges between adjacent ranks even render coincident; Tooltip on a node/edge showing the underlying cohort numbers; Terminal/exit node convention (drop-off sink) with distinct styling in the preset
- **Tools used for this today:** Amplitude / Mixpanel / Heap journey and funnel charts, SankeyMATIC or D3 sankey one-offs, Figma journey maps drawn by designers, Google Analytics path exploration

## 7. Incident replay for a postmortem or exec review

- **Coverage today:** `partial` · **Demand:** medium · **Effort:** medium
- **What the user is doing:** Take the real event log from an incident and replay it as a moving picture: where the first failure landed, which retries fired, which downstream branches stalled waiting on a join, and how long each stall lasted — with scrubbing so a reviewer can rewind to the 03:14 moment and ask 'what was waiting here?'.
- **Example scenario:** A postmortem doc embeds a packed HTML replay of last Tuesday's outage: 'Payment auth' fails at 03:12 with reason 'upstream 503', the retry loop ticks 5 of 5, 'Order confirm' sits waiting on an AND-join for 41 minutes; the incident commander scrubs back and forth during the review to show that the alert fired 9 minutes after the first fail.
- **Required features:** Mode B append-only log replay with time-travel seek; fail() with a reason string carried as an event; Join arrival pips and loop iteration badges; run.log()/run.reset() round-trip so a log can be saved and re-embedded; Import from real log/trace formats; Wall-clock timestamps on the transport; Narration over the replay
- **Missing pieces:** Log import adapter: a documented mapper from a common shape (OpenTelemetry spans, or a generic {ts, id, phase} JSONL) into the Mode B event log — today the caller writes the mapping and the spec by hand; Wall-clock time display and absolute timestamp seeking (seek(ms) is relative to run start; incidents are discussed in UTC clock time); Storyboards cannot drive a Mode B run (enforced in the library, in smv-record and in smv-fit), so a narrated/captioned incident walkthrough of real data is impossible without re-authoring the incident as a fake Mode A simulation; Pinned annotations at timestamps ('alert fired here') that persist through scrub — captions exist only as storyboard ops, i.e. Mode A only; Static failure summary export (which nodes failed, with reasons and durations) as a table for pasting into the postmortem doc
- **Tools used for this today:** Datadog / Honeycomb trace waterfalls, Jeli / incident.io timeline features, Manually written postmortem timelines in Google Docs, Screen recordings of a dashboard being scrubbed

## 8. Narrated explainer video for a launch, release notes, or conference talk

- **Coverage today:** `good` · **Demand:** medium · **Effort:** medium
- **What the user is doing:** Produce an actual mp4 of the product story — camera moves, spotlights, captions, tokens flowing — recorded deterministically from the same storyboard JSON the live embed uses, with the holds stretched to fit a recorded voice-over. This replaces a motion-designer round trip for the class of video that is 'diagram plus narration'.
- **Example scenario:** For a launch, the PM writes the storyboard once, records a 90-second VO, runs smv-fit against the VO marks so each caption lands on the spoken sentence, then smv-record renders the mp4 and a .srt; the same storyboard JSON also ships as the interactive embed on the launch blog post.
- **Required features:** smv-record: deterministic frame-by-frame headless render to mp4/PNG sequence; smv-fit: stretch wait steps to voice-over marks; g.cues() + --cues to .srt/.txt chapters; Manual ticker + forced full motion for byte-identical output; --font pinning for cross-machine stability; Audio muxed into the output; Social/vertical aspect presets; Title and end cards
- **Missing pieces:** Audio muxing: an --audio flag that muxes the VO track into the mp4 (ffmpeg is already a dependency for --out, so the pipe exists but the caller does it by hand); Aspect/format presets (--preset 16:9 / 9:16 / 1:1 with safe margins) for LinkedIn/YouTube Shorts versus a talk deck — today width/height/scale are raw numbers; Transparent-background / alpha output (webm or PNG sequence with alpha) so the graph can be composited over a slide or screen recording; Title card and end card as storyboard-level constructs (a full-frame caption/branding step), not just the bottom/top caption overlay; smv-fit refuses any storyboard containing run.play, which is exactly the step type a token-flow explainer is built around — the VO-fitting workflow and the token-run workflow are mutually exclusive today; Chromium + ffmpeg on disk is a real prerequisite for a PM's laptop; there is no hosted/containerized render path documented
- **Tools used for this today:** After Effects / Rive with a motion designer, Screen Studio or Loom recording of a live prototype, Canva / Visme animated diagram templates, Keynote Magic Move exported to video

## 9. Architecture / integration explainer embedded in developer docs

- **Coverage today:** `partial` · **Demand:** medium · **Effort:** medium
- **What the user is doing:** The 'how our integration actually works' diagram in the docs, but animated: a request enters, fans out to two services, one path retries, both join, a response leaves. Developers scrub it instead of parsing a static PNG that is two releases out of date, and the diagram is checked into the docs repo as JSON so it can be reviewed in a PR.
- **Example scenario:** An API vendor's /docs/webhooks page embeds a graph: 'Your event' -> 'Signature verify' -> fan-out to 'Delivery attempt' and 'Audit log'; the delivery edge is a retry loop with maxIterations 5; a caption explains exponential backoff; the spec JSON lives next to the MDX and is diffed in PRs when the retry policy changes.
- **Required features:** Spec + storyboard as reviewable JSON in the repo; Loop edges with iteration badges for retry policy; Containers to hide/reveal internal detail; Light/dark theme following the docs site; Accessible fallback for a docs-site a11y audit; Service/vendor icons on nodes; Links from a node into the relevant API reference; Tooltips for parameter detail
- **Missing pieces:** Node icon/image slot (SVG symbol or data-URI image) — only rounded rects are documented, so service logos and protocol glyphs cannot be shown; Node hyperlink/href with correct link semantics for jumping into the API reference; Tooltip system for parameter or payload detail on hover (documented as absent, must be built as a preset); A stated WCAG conformance level or third-party audit result — enterprise docs teams ask for this in procurement and the library documents mechanisms only; A docs-framework integration path: there is no React/Vue/Svelte wrapper, so Docusaurus/Nextra/Mintlify authors must write an imperative mount inside an MDX escape hatch; Node shape vocabulary (queue, datastore, external system) that architecture readers expect to distinguish component kinds
- **Tools used for this today:** Mermaid (native in GitHub, Docusaurus, Notion), Static PNG/SVG exported from Excalidraw or Figma, D2 / Structurizr / PlantUML for architecture-as-code, Kroki-rendered diagrams in docs pipelines

## Cross-cutting needs from this perspective

- Node/edge interaction events on the public bus (click, hover-enter/leave with the node id and its data payload). Six of these use cases stall at the same wall: the visual is finished but nothing can hang off a click. tapToggle exists but only for containers, and the GraphEventMap has no pointer events at all.
- A tooltip/popover layer bound to node.data and edge.data, shipped as a preset. It is named as a known limit in three inventory categories and it is the single most-requested affordance for demos, funnels, status pages, live replays, and docs diagrams alike.
- Data-bound numeric encodings that are not durations: a documented way to map a number on a node or edge (volume, cost, throughput, count) to a visual channel (edge width, badge, label) with unit formatting. Today numbers are either the duration grammar or the collapse-aggregation weight; funnels, ROI pitches, and live status pages each need a general version of the same thing.
- Break the Mode A / Mode B wall for narration. Storyboards, smv-record and smv-fit are all Mode A only, which means every use case built on real data (live status, incident replay) loses captions, camera and spotlight — precisely the features that make the library persuasive. Even a read-only subset (caption + camera + highlight ops usable over a live run, with no run.play step) would unlock two use cases.
- Data-source and data-format adapters. The library's spec is its own JSON shape only, and Mode B is fed by hand-written glue. A documented SSE/WebSocket live transport and at least one log/trace importer (plus a spec templating pass in smv-pack) is what moves this from 'a library an engineer wires up' to 'a thing a solutions engineer generates per account'.
- Layout affordances for time and grouping: temporal/Gantt mode, swimlanes, and explicit rank pinning. Explicitly skipped in the plan, but roadmaps, journey maps with stage bands, and incident timelines all want the same underlying capability — put this node in that row/column because I said so, not because longest-path ranking says so.
- Presentation-output polish around the existing recorder: audio muxing, aspect presets, alpha output, and title/end cards. The hard part (deterministic frame-identical rendering) is already done; what is missing is the last mile that decides whether a PM ships the mp4 or re-makes it in Keynote.
- Framework wrappers and an embed story for docs/CMS platforms. No React/Vue/Svelte component exists, and the audiences in every one of these use cases live inside Next.js marketing sites, Docusaurus/Mintlify docs, or a React app console. The imperative mount is correct as the core, but the absence of a thin official wrapper is a real adoption tax.
- A legend/key component and a stated accessibility conformance level. Both are procurement-and-comprehension needs rather than engineering needs, and both block customer-facing embeds (status pages, docs) more than internal pitches.
