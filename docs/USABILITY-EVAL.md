# Usability evaluation — sparkle-motion-visualizer

*End-to-end usability evaluation across the library's core use-cases, 2026-09-04.*

**How this was produced.** Eight independent evaluators each took one core use-case end to
end, working hands-on against this checkout: following the docs the way a newcomer would,
verifying every doc claim against source and tests, and running scratch scripts against the
real modules (the unit-testable surface runs under Node with the repo's own DOM stub; 554/554
unit tests passed throughout). Each use-case was scored on six dimensions, and every reported
issue was then passed to an independent skeptic agent instructed to *refute* it against the
code. **All 43 issues survived verification (0 refuted, 0 unverifiable)** — several were
independently re-reproduced, including a fresh benchmark of the live-mode replay cost. Only
verified findings appear below.

**Scoring.** 1 = major usability barrier · 3 = workable with friction · 5 = excellent.
Dimensions: **learnability** (time-to-first-success from docs alone), **API ergonomics**
(naming, defaults, footguns), **documentation** (accuracy + completeness), **error handling**
(loud vs. silent failure), **robustness** (does the documented path actually work),
**extensibility** (adaptable without forking).

## What's working

- **The quickstart is real.** The README's top-of-file example was extracted verbatim and ran
  to completion (mount → pipeline preset → `g.run().play()` → timeline done) with zero
  source-reading. Defaults are sensible; a bad `mount()` call throws before touching any state.
- **Structural error handling is exemplary.** Every graph-mutation misuse exercised (bad
  selectors, duplicate/missing ids, dangling edges, non-convex condense, split-container…)
  throws a synchronous, consistently-coded `GraphError` with no partial state. This is the
  standard the rest of the library should be held to.
- **The three CLIs are unusually good.** `smv-pack`/`smv-record`/`smv-fit` share one idiom and
  fail fast with precise, actionable messages on every misuse path tried (bad JSON, missing
  ffmpeg, corrupt fonts, unknown labels, too-tight voice-over gaps). Chapter re-renders were
  verified byte-identical via sha256; the docs' worked examples matched character-for-character.
- **The extension architecture works first-try.** A from-scratch layout solver, the dagre
  adapter, and a hand-rolled custom preset were each built against nothing but the public API
  and documented contracts, and all worked on the first attempt.
- **The engine is honest.** Docs are *accurate* nearly everywhere they exist; the run engine's
  join/retry/seek semantics, live-mode out-of-order healing, storyboard backward scrub, and
  focus re-homing on structural commits all behave exactly as claimed.

## Cross-cutting themes

The 43 verified issues cluster into five themes. Fixing by theme will move every use-case at
once, where fixing issue-by-issue would not.

### 1. The documentation stops where the library gets interesting (docs: 2.5/5 — weakest dimension)

Docs are accurate but shallow: complete for `mount()` and the CLIs, then increasingly
skeletal for the layers underneath. Mode A — the flagship `g.run()` — has **one README
bullet** and no reference for the returned run handle's ~14 methods or its two event
vocabularies; Mode B's section omits exactly the primitives a real integrator needs
(`opts.log` seeding, `reset()`/`options()` reconnect, partial `finish(id,{n})`); the ~17
`GraphError` codes, the `g.on('*')` wildcard, the storyboard step format, `g.timeline()`'s
shape, and the fully-supported custom-preset pattern are all undocumented outside source. The
accurate content mostly *already exists* in `types/index.d.ts` and `docs/INTERNALS.md` — it
needs porting into user-facing docs, not writing from scratch.

### 2. Two error-handling philosophies coexist, and users can't predict which they'll get

Structural mutations throw loudly; nearly everything else fails silently: unparseable
durations (`"45mins"`) silently get the same 600ms default as *no* duration; live-mode
`start/finish/spawn` swallow unknown ids; `camera`/`highlight` ignore bad ids, wrong key
names, and bad variants; `style(fn)` silently drops the same non-`--smv-*` keys that
`props()` throws on; a typo'd op inside a storyboard `batch` bypasses the validator that
catches it at top level. Each inconsistency is individually small; together they mean a
competent integrator cannot form a reliable mental model of "if I got it wrong, will I be
told?" **Recommendation: adopt one library-wide rule** (throw on structural misuse, single
`console.warn` on presentational misuse — or a `strict: true` mount opt) and apply it to
every silent path listed in the per-use-case sections.

### 3. Documented features that don't do what the docs say (highest trust cost)

Five places where following the docs verbatim fails — each cheap to fix, each expensive to
leave (a user who hits one stops trusting every other doc claim):

| Break | Where |
|---|---|
| `smv-pack` recipe references `demo/spec.json`, which doesn't exist → ENOENT (README's variant uses a `spec.json` placeholder that also matches no committed file) | EMBED.md (+ README) |
| CDN pins disagree: `@0.1.0` (README) vs `@1` (EMBED.md, resolves to nothing published) | README vs EMBED.md |
| `split` is documented as a storyboard op and wired into pacing code, but missing from the op allowlist → throws | RECORDING.md/PLAN.md vs `storyboard.js` |
| `--smv-radius` documented + worked example, but `render.js` hardcodes `CORNER = 8` → no effect | THEMING.md |
| `presetPipeline(g)` "after the fact" decorates nothing until an unrelated mutation | README/types/INTERNALS.md |

A CI check that executes the docs' copy-paste recipes would prevent this class permanently.

### 4. A short list of genuine engine gaps

Not doc problems — behavior that will bite in production: live-mode replay cost grows
superlinearly (independently benchmarked: ~11ms at 1k events → ~7.6s at 40k, with full
replays on every scrub/mutation), directly undermining "replay a real event log as it
happens"; `finish()` before `start()` silently yields a phantom `done` node; negative
durations invert event ordering; `g.batch(fn)` is neither atomic nor async-safe;
`g.node(id)`/`g.edge(id)` return live mutable store references while all plural queries
clone; `g.run({})` silently destroys and replaces the current run; there is no failed/errored
step concept anywhere in a library whose stated purpose is real pipelines.

### 5. Extensibility is architecturally strong but under-productized

The seams are good — solver contract, event bus, `data` bags, preset boundary discipline —
but half of them are effectively private: no "write your own preset" guide, `preset-pipeline`
subpath untyped, the CLIs' well-tested pure functions (`fit`, `formatCues`, `buildHTML`)
unreachable from an npm install, `smv-record`'s chromium discovery hardcoded to this repo's
CI image with no documented fallback for external users, and no fail/error extension point in
the run engine.

## Prioritized roadmap

Quick wins first — the high-impact/small-effort set is disproportionately large because most
problems are doc/consistency gaps, not architecture.

**P0 — broken promises (all small, do immediately)**
1. Commit a `demo/spec.json` (or inline the spec in the recipe) so `smv-pack` docs run verbatim.
2. Unify the CDN version pin across README/EMBED.md; check it against `package.json` in CI.
3. Add `"split"` to the storyboard `OPS` allowlist (+ fluent builder + regression test).
4. Wire `--smv-radius` in `render.js` or correct THEMING.md.
5. Make `presetPipeline(g)` back-fill current state (one synchronous `onCommit()`), or document the caveat everywhere it's mentioned.

**P1 — silent-failure closure (small/medium)**
6. Warn on unparseable duration strings; reject/clamp negative durations (+ regression test).
7. Validate ids in live-mode `start/finish/spawn` (warn or coded error); fix or document the phantom-`done` case.
8. Recurse storyboard validation into `batch` children; validate director-op args (ids, key names, variants) at least with a `console.warn`.
9. Align `style(fn)` with `props()` on bad keys; guard `batch()` against async callbacks and document non-atomicity.
10. Clone `g.node()`/`g.edge()` to match the stated "read-only copies" contract.

**P2 — documentation debt (small each, highest aggregate leverage)**
11. Mode A reference section (run-handle methods, duration grammar, join values, event table) — mirror the existing Mode B section.
12. Live-mode integration guide: `opts.log`/`reset()` reconnect round-trip + a WebSocket wiring example.
13. `GraphError` code table in the README; export `GraphError` (or a documented type guard).
14. Document `run(opts)`' destructive-replace behavior (or split it into an explicit API).
15. "Writing your own preset" section; type + document the `preset-pipeline` subpath and `on('*', (type, payload))`.
16. A11y honesty pass: document the `a11y:false` keyboard trade-off, the container size fallback, and reading-order behavior for TB/BT.

**P3 — engine investments (medium/large)**
17. Fix live-mode replay's superlinear cost (heap/indexed structures) or ship a documented, enforced scale ceiling.
18. Wire the a11y table to live run status; add an `aria-live` region so the README's announcement claim holds; fix loop-badge contrast.
19. Mutation handles resolve with what actually changed (`{canceled, applied/ids}`), separating "graph changed" from "animation finished".
20. Add a failed/errored step primitive to the run engine (both modes).
21. Un-hardcode `smv-record`'s chromium discovery; document the `playwright install chromium` prerequisite; expose the CLI pure functions as subpath exports.

## Graph mutations & structural animation — 3.2/5

The mutation API is well-designed under the hood: every structural guard (dangling edges, dup ids, non-convex condense sets, split-container, no-entry/no-exit split) runs synchronously at the call site with a descriptive GraphError and code, so misuse fails loudly and never corrupts the graph via the documented mutation methods — verified against 75 passing store/split/condense/query tests plus 16 hands-on scratch scenarios I ran directly against src/index.js under a minimal DOM stub. What is documented in the README is accurate everywhere I could check it (split's edge-id scheme, expandAll/collapseAll's {ids} event, condense's convexity guard). The real friction is completeness and a handful of genuine footguns: g.node()/g.edge() return live, mutable store references (unlike the explicitly-cloned g.nodes()/g.children()), batch() is not atomic and silently misbehaves with an async callback, the resolved {canceled} value does not reliably tell you whether a structural change actually landed (especially for condense/split, where cancel() before vs. after the async 'converge' phase has opposite structural effects but an identical resolved value), and none of the ~17 GraphError codes are catalogued in any user-facing doc. None of this is a happy-path robustness problem — it is a documentation/discoverability and footgun problem that will cost a competent integrator real debugging time the first time they hit one of the named edge cases.

### Verified issues

**[HIGH] g.node(id)/g.edge(id) return live, mutable store references — unlike the cloned query sugar**

src/index.js:679-680 (`node(id) { return store.node(id); }`, `edge(id) { return store.edge(id); }`) return the actual object stored in the Map, while every method added by makeQuery() (g.nodes/g.edges/g.children/g.descendants/g.roots) explicitly clones via cloneItem() in src/query.js:5-7. Mutating the object returned by g.node(id) silently corrupts internal graph state with no validation (bypasses all the guards in store.update()), no re-render, and no event. README.md:165 only notes '(g.node(id) / g.edge(id) singular are unchanged.)' — read naturally as 'no behavior change,' not as a warning about this live-vs-clone asymmetry.

*Evidence:* Scratch script /tmp/claude-0/-home-user-research-graph-library/017f3504-c4d4-53c3-8ef8-da804b30567a/scratchpad/mutations/node-vs-nodes.mjs: `const single = g.node('a'); single.label = 'MUTATED-VIA-SINGULAR'; g.node('a').label` prints 'MUTATED-VIA-SINGULAR' (mutation persisted into the store); `g.node('a') === single` prints true (same object identity across calls, confirming it is not a fresh clone each time).

**[HIGH] The resolved {canceled} value doesn't reliably say whether the graph actually changed**

For addNode/removeNode/removeEdge/update, the structural store mutation always happens synchronously before any animation, so cancel() (and the resulting {canceled:true}) NEVER undoes it. For condense/split, the structural mutation is deferred into the async 'converge' phase (src/condense-anim.js:95-137): calling cancel() before that phase runs prevents the merge entirely, but calling it after the merge has landed only cancels the trailing animation — yet BOTH cases resolve with the identical value {canceled:true}. A caller cannot tell 'nothing happened' from 'the graph changed but the animation was cut short' from the resolved value alone; they'd have to separately re-query g.node(id).

*Evidence:* Scratch script /tmp/claude-0/-home-user-research-graph-library/017f3504-c4d4-53c3-8ef8-da804b30567a/scratchpad/mutations/cancel-semantics.mjs: condense canceled immediately -> `{canceled:true}` and `g.node('merged')` is undefined (m1/m2 survive); condense canceled after pump(20,16) frames -> also `{canceled:true}` but `g.node('merged')` now exists and m1/m2 are gone; addNode canceled immediately -> `{canceled:true}` yet `g.node('b')` exists. README.md:123-124 documents only 'await g.addNode(…), g.condense(…).cancel()); overlapping calls cancel-and-retarget' with no mention of this.

*Independent verification (confirmed):* condense-anim.js: structural store.condense() call happens inside the async IIFE at the converge phase (after phase 1 'highlight' completes), and done(canceled) always resolves {canceled: !!canceled} regardless of whether the mutation already landed. addNode/removeNode/removeEdge mutate synchronously before returning. Same shape of resolved value in both cases confirmed by code inspection.

**[HIGH] g.batch(fn) is not atomic and silently misbehaves with an async callback**

(1) When an op partway through a batch callback throws, ops issued before the throw are already committed to the store and rendered (partial application) — the exception propagates out of batch() but nothing rolls back the earlier ops, contrary to what 'batch' implies to most developers. (2) Passing an async function to batch() (natural if you want to await something before adding more nodes) silently breaks the 'one relayout for many ops' guarantee: because `batch(fn) { batching++; try { fn(g); } ... finally { batching--; } ... }` in src/index.js:865-879 never awaits fn, ops issued after the first `await` inside fn run once `batching` has already returned to 0, landing as a second, separate commit — with no error, warning, or type error (types/index.d.ts:646 types fn as `(g: Graph) => void`, which TypeScript happily accepts an async function against).

*Evidence:* Scratch script /tmp/claude-0/-home-user-research-graph-library/017f3504-c4d4-53c3-8ef8-da804b30567a/scratchpad/mutations/explore.mjs section 6: batch with addNode('b1'); update('does-not-exist', ...) [throws]; addNode('b2') -> batch throws '[smv:missing] "does-not-exist" does not exist', but g.node('b1') is truthy (added) and g.node('b2') is falsy (skipped, as expected since it never ran) — the surprising part is b1 is fully committed/rendered despite the batch failing. Scratch script batch-async.mjs: async batch callback with `addNode('n1'); await Promise.resolve(); addNode('n2')` fires 2 separate 'commit' events instead of 1, and the awaitable batch() returns settles before n2 is even added.

*Independent verification (confirmed):* src/index.js batch(fn): `try { fn(g); } catch (err) { failure = err; } finally { batching-- }` — ops before a throw are already applied to store/rendered (no rollback), and fn is called without await, so an async fn's post-await code runs after batching has returned to 0, landing as a separate commit.

**[MEDIUM] removeNode() cascades silently on compound (container) nodes; the returned handle carries no list of what was removed**

removeNode(id) on a container recursively deletes every transitive descendant plus every edge touching any of them (src/store.js:131-147, the `doomed` closure), but the resolved awaitable from g.removeNode() is just `{canceled:false}` (index.js:701-711) — nothing in the return value tells the caller what else vanished; that's only discoverable via `g.on('remove', ...)` listeners registered ahead of time. README never shows removeNode used on a node with children or incident edges and never mentions the cascade.

*Evidence:* Scratch script /tmp/claude-0/-home-user-research-graph-library/017f3504-c4d4-53c3-8ef8-da804b30567a/scratchpad/mutations/remove-container.mjs: removing container 'clean' (children clean.dedupe/clean.validate, incident edges e1 ingest->clean and e2 clean->build) leaves nodes ['ingest','build'] with edges [] — both formerly-connected siblings end up fully disconnected, and the only signal is whatever 'remove' events a caller happened to be listening for.

*Independent verification (confirmed):* store.js removeNode builds a `doomed` set transitively (children) and deletes all edges touching any doomed node; index.js removeNode() only returns commitOrDefer(null) i.e. {canceled:false}-shaped awaitable, not the removed set — caller must rely on 'remove' event listeners.

**[MEDIUM] condense() silently drops containment when sources have different parents**

store.js:210-213 computes the merged node's parent as `parents.size === 1 ? [...parents][0] : undefined` — condensing nodes from two different containers produces a top-level (no-parent) merged node with no error, warning, or documented rule. README's Condense/split bullet (README.md:85-88) says nothing about parent handling.

*Evidence:* Scratch script /tmp/claude-0/-home-user-research-graph-library/017f3504-c4d4-53c3-8ef8-da804b30567a/scratchpad/mutations/condense-parent.mjs: condensing `a` (parent 'box1') and `b` (parent 'box2') into 'merged' yields `g.node('merged').parent === undefined`.

**[MEDIUM] GraphError is not part of the public API and its ~17 error codes are undocumented outside source**

src/index.js imports GraphError from store.js but never re-exports it (`await import('sparkle-motion-visualizer')` has no GraphError key), so `instanceof GraphError` checks are impossible for a consumer; you must catch structurally via `.code`, which is documented only in a code comment on `SmvErrorLike` in types/index.d.ts:50-55, never in README. ### Recommendations

- **Clone in g.node()/g.edge() like the rest of the query sugar** *(impact: high, effort: small)* — Route the singular accessors through query.js's cloneItem() (or an equivalent) so g.node(id)/g.edge(id) return copies, matching the 'read-only, returns plain copies' contract the README already states for the plural query methods. If a live handle is intentionally kept for performance-sensitive callers, expose it under a differently-named, clearly-documented method instead.
- **Surface what actually mutated in the resolved value, and split 'the graph changed' from 'the animation finished'** *(impact: high, effort: medium)* — Have mutation awaitables resolve with something like `{canceled, applied}` (or `{canceled, ids}` for removeNode/condense/split) so a caller can tell, without a follow-up query, whether the structural change actually landed — this is especially important for condense/split where the timing of cancel() relative to the internal 'converge' phase currently produces two structurally opposite outcomes behind the same {canceled:true} value.
- **Document batch()'s non-atomicity and forbid/guard against async callbacks** *(impact: high, effort: small)* — Add a paragraph to the README stating batch(fn) is not transactional (ops before a thrown error stay applied) and that fn must be synchronous. Cheaply and defensively, also detect a Promise return from fn (e.g. `const r = fn(g); if (r && typeof r.then === 'function') throw new GraphError('batch-async', ...)`) so misuse fails loudly instead of silently splitting into extra commits.
- **Publish an error-code reference and export GraphError (or a documented type guard) from the public entry** *(impact: medium, effort: small)* — Add a table of every GraphError `code` (dangling, dup-id, missing, non-convex, split-container, split-no-entry, split-no-exit, parent-cycle, unbounded-loop, etc.) with a one-line trigger description to the README's API section, right next to the mutation method list. Either re-export GraphError from src/index.js for instanceof checks, or add a documented `isGraphError(e)` / `SMV_ERROR_CODES` export so consumers don't have to grep source.
- **Document removeNode's cascade and condense's parent-merge rule with worked examples** *(impact: medium, effort: small)* — Extend the README's Condense/split section with (a) a one-line note + example that removeNode(containerId) removes all descendants and every touching edge, and that the full removed set is only available via `g.on('remove', ...)`, and (b) a note that condensing nodes with different parents produces a top-level merged node unless the new node spec sets `parent` explicitly. Add a minimal condense() worked example mirroring the split() one already present.

### Verified issues

**[HIGH] Unparseable duration strings fail completely silently**

A plausible typo like `duration: "45mins"` (instead of `"45m"`) parses to `null` via parseDuration's regex and falls back to the exact same 600ms default dwell used for a node with NO duration at all — with zero console warning, thrown error, or any other signal. A developer has no way to discover the typo except noticing the animation timing looks off.

*Evidence:* src/run.js:22-33 (DURATION_RE, returns null on non-match), src/run.js:149-163 (dwellOf: `sec == null ? DWELL_NO_DURATION : ...`). Verified via scratchpad script: `parseDuration("45mins")` -> `null`; `mount(el, {nodes:[{id:'a'},{id:'b',data:{duration:'banana'}}], ...})` succeeds with no throw, `run.duration` identical (1500ms) to the no-duration case. `grep -na "console\." src/run.js src/store.js src/run-transport.js` returns no matches — no warning path exists anywhere in this code.

*Independent verification (confirmed):* Verified via repro: parseDuration("45mins") returns null (regex requires unit token to consume to end of string). compileRun with 'b' having duration:'45mins' produces identical run.duration (600) as a run with no duration at all. grep for console.* in src/run.js, src/store.js, src/run-transport.js returns nothing — no warning path exists.

**[HIGH] Negative duration strings corrupt event ordering and node status**

parseDuration's regex accepts a leading sign (`[+-]?`), so `duration: "-5s"` parses to -5 and is not rejected or clamped anywhere before it feeds the dwell-time formula, producing a segment with t1 < t0. The resulting node status window becomes inverted, causing the node to report status 'done' before it has even 'entered', and the sim's own time-sorted events array places a node's 'finish' event before its causally-preceding 'enter' event.

*Evidence:* src/run.js:145-163 (dwellOf, unclamped), src/run.js:272-281 (startDwell: `segment(tk, {kind:'node', id: nodeId, t0: t, t1: t + d})` with d possibly negative), src/run.js:356-364 (nodeWindow from/to). Verified via scratchpad script (node b: `data:{duration:'-5s'}`, node c: `data:{duration:'10s'}`): resulting `sim.events` is `[..., {t:600, type:'finish', nodeId:'b'}, {t:900, type:'enter', nodeId:'b', edgeId:'ab'}, {t:900, type:'start', nodeId:'b', dwellMs:-300}, ...]` — 'finish' at t=600 sorts before the 'enter'/'start' at t=900 for the same node.

*Independent verification (confirmed):* Verified via repro: node b duration '-5s', node c duration '10s' (sets maxSec=10). dwellOf for b computes 300+1200*(-5/10) = -300ms, unclamped. Resulting events array has {t:600,type:'finish',nodeId:'b'} appearing before {t:900,type:'enter'/'start',nodeId:'b'} for the same node/token — exactly the inverted ordering claimed, matching src/run.js:145-163 (dwellOf) and 272-281 (startDwell).

## Live mode (Mode B) event replay — 2.7/5

**[HIGH] finish() on a node that never started silently produces a phantom 'done' state**

run.finish(id) does not check that the node has any active occupants. When nodeQueue is empty, doFinish splices 0 entries, the for-loop that fans tokens out to children never runs, and nodeStatus is still set to 'done' because q.length===0. The node reports status:'done', progress:1, occupancy:0 with no tokens ever created and no downstream propagation, and no error/warning is raised.

*Evidence:* src/run-live.js:249-279 (doFinish); reproduced with a scratch script: run.finish('a',{at:5}) on a fresh transport → run.state().nodes.a === {status:'done',progress:1,occupancy:0}. Not covered by any test in test/run-live*.test.js (grepped for 'before.*start' and 'finish.*without' — no hits).

*Independent verification (confirmed):* Reproduced directly: replayLive with only a finish('a') event on a fresh graph yields nodes.a = {status:'done',progress:1,occupancy:0} and nodes.b stays pending (no fan-out). src/run-live.js:154 pre-populates nodeQueue with an empty array for every known node id, so doFinish (src/run-live.js:249-279) splices 0 entries from an empty queue, the for-loop over `finished` never runs (no children/tokens), and `nodeStatus.set(nodeId, q.length===0 ? A typo'd id in a live feed produces silent data loss instead of a debuggable error.

**[HIGH] replayLive's cost grows worse than linearly with log size, causing multi-second per-frame stalls on realistic live-session logs**

**[MEDIUM] Wildcard g.on('*', fn) is real but undocumented and mistyped (fn receives (type, payload), not (payload))**

*Evidence:* Reproduced live: script /tmp/.../scratchpad/extensibility/06-wildcard-event.mjs registers `g.on('*', (a,b) => console.log(a,b))`; output on an `update()` call: `wildcard listener called with: "update" and object` — confirming `a` = type string, `b` = payload, contradicting the single-arg typed signature.

## Accessibility surface — 3.0/5

The accessibility surface's documented happy path — tree ARIA (role=tree/treeitem, aria-level, aria-expanded, label·status naming), arrow/Home/End/Enter/Space keyboard nav, and focus re-homing on structural commits — is accurately described and works exactly as claimed (verified against the real engine, not just tests: condense, removeNode, and container-collapse all correctly re-home the roving tabindex instead of dropping focus to <body>). All 31 existing a11y tests pass. However, the two other pieces the scope specifically asks about are weaker than the docs suggest: the linearized `<table>` fallback, presented as an equivalent 'accessible surface' for the `a11y:false` path, silently omits live run status entirely (verified live: the status cell never updates through a full run.start/run.finish cycle) and is completely non-interactive, so switching to it also silently strips all keyboard operability from the widget (no tabindex anywhere) with no documented warning. An integrator following the README alone would ship a setup that looks compliant but would very likely fail a real accessibility audit on run-status announcements and on the table-fallback path specifically.

### Verified issues

**[HIGH] Table fallback never reflects live/simulated run status**

computeRows() (src/a11y-table.js:85-96) derives the 'status' column solely from the static spec's n.data.status; it never reads the data-run attribute that run-render.js writes, and attachA11yTable only re-renders on 'commit'/'update' (src/a11y-table.js:165-168), never on the 'runstatus' event that a11y.js's tree listens to (src/a11y.js:249). Since README explicitly instructs `mount(..., {a11y:false})` + attachA11yTable as the path to make the table 'the accessible surface' for run-status-driven graphs, a screen-reader-only integrator following the docs gets zero indication that any node started or finished a run.

*Evidence:* Ran /tmp/claude-0/-home-user-research-graph-library/017f3504-c4d4-53c3-8ef8-da804b30567a/scratchpad/a11y/check1-table-live-status.mjs against the real mount()/attachA11yTable(): with a11y:false, after run.start('ingest') and run.finish('ingest') the table's status cell for 'ingest' stayed `""` both times, while in the default (tree-on) mode the tree's aria-label correctly updated to 'Ingest · active' then 'Ingest · done'. README.md:229-232 claims the table and tree are 'two views of the same content.'

*Independent verification (confirmed):* src/a11y-table.js:85-96 (computeRows) builds status solely from n.data.status (d.status), never reading data-run. attachA11yTable only re-renders on 'commit'/'update' (lines 165-168), not 'runstatus'. Meanwhile src/a11y.js:112-118/189-194 explicitly prefers data-run over spec status and listens to 'runstatus' via g.on('runstatus', onRunStatus) at line 249 — proving the two surfaces diverge exactly as claimed. README.md:229-231 says 'two views of the same content' and directs a11y:false users to the table as 'the accessible surface'.

**[HIGH] a11y:false removes ALL keyboard operability from the graph, leaving only a static read-only table with no expand/collapse control**

attachA11y (which owns tabindex/role/keydown wiring) is only invoked when opts.a11y !== false (src/index.js:1004); with a11y:false no node gets a tabindex or role at all, so the interactive SVG becomes fully keyboard-unreachable. attachA11yTable's <table> has no interactive elements (no buttons, no tabindex, no role) and no wiring to g.expand()/g.collapse(), so a collapsed container's children are permanently excluded from the table's rows with no way for a keyboard/screen-reader-only user to reveal them. None of this is documented; README presents attachA11yTable as simply 'the accessible surface' with no caveat about losing interactivity.

*Evidence:* check7-a11yfalse-no-tabindex.mjs: with a11y:false, all three .smv-node elements report tabindex=null, role=null. check3-table-interactivity.mjs: for a spec with a collapsed container ('box', children box.a/box.b), computeRows(g) returns only ['in','box','out'] and findInteractive() over the rendered table returns []  no tabindex/role/button anywhere in the table DOM.

*Independent verification (confirmed):* src/index.js:1004: `if (opts.a11y !== false) a11y = attachA11y(...)` — with a11y:false, attachA11y (sole owner of tabindex/role/keydown per a11y.js) never runs. a11y-table.js's <table> only creates <caption>/<thead>/<tbody>/<tr>/<td> elements (lines 107-158) — no button, tabindex, or role, and no call into g.expand()/g.collapse(). computeRows uses g.layoutResult().nodes as the visible set (line 55), so a collapsed container's children are simply absent from rows with no in-table way to reveal them.

**[MEDIUM] No aria-live region backs the 'screen reader hears nodes start and finish' claim; unfocused-node status changes are effectively silent**

README.md:218-219 states status changes are announced ('so a screen reader hears nodes start and finish'), but this relies solely on mutating aria-label on a role=treeitem (src/a11y.js:112-118,189-194). Real assistive tech generally only announces attribute changes on the element that currently holds focus, or on elements inside an aria-live region. Grepping the whole src/ tree for 'aria-live' finds none; the only role="status" region in the codebase is director.js's storyboard caption (src/director.js:246,260), which is explicitly unrelated to run/token status. This directly bears on the scope's 'announcements during condense/split' question: there is no live-region mechanism for any of these, so nodes not currently focused change state with no announcement at all.

*Evidence:* grep -rn "aria-live" /home/user/research-graph-library/src/*.js -> no matches. src/a11y.js:112-118 (ariaLabelFor) and :189-194 (onRunStatus) only ever call el.setAttribute('aria-label', ...); no aria-live wrapper is created anywhere in a11y.js.

*Independent verification (confirmed):* grep confirms no 'aria-live' or role="status" anywhere in a11y.js/a11y-table.js/index.js; the only role="status" hit is director.js:246 (storyboard caption, unrelated to node/run status). onRunStatus (a11y.js:189-194) and ariaLabelFor only ever call el.setAttribute('aria-label', ...) on the treeitem itself — there is no live region wrapping it, so per standard AT behavior an unfocused node's status change is not announced.

**[MEDIUM] Loop/iteration badge text fails WCAG AA contrast in the default light theme**

`.smv-loop-badge` (src/styles.js:157) renders 10px text filled with `--smv-condense:#f0a000` over the light-theme background/fill tokens (`--smv-bg:#fbfbfd`, `--smv-fill:#ffffff`, src/styles.js:13-27). This badge is correctly aria-hidden (excluded from the accessibility tree per src/render.js:164/render-run.js:64), but aria-hidden does not exempt it from WCAG 1.4.3 (Contrast Minimum), which applies to all visually rendered text regardless of AT exposure — sighted low-vision users still need to read it. This is exactly the 'color contrast of tokens/badges' item named in scope, and it is undocumented.

*Evidence:* Computed relative-luminance contrast (standard WCAG formula) for #f0a000 against #fbfbfd = 2.09:1 and against #ffffff = 2.16:1 — both well under the 4.5:1 AA minimum for text under 18px/14px-bold (see /tmp/claude-0/-home-user-research-graph-library/017f3504-c4d4-53c3-8ef8-da804b30567a/scratchpad/a11y/ inline python calculation output). Dark theme is fine (8.43:1).

*Independent verification (confirmed):* src/styles.js:157 sets .smv-loop-badge fill to var(--smv-condense) at 10px/600 weight; --smv-condense:#f0a000 (line 27) against light-theme --smv-bg:#fbfbfd (line13)/--smv-fill:#ffffff (line14). #f0a000 on white/near-white computes well under 4.5:1 (evaluator got ~2.1-2.2:1), consistent with WCAG 1.4.3 failure for text this size; nothing in styles.js or README documents/excepts this.

**[LOW] Keyboard 'reading order' does not track layout.dir; TB/BT graphs get column-major, not rank-major, arrow-key traversal**

readingOrder() (src/a11y.js:38-46) is a fixed sort — primary key x ascending, secondary key y ascending — independent of the mount's `layout.dir`. For LR/RL layouts this happens to line up with the graph's rank order (ranks vary along x), but for TB/BT layouts (ranks vary along y, a first-class documented `layout.dir` value per README.md:116-117) the same sort produces a column-major walk: it exhausts one x-column across all ranks before moving to the next column, rather than visiting rank 1 (top) left-to-right, then rank 2, etc. README.md:216 just says 'Arrow keys move focus in reading order' with no qualification.

*Evidence:* check6-tb-reading-order.mjs mounted a real 2-rank/2-per-rank TB graph (a1,a2 rank1; b1,b2 rank2) and read g.layoutResult(): a1(x=50,y=38) a2(x=138,y=38) b1(x=50,y=130) b2(x=138,y=130). readingOrder(lr) returned ['a1','b1','a2','b2'] — ArrowRight/Down from a1 jumps straight down to b1 (next rank, same column) before ever reaching a2 (same rank, next column).

*Independent verification (confirmed):* src/a11y.js:38-46 readingOrder() sorts strictly by x then y with no reference to layout.dir or any orientation parameter, so for TB/BT layouts (ranks vary in y) it produces column-major ordering as described. README.md:216 states 'Arrow keys move focus in reading order' with no directional qualification, and layout.dir is a documented option (README.md:116-117 per evidence).

### Recommendations

- **Wire the table fallback to live run status** *(impact: high, effort: medium)* — In src/a11y-table.js, add a `g.on('runstatus', render)` subscription alongside the existing 'commit'/'update' ones, and have computeRows() prefer a live data-run value (exposed via a small g.runStatus(id) accessor, or by reading the same DOM attribute a11y.js already writes) over the static spec's data.status, mirroring exactly what a11y.js's ariaLabelFor() already does. Cover it with a test analogous to a11y-fixes.test.js's 'aria-label follows live run status' but asserting on the table's status cell.
- **Document (and/or fix) the a11y:false interactivity trade-off explicitly** *(impact: high, effort: small)* — At minimum, add a sentence to the README Accessibility section stating that `a11y:false` removes all keyboard/tabindex handling from the graph itself, so `attachA11yTable` becomes a read-only, non-expandable view, and that collapsed-container children are unreachable through it. - **Add an aria-live region for run-status changes on non-focused nodes** *(impact: medium, effort: medium)* — Introduce a single visually-hidden `role="status"` (or aria-live="polite") container in attachA11y, and push a short text update ('Ingest started', 'Ingest finished') into it from onRunStatus() in addition to (not instead of) the per-node aria-label update, so status changes on nodes the user isn't currently focused on are still announced — matching what the README already claims happens.
- **Fix or document loop-badge contrast** *(impact: medium, effort: small)* — Darken --smv-condense for light theme (e.g. to something around #b8730a, which clears 4.5:1 against #fbfbfd/#ffffff) or bump the badge's font-weight/size into the 'large text' 3:1 exemption deliberately and document that choice. - **Make readingOrder direction-aware or document its limitation** *(impact: low, effort: medium)* — Either compute reading order as rank-major using the same rank/order data the layout engine already produces (src/engine.js) rather than a raw x/y sort, or, cheaper, document plainly that keyboard 'reading order' is always screen left-to-right/top-to-bottom regardless of layout.dir, so integrators building TB/BT flowcharts know arrow-key traversal will not match the graph's own rank flow.
